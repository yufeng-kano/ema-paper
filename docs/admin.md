# Operator console

The operator's own pages inside Ema Paper — 管理後台, *Admin console* — the decision of 2026-10-27: the people the operator lets in sign in with the Google account they already use the app with, and do in pages what took hand-written SQL before. The console was built in five steps (§ Roadmap); the first was its skeleton — the permissions, the groups that hand them out, the sign-in rules, the audit log — and two pages, *Groups* and *Audit*; the second added *Users*, with the grants of credits and days an operator makes to an account (§ Users and grants); the third added *Redeem codes* (§ Redeem codes); the fourth the *Overview*, *Jobs* and *Usage* pages, what the deployment is doing and what its model calls cost (§ Overview, jobs and usage); the fifth, *Settings*: twelve settings of `.env` — the models, their prices, the credit rate, the Free plan, the paid plans and the packs — that the database may override, changed in a page and in effect without a restart (§ Settings). The redeem-code CLI, `python -m sightread.codes`, stays beside that page, on the same functions ([self-hosting.md](./self-hosting.md) § Redeem codes).

What it is not: no deploys or container operations; no value of `.env` changed — the settings page overrides twelve of them in the database and restores them, never `.env` itself — and no secret of it shown, not even in part; **no user's content** — no route under `/api/admin` returns a document, an original, a note, a conversation, a memory or a file of the workspace — and **no signing in as another user**; no deleting or suspending an account (a reader deletes their own, [auth.md](./auth.md) § Deleting the account); no refunds (they are made in the payment provider's dashboard, [billing.md](./billing.md) § Kano Pay); nothing of Kano Proxy; and no permission limited to some users — a permission covers its whole area.

**Off until configured.** With `OWNER_EMAILS` empty the console does not exist: the API mounts no `/api/admin` route, so every such path answers the 404 any unknown path answers (`invalid_request`, *Not Found*), `GET /api/me` answers `console: false`, and the web app's `/admin` pages show the Not Found page. Setting it needs the api container recreated, not restarted (§ Configuration).

## Permissions

| Permission | Lets you |
|---|---|
| `users.read` | see accounts: the list and one account's detail (§ Users and grants) |
| `users.write` | add credits or days of a paid plan to an account (§ Users and grants) |
| `codes.read` | see redeem codes, masked (§ Redeem codes) |
| `codes.write` | create and disable redeem codes (§ Redeem codes) |
| `jobs.read` | see the overview, the jobs, usage and cost per model, and the connections' status (§ Overview, jobs and usage) |
| `jobs.write` | put a stuck job back in the queue (§ Overview, jobs and usage) |
| `groups.read` | see the groups, their permissions and their members |
| `groups.write` | create, rename and delete groups, change their permissions, add and remove members — within the rules below |
| `audit.read` | read the audit log (§ The audit log). There is no `audit.write`: a record is never changed |
| `settings.read` | see the settings the database may override — each one's value, whether it comes from the database or `.env`, `.env`'s beside a database one, who changed it and when — and whether each secret of `.env` is set, never its value (§ Settings) |
| `settings.write` | override them in the database, and restore them to `.env` (§ Settings) |

- **Fixed in code, not in the database.** `ALL_PERMISSIONS` in `sightread/admin/permissions.py` is the ordered list above: two strings per area, `<area>.read` and `<area>.write`, the areas in the order `users`, `codes`, `jobs`, `groups`, `audit`, `settings`, `audit` with a read only. The areas whose pages come later are in the list from the start, so the matrix a group is edited in never changes shape. A new area is two strings there, its entry in the web app's area list (`app/lib/admin.ts`) and its words in both catalogs — no migration; the owner group holds it at once.
- **Permissions add up; nothing denies.** A person may be in several groups and holds the union of their permissions. There is no deny rule and no per-user exception.
- **Write includes read.** A group's list is normalized before it is stored: an unknown string is refused (**422** `invalid_request`), a repeated one counted once, every `<area>.write` brings its `<area>.read`, and the list is kept in `ALL_PERMISSIONS` order. Unticking a read while its write stays ticked therefore changes nothing.
- **Any permission opens the console.** `read` shows an area's page, `write` the buttons on it. Hiding is only the page's courtesy: every `/api/admin` route checks its own permission on the server, and permissions are read from the database on every request, so a change applies at the member's next request, without signing in again.
- **No escalation.** An operator hands out and takes away only what they hold themselves, and changes only groups that give nothing beyond it: (a) a group's permissions are changed — on one being created or one being edited — only by someone who holds every permission the group gives and every permission the change ticks, so a group stronger than the operator keeps its list; (b) a group's members are added or removed only by someone who holds every permission of that group — its effective list, so the built-in group's members are managed only by someone holding every permission: an owner, or an account whose groups between them give every permission, which can already do everything an owner can; (c) a group is deleted only by someone who holds every permission it gives; (d) a member is added by account id (`{user_id}`) only by someone who also holds `users.read` — ids can be walked one by one, and each answer names an account — while adding by address needs only the address, and answers with that account's name as the member list shows it. Anything else answers **403** `permission_denied`. A rename needs `groups.write` alone: a name grants nothing. A change to a group or its members reads the operator's permissions again under the group's row lock (§ Groups), so an owner removed while their own request waited on the owner group no longer holds what the removal took.

## Groups

- **Code checks permissions, never group names.** A group binds people to permission strings. What code compares is a permission string or the `builtin` flag — never a name, not even `owner`'s.
- **A name** is 1–32 characters of `a`–`z`, `0`–`9`, `_` and `-`, starting with a letter or a digit (`^[a-z0-9][a-z0-9_-]*$`), unique among the groups: a taken one answers **409** `admin_conflict` (`name_taken`). The web app checks the same rule before it sends.
- **The built-in group, `owner`.** Exactly one group carries `builtin` true — a partial unique index holds it to one. It gives every permission of `ALL_PERMISSIONS`, those added later included, whatever its stored list says; that list is kept empty. It cannot be renamed, deleted or given other permissions (**409** `admin_conflict`, `builtin`), and its last member cannot be removed (**409** `admin_conflict`, `last_owner`) — counted under the group's row lock, so two removals at once cannot both pass. The migration creates it ([database.md](./database.md) § Rules), and the code creates it too wherever it needs it and finds none (get or create; a second insert racing the first is absorbed by the index and read back), so nothing depends on the seed — a database built from the models, as the tests' is, has none.
- **Owners come from `OWNER_EMAILS`.** When someone signs in with Google, Google has verified the address — `email_verified` is the boolean `true` in the ID token's claims — and the address, trimmed and in any letter case, is one of `OWNER_EMAILS`, they join the owner group in the same transaction as the session the sign-in creates, with one audit row (`groups.owner_joined`, § The audit log). The join is idempotent: someone already in the group changes nothing and writes no row, and two sign-ins at once never fail. An address Google has not verified never joins, listed or not. The local dev login ([auth.md](./auth.md) § 1, `APP_ENV=local` only) does the same for `dev@localhost`, counted as verified, so a test or a local demo becomes an owner with `OWNER_EMAILS=dev@localhost`. A sign-in's join records the member as their own `added_by`.
- **Configuration never revokes, and a listed address comes back.** Taking an address out of `OWNER_EMAILS` removes no one — an owner removes the membership on the Groups page. The reverse holds too: an owner removed on the Groups page while their address is still listed joins again at their next Google sign-in. To take an owner's access away for good, take the address out of `OWNER_EMAILS` (and recreate the api container, § Configuration), then remove the membership; the built-in group's *Remove* dialog says so. A listed address that has never signed in has no account yet and joins at its first sign-in. Emptying `OWNER_EMAILS` turns the console off and keeps every group and membership; listing an address again brings them back as they were.
- **Members are accounts.** Adding someone by address needs an account that has signed in at least once: the address is matched trimmed, in any letter case, exactly. None answers **404**; more than one — `users.email` is not unique, and a Google account deleted and made again signs in as a new `sub` — answers **409** `admin_conflict` (`email_ambiguous`), and that person is added by account id (`{user_id}`, which the Users page sends, § Pages; it needs `users.read` too, § Permissions). Adding someone already in the group answers 200 and changes nothing. The account's row is locked for key share while it is added — enough to make a deletion of it wait, never in the way of a sign-in of it running at the same time.
- **Deleting a group** removes its memberships; its members keep whatever their other groups give them.
- **Deleting an account** takes its memberships with it and is never refused for them ([auth.md](./auth.md) § Deleting the account). Deleting the last owner's account therefore empties the owner group: the console then has no owner until an `OWNER_EMAILS` address signs in again — as a new account, which joins as any listed address does. A membership the deleted account had added keeps its row, with `added_by` NULL; the audit rows it made keep theirs, with `actor_id` NULL (§ The audit log).

## Signing in

- **Browser sessions only.** Every `/api/admin` route reads the Google session's cookie ([auth.md](./auth.md) § 1) and nothing else. A request that carries an `Authorization` header — an API key, an OAuth access token, an upload ticket, anything — answers **401** `auth` even when it also carries a valid session cookie; a request with no cookie, or one whose session is unknown or expired, answers **401** `auth`. A mutation also needs the `X-Requested-With` header every control-plane mutation carries (**403** `auth` without it, [api.md](./api.md) § Control plane).
- **A short window.** Once a session is older than `ADMIN_REAUTH_HOURS` (12) — measured from `sessions.created_at`, which a sign-in sets and nothing renews — a console route answers **403** `reauth_required`. Signing in again makes a new session, and the window starts over; the rest of the app goes on with the old session for its 30 days. Google is not asked to prompt again, so a browser still signed in to Google comes back without a password: the window bounds what an old cookie can do, not what a stolen Google account can.
- **The order of refusals:** the console off (404), then a foreign credential or no session (401), then a mutation without `X-Requested-With` (403 `auth`), then the route's permission missing (**403** `permission_denied`), then the session past the window (**403** `reauth_required`), then the route's own refusals (§ Refusals). Someone who lacks the permission is never sent to sign in again for nothing.
- **`GET /api/admin/me` refuses on neither permissions nor the window** — it is how the pages learn both: an account in no group gets an empty list, a session past the window `reauth_required: true`.
- **`GET /api/me` says whether to offer the console:** `console` is true while the console is on and the account holds any permission. It applies no window, so the account menu keeps its *Admin console* item while the console asks for a new sign-in ([api.md](./api.md) § Control plane).

## The audit log

Every change made through the console writes one `audit_log` row in the transaction that makes the change, so neither exists without the other ([database.md](./database.md)). A request that changes nothing — a `PATCH` to the values already stored, adding someone already in the group, a grant sent again with its `request_id` — writes no row.

| Column | Holds |
|---|---|
| `actor_id` | who made the change: the signed-in account; NULL once that account is deleted |
| `permission` | the permission the route required (`groups.write`); NULL for a sign-in's owner join, which no permission allowed |
| `action` | `<area>.<verb>` (below) |
| `target_type`, `target_id` | what was changed: `group`, `user`, `code`, `job` or `setting` and its id as text (a job's is its UUID; a setting's is its key, `CREDIT_USD`), with no foreign key — a record outlives what it names |
| `before`, `after` | the fields the change touched, as they were and as they became (JSON; NULL where there was nothing before or is nothing after) |
| `ip` | the request's client address (below) |
| `created_at` | when |

The actions:

| Action | Target | `before` → `after` |
|---|---|---|
| `groups.create` | the group | NULL → `{name, permissions}` |
| `groups.update` | the group | the fields that changed, of `name` and `permissions`, as they were → as they became |
| `groups.delete` | the group | `{name, permissions, member_ids}` → NULL |
| `groups.add_member` | the member (`user`) | NULL → `{group_id, group}` — `group` the group's name at the time |
| `groups.remove_member` | the member (`user`) | `{group_id, group}` → NULL |
| `groups.owner_joined` | the owner group | NULL → `{user_id}`; the actor is the person who signed in, `permission` NULL |
| `users.grant_credits` | the account (`user`) | `{credits_available}` → `{pack_id, credits, expires_at, credits_available, reason}` — the balance a charge is measured against before and after, the pack written (§ Users and grants) |
| `users.grant_days` | the account (`user`) | `{day_bank, period}` → `{request_id, plan, days, day_bank, period, reason}` — `request_id` the request's, which a day grant sent again is found by, `day_bank` the bank as the period decision leaves it, `{plan_id, days_banked, period_start, period_end}` or null for an account that never had one, `period` the current period's `{source, plan, end}` |
| `codes.create` | the batch's first code (`code`) | NULL → `{count, kind, credits, valid_days, max_uses, redeem_by, ids}` for credits, `{count, kind, plan_id, days, max_uses, redeem_by, ids}` for days of a plan — `ids` every code the batch made (§ Redeem codes) |
| `codes.disable` | the code (`code`) | `{disabled_at: null}` → `{disabled_at}` |
| `jobs.requeue` | the job (`job`) | `{user_id, status, worker_generation, pages_done}` → the same four: `running` with the generation it had → `queued` with none, `pages_done` the pages it keeps (§ Overview, jobs and usage) |
| `settings.update` | the setting (`setting`, its key) | `{value, source}` → `{value, source}`: the key's text as it was and as it became, and where each came from, `database` or `env` (§ Settings) |
| `settings.reset` | the setting (`setting`, its key) | `{value, source: "database"}` → `{value, source: "env"}`: restored to `.env`, its `.env` text after |

A membership's target is the person whose access changed, so one person's history reads under one target, a grant's the account it went to.

- **What `before` and `after` may hold:** ids, amounts, flags, permission strings, a group's name, dates as ISO 8601 strings — JSON as written, nothing a JSON encoder would have to guess. **Never** an email address or a person's name, a document's or a message's text, a secret or a token, a redeem code in plaintext: the [auth.md](./auth.md) § Logging rule holds for the log as for the server's logs. The one free text a record holds is a grant's `reason`, the operator's own note (§ Users and grants), which the operator writes under the same rule; a setting's record holds the setting's text — a model id, a number, a price or plan table — and none of the settings the console changes is a secret (§ Settings). Who a row is about is read when the log is read — the actor's email and name, and a user target's email, are joined from `users` then, never stored in the row.
- **Never edited, never deleted.** No route updates or deletes a row, and nothing sweeps the table: the log is kept as long as the deployment.
- **It outlives the accounts it names.** Deleting an account sets `actor_id` NULL on its rows (the page prints *Deleted account*), and a row whose target it was keeps the id, which no longer resolves to an address. A deleted account's email and name leave the log with it; its ids and amounts stay, and so does the `ip` of every row it made — the address it changed things and signed in as an owner from, kept with the row as long as the deployment, as the Privacy page says (§ What an operator sees).
- **The address behind proxies.** `ip` is the client address uvicorn reports for the request. In production Caddy sets `X-Forwarded-For` to the address that connected to it — it drops one a client sent — and uvicorn takes the client from that header because the production compose file sets `FORWARDED_ALLOW_IPS: "*"` on `api`, which nothing outside the compose network reaches ([deployment.md](./deployment.md)). Behind a front proxy that passes TLS through by SNI without the PROXY protocol, what connected to Caddy is the router, so the router's address is what the row records. NULL when the request has none.

## Redeem codes

The console's side of [billing.md](./billing.md) § Redeem codes: the codes `python -m sightread.codes` makes, lists and disables, through the same functions of `billing/codes.py` — `create_codes`, the disable and the status rule — so a code made at either door is a code of the other, and a rule changed once changes for both. The CLI stays, for a server without the console and for the one thing the console never shows again: a code in full after it was created.

- **Creating takes the CLI's fields.** `kind` — `credits` (`--credits`) or `plan` (`--plan`) — then for credits `credits` and `valid_days` (`--valid-days`, 365: how long the credits last once redeemed), for a plan `plan_id` and `days` (`--days`); `count` (`--count`, 1), `max_uses` (`--uses`, 1: how many accounts may redeem one code), `redeem_by` (`--redeem-by`, a date: the code can be redeemed until 23:59:59 UTC that day, none = no date) and `label` (`--label`, the operator's note, never shown to a user). The other kind's fields are ignored, as the CLI's default `--valid-days` is on a plan code.
- **One set of rules for both doors.** `create_codes` checks the batch before it writes anything: the kind is one of the two; `count`, `max_uses` and `credits` are present and whole numbers from 1 to 2,147,483,647, what their columns hold; `valid_days` and `days` are present and whole numbers from 1 to 36,500 — a hundred years, so the dates a redemption works out from them (a pack's expiry, a granted period's end) stay dates; a plan is one of `KANO_PAY_PLANS_JSON`; the label is at most 255 characters; `redeem_by` is not already past — today, UTC, at the earliest — since a code born expired would be handed out and refused to everyone; and one batch makes at most `REDEEM_CODES_MAX_COUNT` (1000) codes. The console answers a refusal **422** `invalid_request` with the rule in its message; the CLI prints the same message and exits 2.
- **The plaintext is shown once.** The create answer is the only one that holds the codes in full, as printed (`EMA-XXXX-XXXX-XXXX`): the page shows them in one dialog, with *Copy all* and *Download CSV* — the file built in the browser from that answer, nothing stored — and once it closes the console never shows them whole again. Every other answer names a code masked: the prefix and the first group of four while at least eight characters stay hidden, every other character a `•` (`EMA-7K2Q-••••-••••` for twelve, `REDEEM_CODE_CHARS`' default); a shorter code — under a smaller `REDEEM_CODE_CHARS`, now or when it was made — shows none of it (`EMA-••••-••`). Eight hidden characters leave 32⁸ ≈ 10¹² possibilities, past guessing under the attempt cap ([billing.md](./billing.md) § Redeem codes), whatever the setting. The database still holds them as printed: a code lost after the dialog closed is read back with the CLI's `list`, on the server, by whoever holds the container.
- **What a code is now**, the same rule as the CLI's `list` and the order redemption refuses in: `disabled` once disabled, else `expired` once now is past `redeem_by`, else `used_up` once `uses` has reached `max_uses`, else `plan_missing` for a plan code whose plan `KANO_PAY_PLANS_JSON` no longer names — redemption refuses it as `code_invalid` until the plan is configured again ([billing.md](./billing.md) § Redeem codes) — else `active` — the CLI prints `disabled`, `expired`, `used up`, `plan missing` and `live`.
- **Disabling** is by the code's id, behind a second confirmation: the code is dead from that moment, and what was redeemed with it stays — credits, days, the redemptions. Disabling a code already disabled changes nothing and writes no record.
- **The records.** `codes.create` is one row per batch, its target the batch's first code, with the amounts and the ids of every code it made (§ The audit log); `codes.disable` one row per code disabled. Neither holds a code, plain or masked, nor its label — free text the operator typed, which may name a person; the list joins the label to the id. The CLI writes no record: it runs on the server, outside the console, under whoever holds the container.

## What an operator sees

- **Groups and audit.** `groups.read` shows every group's members — their address and name, who added them and when. `audit.read` shows every record: when, the actor's address and name, the action, the permission it used, a user target's address or a group target's name, the source address, and `before` and `after` as stored.
- **Users.** `users.read` shows every account: its address, name and sign-up date, its plan, period and Pay subscription's state, its credits by source and its day bank, its storage used, how many jobs it has on record and, of its five newest, the file's name, the pages, the status and the times — and, to a caller who also holds `groups.read`, the groups it is in (§ Users and grants).
- **Redeem codes.** `codes.read` shows every redeem code masked, with what it grants, its uses, its date, its status, its label and who disabled it in the console; the full codes only to the `codes.write` holder who creates them, in the answer that creates them (§ Redeem codes).
- **Jobs and usage.** `jobs.read` shows every job on record — when it was created, started and finished, whose it is (the account's address to a caller who also holds `users.read`, its id otherwise), its pages, its model, its status and a failed one's reason, never its file name — the tokens and cost per UTC day and model of every account together, and the deployment's state: the worker, the Kano Proxy and Kano Pay connections, the number of accounts (§ Overview, jobs and usage).
- **Settings.** `settings.read` shows the twelve settings the database may override — each one's text, where it comes from, `.env`'s text beside a database one, and who changed it last and when — and, for each secret of `.env`, whether it is set: never its value, its length or any of it (§ Settings).
- **The boundary, for every area.** The console shows account and billing metadata — who an account is (address, name, when it signed up), what it has (plan, credits and where they came from, storage used) and what it ran (its parses' file names, page counts, status and failure reasons, tokens and cost per model) — and the record of what operators changed. **Never content:** no document's text, original, figures or images, no note, no conversation, message, memory or memory file, no instruction, prompt or skill an account wrote, no file of the workspace; no API key, session, OAuth token or upload ticket; no secret of `.env` (a setting that is a secret is shown only as set or unset); no redeem code in plaintext after the moment it was created. No route signs anyone in as another user.
- **The Privacy page says so**, in a paragraph at the end of its section 3, *Who else receives it*: who can open the console (the operator and the people the operator gives access to it), the metadata above, never the content, and that what they change in the console is recorded with who made the change and the IP address it came from, with ids and amounts and never content, in records that stay after an account is deleted — without its address or name, but with the IP addresses of the changes it made ([web.md](./web.md) § Pages).

## Users and grants

The second step: the accounts, read with `users.read`, and two grants an operator with `users.write` makes to one — credits, or days of a paid plan. Both go through the billing code a redeem code goes through ([billing.md](./billing.md) § Operator grants), so a grant is spent, banked and shown to the account as a code's would be. Neither is refunded, and nothing undoes one: a grant made by mistake stays made, which the grant dialog says before it is sent.

- **The list** (`GET /api/admin/users`) holds every account, the newest sign-up first, `ADMIN_PAGE_SIZE` to a page (§ Routes). `q` keeps the accounts whose address or name contains it, in any letter case (`%` and `_` match themselves). `plan` keeps those whose current period belongs to that plan — `free`, or a `planId` of `KANO_PAY_PLANS_JSON`; any other value is **422** — decided as every read of the period decides it ([billing.md](./billing.md) § Periods): a paid subscription running now on a configured plan; else the granted days of a configured plan, running or waiting in the bank; else Free. A row carries the account's id, address and name, its plan and what its period is (`subscription`, `grant` or `free`), the credits available — the period's and the active packs' together, what a charge is measured against — the workspace's storage as the quota counts it ([workspace.md](./workspace.md) § Quota), the jobs it has on record, and when it signed up. Storage is measured for every row of the page, one account after another, so a page of large workspaces takes a moment. A workspace the walk cannot measure — a tree nested past its depth bound — reads `null`, which the page prints as unknown, and the rest of the page is answered as usual; a directory the walk cannot read is skipped, as the quota's own measure skips it, so its figure can be low rather than unknown. The jobs are those on record: a finished parse no document names is deleted after `PARSE_RETENTION_DAYS` ([jobs.md](./jobs.md) § Retention), so this is not every parse ever run. Beside the page, `plans` lists the plans the filter offers — `free` first, then `KANO_PAY_PLANS_JSON`'s order — each with how many accounts are on it now, whatever `q` and `plan` say; `grant` gives the facts the grant dialog shows: `credit_usd` (`CREDIT_USD`, the model cost one credit stands for), `valid_days` (`ADMIN_GRANT_VALID_DAYS`), `max_credits` (`ADMIN_GRANT_MAX_CREDITS`) and `max_days` (`ADMIN_GRANT_MAX_DAYS`).
- **One account** (`GET /api/admin/users/{id}`; **404** for no such account) gives who it is — id, address, name, sign-up date — and what it has. Its plan and current period (`source`, `start`, `end`), and its Pay subscription's state when it has a row. Its credits by source: the period's remaining, then the packs bought (`pay`), redeemed (`code`) and granted here (`grant`). That is not the order a charge takes them in: a charge takes the period's first, then the packs of every source together, the earliest expiry first ([billing.md](./billing.md) § Top-up packs, *Spending order*). Each source gives what is left and the earliest expiry among its active packs that still hold credits; `available` is their total. Its day bank (`plan_grants`): the plan, the days waiting and the open granted period, as the period decision leaves it. Its workspace's storage against its plan's quota (`null` when it cannot be measured). How many jobs it has on record, and the five newest: the file's name, the pages parsed and the pages in all, the status, and when it was queued and finished — **never** a page of the result, the prompt or the job's error text. And the groups it is in, given only to a caller who also holds `groups.read` (`null` otherwise), since who holds what is the Groups page's to show.
- **Credits** — `POST /api/admin/users/{id}/grants` with `{kind: "credits", credits, valid_days?, request_id, reason?}` — add one pack: a `credit_packs` row with `source` `grant`, `pack_id` `grant`, `id` `grant-<request_id>`, the `credits` asked (1 to `ADMIN_GRANT_MAX_CREDITS`), `purchased_at` now and `expires_at` `valid_days` days later (1 to `ADMIN_GRANT_MAX_DAYS`; `ADMIN_GRANT_VALID_DAYS`, 365, when the body gives none, as long as a top-up pack lasts). There is no grant without an expiry: every pack has an `expires_at`, and the ledger orders and expires packs by it ([billing.md](./billing.md) § Top-up packs). `request_id` is a UUID the page makes each time the dialog opens. A second request with the same one — a double click, a retry after an answer that was lost — writes nothing and answers the pack the first one made, **200** where the first answered **201**, with no second record; a `request_id` whose pack belongs to another account is **409** `admin_conflict` (`request_reused`).
- **Days** — `{kind: "days", plan, days, request_id, reason?}` — add `days` (1 to `ADMIN_GRANT_MAX_DAYS`) of `plan` to the account's bank. `plan` is a `planId` of `KANO_PAY_PLANS_JSON` (**422** for any other, `free` included), so with no paid plan configured there are no days to give. The days follow a plan code's rules ([billing.md](./billing.md) § Periods, *Granted days*), through the one function both use, `ledger.bank_days`: a paid subscription comes first, and the days wait while it pays; with nothing paying, a granted period opens at once; the bank holds one plan, so days of another plan, while it holds days or runs a period, are **409** `admin_conflict` (`plan_conflict`) and nothing is written. No `redemptions` row is written — there is no code — so the record is the grant's only history; the account sees the days as it sees redeemed ones. `request_id` is the dialog's, as for credits, and the record keeps it (`after.request_id`): a second request with the same one for the same account finds that record under the account's row lock and writes nothing, answering **200** with the plan and days the record holds and the bank and period as they stand now. Days have no row of their own to carry the id, so it is looked for among that account's day grants only; the same id sent for another account is a grant of its own there.
- **One transaction each.** A grant takes the account's row lock and the ledger's lock order ([billing.md](./billing.md) § The ledger), and writes its record in the same transaction: `users.grant_credits` or `users.grant_days` (§ The audit log). It answers `{kind: "credits", pack: {id, credits, expires_at}, credits_available}` or `{kind: "days", plan, days, day_bank, period: {source, plan, end}}` — `period` the current period after the grant: under a paid subscription still the subscription's, the days waiting in `day_bank`; with nothing paying, the granted period that runs, opened by this grant when none ran.
- **The reason** is the operator's note on why — optional, trimmed, at most 200 characters, empty read as none. It is the one free text the console keeps: it is written only into the record's `after.reason`, read on the Audit page by those who hold `audit.read`, and **never** shown to the account, on no page and in no answer of its own. It follows the record's rule (§ The audit log): no address, no person's name, nothing of a document.
- **Adding an account to a group** from its page is the members route by account id (`POST /api/admin/groups/{id}/members` with `{user_id}`, § Routes) under that route's rules: `groups.write`, `users.read`, and every permission of the group held (§ Permissions, *No escalation*).

## Overview, jobs and usage

The fourth step: what the deployment is doing, read with `jobs.read` — its jobs, whether the worker runs, what the model calls cost, whether Kano Proxy and Kano Pay answer — and one change, made with `jobs.write`: a stuck job put back in the queue. **Days are UTC days** throughout — the dates the usage route takes and answers, the overview's *today*, the chart's and the table's days — and the pages say so.

- **Whether the worker runs** is read from PostgreSQL's lock table, never by trying the lock ([jobs.md](./jobs.md) § Queue). The worker holds a session-level advisory lock on `WORKER_LOCK_KEY` (`sightread/jobs/queue.py`) for its whole life, which `pg_locks` shows as a granted `advisory` lock in the current database with the key's high 32 bits as `classid`, its low 32 bits as `objid` and `objsubid` 1 — the form of a lock taken on one bigint. Such a row is `running`: with the holder's connection start (`pg_stat_activity.backend_start`, about when the worker started) and the live generation — the last value `worker_generation_seq` handed out, read without taking one, null before any worker took one. No row is `stopped`. The API never calls `pg_try_advisory_lock`: a probe that found the worker down would take the lock itself, and a session lock left on a pooled API connection would keep every worker from starting. Off PostgreSQL — the SQLite fallback — the state is `unknown`.
- **A stuck job** is a `running` one that no live worker drives: the worker is `stopped`, or it runs with another generation than the job's (`jobs.worker_generation`) — a job a dead or stale worker left. A worker starting puts such jobs back itself; the console's requeue is for the time until it does — a stuck job counts against its account's parse cap and keeps the account from being deleted — and for the rare one a worker's start-up missed. A job the live worker runs is never stuck, however long it has run: requeuing it would leave the run paying for calls it could no longer record, and the same worker would claim the job again and pay for its pages twice. A hung worker is restarted on the server, which the console does not do.
- **Requeue** — `POST /api/admin/jobs/{id}/requeue` — takes the job's row lock and checks, in this order: the job exists (**404**); it is `running` (**409** `admin_conflict`, `not_running` — a queued job waits its turn, a finished one stays as it ended, and a failed parse is its reader's to retry, [jobs.md](./jobs.md) § Retrying failed pages); the worker's state can be read (`worker_unknown`); the live worker does not drive it (`not_stuck`). Then, still under the lock, it does what a worker's start-up does to an orphan: the job's crops are discarded — every attempt directory, before the commit, so a worker that claims the job a moment later cannot lose a new attempt's — and the job goes back `queued`, its start and generation cleared, its failed pages forgotten and its succeeded ones kept, `pages_done` their count. Its credits stay reserved, as for any job not finished ([billing.md](./billing.md) § A parse). The record (`jobs.requeue`, § The audit log) is written in the same transaction, which commits once, and the answer is the job as the list shows it. A refusal changes nothing and records nothing.
- **The jobs** (`GET /api/admin/jobs`) are the jobs on record, newest first, paged, `status` keeping one status — a finished parse no file names is deleted after `PARSE_RETENTION_DAYS` ([jobs.md](./jobs.md) § Retention), so this is not every parse ever run. A row says when the job was created — `jobs.created_at`, which a reader's retry and a requeue keep when they put the same job back in the queue, so it is the job's age, not how long it has waited this time — started and finished, whose it is, how many of the pages it selected are done, the model it runs (its retry's, when a retry named one), its status, and for a failed one `jobs.error`: phrases the runner writes, which name failed pages and their reasons (*2 of 9 pages failed (page 3: rate limited; …)*) and never anything of the document. The account is named by its address only to a caller who also holds `users.read`, by its id otherwise. Beside the page, the count of every status and the worker's state; each running row says whether it is stuck, which is what offers *Requeue*. No file name, prompt, page text or figure is in the answer.
- **Usage** (`GET /api/admin/usage?from=&to=`) adds up `usage_log` — every upstream call, of the parse, check and chat agents, of every account — per UTC day and model over the days from `from` to `to`, both included, with the range's totals. The figures are [api.md](./api.md) § Usage aggregates' and keep its rule: billed cost (`cost`), estimated cost and unpriced calls are never added together, and an unpriced call is counted, never priced at $0. Calls through Kano Proxy carry its estimate, so the pages' *Cost* is `estimated_cost`, a billed amount gets a column of its own only in a range that has one, and the calls without a cost are said, not hidden. A range longer than `ADMIN_USAGE_MAX_DAYS` days is **422**. The figures are those of the accounts that exist: deleting an account deletes its `usage_log` rows ([database.md](./database.md)).
- **The overview** (`GET /api/admin/overview`) gathers in one answer: the queued and running jobs, with when the oldest queued one was created (its `created_at`, kept by a retry and a requeue, as in the list) and how many of the running are stuck; the jobs that failed in the last `ADMIN_FAILED_WINDOW_HOURS` hours (24), with the last one's time; the worker's state; today's usage — the UTC day so far — per model and in total; the number of accounts; the two connections; and, only for a caller who also holds `audit.read`, the newest audit records — the audit list's first page, ten records, or `ADMIN_PAGE_SIZE` when that is fewer, since that setting caps every console read — otherwise the answer has no `audit` key. The database is read first — the newest audit records too — and the request's database session is closed before the two catalogs are asked, together, so a failed read answers its error at once and leaves no request running, and a slow upstream holds no pool connection while the page waits for it.
- **The connections.** Each overview read asks Kano Proxy for its model catalog (`GET {KANO_PROXY_BASE_URL}/openai/v1/models` on the operator's key — free, the request the chat agent's model list makes, [billing.md](./billing.md) § Models and the operator's upstream) and Kano Pay for its catalog (`GET /v1/catalog`, read-only) — once each, both at once, each given `ADMIN_PROBE_TIMEOUT_SECONDS`, and nothing remembered: a catalog kept from minutes ago would say a service answers while it does not. A connection is `ok`; `unconfigured`, with no request made — Kano Proxy without `KANO_PROXY_BASE_URL` and its key, Kano Pay without its four settings, which leaves the deployment on Free alone ([billing.md](./billing.md) § Kano Pay); or `failed`, with the client's own message — the key refused, the status answered, unreachable, no answer in time — never a key or a URL. An error the client does not expect — an answer shaped so that reading it raises — is `failed` too, with *Unexpected error (see the API's log)*, and the API logs it with its traceback: a connection never turns the overview into a 500. With `ok` comes what was read: for Kano Proxy how many models the catalog lists, how many of those `MODEL_PRICES_JSON` prices, and `PARSE_MODEL`; for Kano Pay whether checkout is open and how many plans and packs are on sale — configured here and priced there ([billing.md](./billing.md) § Plans).

## Settings

The fifth step: the settings an operator changes most — the models, their prices, the credit rate, the Free plan, the paid plans and the packs — changed from a page instead of `.env`, without a restart. `.env` stays the default and the database overrides it, key by key: a key without a row is `.env`'s.

- **What the database may override** — these twelve and nothing else (`OVERRIDABLE`, `sightread/runtime_settings.py`), in the page's order: `PARSE_MODEL`, `CHECK_MODEL`, `PARSE_FALLBACK_MODEL` and `MODEL_PRICES_JSON` (models and prices); `CREDIT_USD`, `PARSE_CREDITS_PER_PAGE` and `CHAT_MIN_CREDITS` (credits); `FREE_CREDITS_PER_PERIOD`, `FREE_STORAGE_BYTES` and `FREE_MAX_JOBS` (the Free plan); `KANO_PAY_PLANS_JSON` (the paid plans) and `KANO_PAY_PACKS_JSON` (the top-up packs) — each meaning in the database what it means in `.env` ([billing.md](./billing.md) § Configuration). **Everything else is `.env`'s alone**: every secret and every connection (`SECRET_KEY`, `GOOGLE_*`, `KANO_PROXY_*`, `KANO_PAY_URL`, `KANO_PAY_APP_ID`, `KANO_PAY_API_KEY`, `KANO_PAY_WEBHOOK_SECRET`, `SANDBOX_*`, the search keys, `DATABASE_URL`), every path, the ceilings every plan must fit under (`WORKSPACE_QUOTA_BYTES`, `MAX_JOBS_PER_USER`), `WEB_SEARCH_CREDITS`, `GRANT_PERIOD_DAYS`, the console's own `OWNER_EMAILS` and `ADMIN_*`, and `RUNTIME_SETTINGS_CACHE_SECONDS` ([deployment.md](./deployment.md) § Environment variables). A row whose key is not one of the twelve — written by hand, or by a release that allowed it — is ignored.
- **Stored as the text `.env` would hold.** One `runtime_settings` row per overridden key ([database.md](./database.md)): `value` is the setting exactly as it would stand in `.env` — `0.002`, `150`, a model id, a JSON table — kept as a JSON *string*, never as the JSON it may contain: PostgreSQL's `jsonb` keeps no key order, and `MODEL_PRICES_JSON`'s order is the order the chat agent offers its models in, the first the default ([billing.md](./billing.md) § Models). A value is trimmed of the whitespace around it and is at most 65,536 characters; the rest is the operator's text as sent, and the page keeps a table's order as typed. `updated_by` is who stored it (NULL once that account is deleted) and `updated_at` when.
- **One reading layer, the container always starts.** The API and the worker start from `.env` and check it as they always have, so a container starts whatever the database holds, and apply the database's values after start through one reading layer (`RuntimeSettings`): `.env`'s settings with the rows on top, built anew and checked whole, as at start, then kept in memory for `RUNTIME_SETTINGS_CACHE_SECONDS` (30), counted from the end of the read, before the rows are read again — one read at a time, whoever else asks meanwhile waiting for its answer. A change made on the page empties the API's copy, so the API answers with it at once — a read already under way when the change is written answers whoever waits for it, and is not kept, so the next request reads the rows again; the worker reads it within `RUNTIME_SETTINGS_CACHE_SECONDS`. With no row at all the settings in effect are `.env`'s, the very object the process started with. The API reads the rows on the request's own session, the one its routes then use, so a request never holds a second connection for them, and connects it before it waits for another request's read: the requests waiting each hold a connection, so a read that asked the pool for one while they wait could wait out the pool's timeout. It reads them inside a savepoint, so a failed read is undone alone — the request's transaction stays usable and what it loaded before, such as the signed-in account, stays loaded — and the request goes on with `.env`'s settings or the last ones read; the worker and the CLI read on a session of their own.
- **One snapshot for a piece of work.** A request reads the settings once and uses that copy throughout. The worker takes one before each claim: the per-plan parse caps the claim applies come from it ([jobs.md](./jobs.md) § Concurrency caps), and the job or the chat turn it claims runs on it to the end — a turn's prices, from its first model call to its last settlement, are those of the moment it was claimed, whatever is saved meanwhile ([billing.md](./billing.md) § A chat turn). One exception keeps a model priced a moment ago working: the API offers it at once, while the worker's copy may be `RUNTIME_SETTINGS_CACHE_SECONDS` old, so a claimed turn whose conversation is on a model its snapshot does not price reads the rows again, once, and runs on what it reads — the model priced since runs; one still unpriced fails `model_unpriced` as before. The worker's idle compaction takes one per pass ([jobs.md](./jobs.md) § Chat turns). A parse already queued keeps what it was queued with — its model, check model and fallback, and the credits reserved for it, are written onto the job and its entry at enqueue ([jobs.md](./jobs.md) § Credits). `python -m sightread.codes` applies the database's values the same way when it starts, so the CLI and the console agree on which plans a code may give ([self-hosting.md](./self-hosting.md) § Redeem codes).
- **Checked as the start checks it.** A change — a new value, or *Restore to .env* — is applied to the stored values and the settings they make with `.env` are checked whole, by the checks the API and the worker run at start ([deployment.md](./deployment.md) § Environment variables): a number where a number belongs, `CREDIT_USD` above 0, the credits and `FREE_STORAGE_BYTES` and `FREE_MAX_JOBS` at least 0, the credits — `PARSE_CREDITS_PER_PAGE`, `CHAT_MIN_CREDITS`, `FREE_CREDITS_PER_PERIOD`, a plan's and a pack's `credits` — at most 2,147,483,647, the ledger's 32-bit integers, the Free plan and every paid plan within `WORKSPACE_QUOTA_BYTES` and `MAX_JOBS_PER_USER`, each JSON table well-formed, and every model the deployment runs on its own — `PARSE_MODEL`, `CHECK_MODEL`, `PARSE_FALLBACK_MODEL` — priced by `MODEL_PRICES_JSON` ([billing.md](./billing.md) § Models). A change that fails is **422** `invalid_request` with nothing written, in the checks' own words — `MODEL_PRICES_JSON prices none of: gpt-6-luna`, `FREE_MAX_JOBS: Input should be a valid integer, unable to parse string as an integer` — built from the failed checks' messages alone, never from the settings they checked, which hold every secret of `.env`; neither the answer nor the server's log ever prints those settings.
- **Confirmed when it takes away what accounts have.** A change that removes something in use is answered first with **409** `admin_conflict`, `reason` `impact`, and `impact`: what it removes and how much uses it, with nothing written. The page shows it and, once the operator confirms, sends the change again with `confirm: true`, which applies it. In use means, by what goes: **a priced model** — the conversations on it (`conversations`), which fail `model_unpriced` at their next turn until moved to another model ([billing.md](./billing.md) § Models), the accounts whose chat agent has it chosen (`chat_settings`), and the subagents that name it (`subagents`); **a paid plan** — the subscriptions running on it now (`subscriptions`), which fall to Free at once, the accounts with granted days of it, running or banked (`day_banks`) — a running granted period falls to Free and keeps counting down, banked days wait until the plan is configured again, whatever plan a subscription pays meanwhile — the live redeem codes of it (`plan_codes`), which are then refused as unknown ([billing.md](./billing.md) § Periods, § Redeem codes), and the plan checkouts still open and young enough to be paid (`plan_checkouts`, `checkouts` rows not completed and younger than `KANO_PAY_CHECKOUT_LIFETIME_SECONDS`), whose payment would start a subscription on a plan this deployment no longer configures, so the payer stays on Free ([billing.md](./billing.md) § Kano Pay); **a pack** — the pack checkouts still open and young enough to be paid (`pack_checkouts`, younger than `KANO_PAY_CHECKOUT_LIFETIME_SECONDS`), whose payment would add no credits until the pack is configured again ([billing.md](./billing.md) § Kano Pay); **`FREE_CREDITS_PER_PERIOD`, `FREE_STORAGE_BYTES` or `FREE_MAX_JOBS` lowered** — the accounts on Free now (`free_accounts`), each of which gets the smaller allowance. Each is one `count` — conversations through the index on their model (`ix_conversations_model`), the rest over tables of a row or a few per account and over the operator's codes — and a change that finds nothing in use is applied at once. Storage used is not counted: it is not in the database, and measuring every workspace is the Users page's slow walk, not a confirmation's.
- **Restore to .env** deletes the key's row, checked and confirmed as a change is; the key is `.env`'s again, whatever `.env` says by then.
- **One change at a time.** A change takes a transaction-scoped PostgreSQL advisory lock, then reads the rows, checks, writes and records under it, so two changes at once — one making a model the parse model, another dropping its price — are checked one after the other, never each against what the other replaces.
- **When the database's values no longer fit `.env`.** `.env` can change under them — a ceiling lowered below a stored Free allowance, `PARSE_MODEL` set to a model only `.env`'s own price table priced — and the settings they make together then fail the checks. The reading layer then runs on `.env` alone, so the service keeps working on the values it was started with, logs the checks' message once, and the settings page says so in a banner with that message, until the values are changed or restored. While they are ignored, *Restore to .env* is never refused for failing the checks: it only moves toward `.env`, which passed them at start, so with two values that no longer fit each is restored on its own, `.env` alone staying in effect until the rest fit too (impact is then counted against `.env`, what is in effect). A new value is checked with the rest as always, so it is refused while another stored value still fails: restore that one first. A database the reading layer cannot read keeps the settings last read, logged once until a read succeeds again; it never fails a request.
- **The record.** `settings.update` for a value stored, `settings.reset` for a key restored to `.env`, each with the key as its target and `{value, source}` before and after — the text and where it came from (§ The audit log). A change that changes nothing — the value the row already holds, or *Restore to .env* on a key the database does not override — writes nothing and answers the settings as they are.
- **What does not follow within `RUNTIME_SETTINGS_CACHE_SECONDS`.** The public catalog, `GET /api/billing/catalog` ([billing.md](./billing.md) § Kano Pay), goes out with `Cache-Control: public, max-age=KANO_PAY_CATALOG_TTL_SECONDS` (300): a browser that read it may show the pricing and rates pages' plans, Free allowance and rates as they were for up to that long, while the API already answers the new ones. Lowering `FREE_CREDITS_PER_PERIOD` or a plan's `credits` does not lower a period already running: its row keeps the higher grant, and the new number applies from the next period ([billing.md](./billing.md) § Periods); raising them shows at once. What was queued or started keeps its snapshot (above). A subagent on a model priced on the page less than `RUNTIME_SETTINGS_CACHE_SECONDS` ago, inside a turn claimed on the worker's older copy, is answered in that turn that its model is not priced; the turns claimed after the worker's next read run it. An open page keeps what it showed until it reads again.

## Routes

All under `/api/admin`, mounted only while `OWNER_EMAILS` names an address, each behind the rules of § Signing in; a mutation needs `X-Requested-With` (*+ CSRF* below). Answers are plain JSON objects with times as ISO 8601 UTC strings. A paged list answers `{items: [...], total, page, page_size}`: `page` counts from 1 (default 1; under 1 or above 2,147,483,647 is **422**; past the end, `items` is empty and `total` still counts), and `page_size` is `ADMIN_PAGE_SIZE` unless the query asks for fewer — a larger value counts as `ADMIN_PAGE_SIZE`, under 1 is **422**. Groups and their members are few and come unpaged.

| `POST /api/admin/groups` | `groups.write` + CSRF | `{name, permissions}` → **201** `<group>`. **422** for a name outside the rule or an unknown permission, **403** `permission_denied` for a permission the caller does not hold, **409** `admin_conflict` (`name_taken`) |
| `PATCH /api/admin/groups/{id}` | `groups.write` + CSRF | `{name?, permissions?, based_on?}` → `<group>`: `permissions` the whole new list and `based_on` the list it was edited from — the group's `permissions` as the caller last read them — sent together (**422** for one without the other), both normalized; the new list is compared with the stored one. **404**; **403** `permission_denied` when the caller does not hold every permission the group gives and every one the change ticks; **409** `admin_conflict` — `builtin` for the built-in group, whatever the body, `stale` when `based_on` is not the stored list (someone changed it since: nothing is written, and the caller reads the group again), `name_taken` |
| `DELETE /api/admin/groups/{id}` | `groups.write` + CSRF | **204**, its memberships gone. **404**; **403** `permission_denied` unless the caller holds every permission it gives; **409** `admin_conflict` (`builtin`) |
| `POST /api/admin/groups/{id}/members` | `groups.write` + CSRF | `{email}` or `{user_id}`, exactly one (**422** otherwise) → **201** `<member>`, or **200** `<member>` and no change when already in the group. **404** for an unknown group, or no account by that address or id; **403** `permission_denied` unless the caller holds every permission of the group, and for `{user_id}` without `users.read`; **409** `admin_conflict` (`email_ambiguous`) |
| `DELETE /api/admin/groups/{id}/members/{user_id}` | `groups.write` + CSRF | **204**. **404** for an unknown group or someone not in it; **403** `permission_denied` as for adding; **409** `admin_conflict` (`last_owner`) |
| `GET /api/admin/audit?page=&page_size=&area=&q=` | `audit.read` | a paged list of `<entry>`, newest first. `area` one of the six areas (**422** otherwise) keeps the rows whose action starts with `<area>.`; `q` keeps those whose actor's address or name, user target's address or group target's name contains it in any letter case, or whose `target_id` is exactly it. The search travels in the URL, so it also lands in the Caddy and uvicorn access logs of the server ([deployment.md](./deployment.md)) |
| `GET /api/admin/settings` | `settings.read` | `{settings: [<setting>], secrets: [{key, set}], ignored, cache_seconds, ceilings: {WORKSPACE_QUOTA_BYTES, MAX_JOBS_PER_USER}}` — the twelve in the order of § Settings; `secrets` the secrets of `.env` by name — `SECRET_KEY`, `GOOGLE_CLIENT_SECRET`, `KANO_PROXY_API_KEY`, `KANO_PAY_API_KEY`, `KANO_PAY_WEBHOOK_SECRET`, `SANDBOX_TOKEN`, `BRAVE_SEARCH_API_KEY`, `OPENALEX_API_KEY` — `set` whether each holds a value (for `SECRET_KEY`, whether it is other than the local fallback), never more; `ignored` null, or the checks' message while the database's values no longer fit `.env` (§ Settings); `cache_seconds` `RUNTIME_SETTINGS_CACHE_SECONDS`; `ceilings` `.env`'s two ceilings, for the page's hints |
| `PUT /api/admin/settings/{key}` | `settings.write` + CSRF | `{value, confirm?}` → the settings as `GET` answers them, with `key` stored as `value`. **422** for a key not among the twelve, a `value` past 65,536 characters, or settings that fail the start checks (§ Settings); **409** `admin_conflict` (`impact`) for a change that takes away what accounts have, sent without `confirm: true` |
| `DELETE /api/admin/settings/{key}` | `settings.write` + CSRF | *Restore to .env*: an optional body `{confirm?}` → the settings as `GET` answers them, `key` `.env`'s again; **422** and **409** as for `PUT` |

- `<group>` = `{id, name, builtin, permissions, stored_permissions, member_count, updated_at, updated_by: {id, name} | null}` — `permissions` the effective list (every one for the built-in group), `stored_permissions` the row's (`[]` there); `updated_at` when it was created or its name or permissions last changed, and `updated_by` who did it, read from the newest `groups.create` or `groups.update` record of it — null for the built-in group, which no one edits, and for an account since deleted.
- `<member>` = `{user_id, email, name, added_at, added_by: {id, name} | null}` — `added_by` the member themselves for a sign-in's owner join, null once the account that added them is deleted.
- `<account>` = `{id, email, name, plan: {id, source}, credits_available, storage_bytes, jobs, created_at}` — `plan.id` `free` or the plan's `planId`, `plan.source` what the current period is (`subscription`, `grant` or `free`), `storage_bytes` null when the workspace cannot be measured, `jobs` the jobs on record.
- `<account detail>` = `{user: {id, email, name, created_at}, plan: {id, source, start, end}, subscription: {status, plan_id, period_end, cancel_at_period_end} | null, credits: {available, sources: [{source, remaining, expires_at}]}, day_bank: {plan_id, days_banked, period_start, period_end} | null, storage: {bytes, quota_bytes} | null, jobs: {total, recent: [{id, filename, status, page_count, pages_done, created_at, finished_at}]}, groups: [{id, name, builtin}] | null}` — `sources` always the four, `period`, `pay`, `code`, `grant`, in that order, `expires_at` the period's end or a source's earliest expiry among its active packs that still hold credits, null when it holds none; `recent` the five newest jobs; `groups` null without `groups.read`.
- `<code>` = `{id, masked, kind, credits, valid_days, plan_id, days, uses, max_uses, redeem_by, label, status, created_at, disabled_at, disabled_by: {id, name} | null}` — `masked` the code as § Redeem codes shows it, never whole; the fields of the other kind null; `status` one of `active`, `disabled`, `expired`, `used_up`, `plan_missing`; `disabled_by` who disabled it, from its newest `codes.disable` record — null for a code not disabled, one disabled with the CLI, and once that account is deleted.
- `<job>` = `{id, created_at, started_at, finished_at, user_id, email, status, pages, pages_done, model, error, worker_generation, stuck}` — `email` the account's address for a caller who also holds `users.read`, else null; `pages` how many pages the job selected, null while the document's page count is unknown or when the selection does not fit it; `model` the retry's model when a retry named one, else the job's; `error` a failed job's `jobs.error`; `stuck` whether a requeue would take it (§ Overview, jobs and usage).
- `<worker>` = `{state, since, generation}` — `state` `running`, `stopped` or `unknown`; `since` the lock holder's connection start and `generation` the live generation, both null unless `running` (`generation` also before any worker took one).
- `<figures>` = `{calls, prompt_tokens, completion_tokens, cost, estimated_cost, estimated_calls, unpriced_calls, cache_read_tokens, cache_write_tokens}`, as [api.md](./api.md) § Usage aggregates defines them.
- `<entry>` = `{id, created_at, actor: {id, email, name} | null, permission, action, target_type, target_id, target_label, before, after, ip}` — `actor` null once that account is deleted; `target_label` what the page prints for the target, read now: a user target's address or a group target's name, null for any other target and for one since deleted (the page then prints the type and the id — a setting's id is its key).
- `<setting>` = `{key, value, source, env_value, updated_at, updated_by: {id, name} | null}` — `value` the text in effect for the key once the change is saved (the row's when `source` is `database`, `.env`'s when it is `env`), `env_value` `.env`'s text, the same as `value` when `source` is `env`; `updated_at` and `updated_by` the row's, null for a key `.env` holds and `updated_by` null once that account is deleted. A setting's text is what `.env` would hold: a number as written, a model id, a JSON table as the operator typed it.
- `impact` (in a **409** `impact`'s `error`, beside `reason`) = `{removed: {models, plans, packs}, counts}` — what the change removes, by id, and of the counts of § Settings, *Confirmed when it takes away*, those above 0 by name.
- Within a route the checks run in this order, after § Signing in's: the body and query (**422**), what the path names (**404**), the escalation rules (**403**), then the rest — an address that resolves to no account or to several, and the group rules (**409**).

## Refusals

| Situation | Answer |
|---|---|
| the console off: `OWNER_EMAILS` names no address | **404** `invalid_request` on every `/api/admin` path, as for any path that does not exist |
| an `Authorization` header; no session cookie, or an unknown or expired session | **401** `auth` |
| a mutation without `X-Requested-With` | **403** `auth` |
| the route's permission missing; a group change that would hand out a permission the caller does not hold, or touch a group whose permissions are not all the caller's; a member added by account id without `users.read` (§ Permissions, *No escalation*) | **403** `permission_denied` |
| the session older than `ADMIN_REAUTH_HOURS` | **403** `reauth_required` |
| an unknown group; a member who is not in the group; no account by that address or id; no account by the id a users route names; no job by that id | **404** `invalid_request` |
| a group rule — the name is taken (`name_taken`); the built-in group renamed, given other permissions or deleted (`builtin`); its last member removed (`last_owner`); an address several accounts share (`email_ambiguous`); a permission list edited from one that is no longer stored (`stale`); days of another plan than the account's bank holds (`plan_conflict`); a credit grant's `request_id` that another account's pack has (`request_reused`); a requeue of a job that is not running (`not_running`), while the worker's state cannot be read (`worker_unknown`), or of a job the live worker drives (`not_stuck`); a settings change that takes away what accounts have, sent without `confirm: true` (`impact`, with `impact` beside it) | **409** `admin_conflict`, with `reason` beside `message` in `error` |
| a malformed body or query — a name outside the rule, an unknown permission, `permissions` without `based_on` or the reverse, both or neither of `email` and `user_id`, a page or page size under 1, a page above 2,147,483,647, an unknown area; a plan filter or a day grant's plan that is not configured, a grant's unknown `kind`, a number outside its range, a `request_id` that is not a UUID, a `reason` past 200 characters, an account id in a users route's path outside 1 to 2,147,483,647; a job status other than the four, a job id that is not a UUID; a usage range with `from` or `to` missing or not a date, `from` after `to`, or longer than `ADMIN_USAGE_MAX_DAYS` days; a setting key not among the twelve, a setting's value past 65,536 characters, a settings change the start checks refuse (in their words, never the settings') | **422** `invalid_request` |
| a redeem code that does not exist, to disable — an id above 2,147,483,647 among them | **404** `invalid_request` |
| a batch of redeem codes `create_codes` refuses — an unknown kind; a count, a use or an amount missing, under 1 or above 2,147,483,647; days above 36,500; a plan not in `KANO_PAY_PLANS_JSON`; a label over 255 characters; a redeem-by date already past; more codes than `REDEEM_CODES_MAX_COUNT` — or a `status` other than `active` and `all` (§ Redeem codes) | **422** `invalid_request` |

`admin_conflict` is one type for every conflict of the console; `reason` says which, so a page can say it in the reader's language and fall back to `message` for a reason it does not know. A page added later adds its own reasons.

## Pages

The screens follow the app's design system and its one layout ([web.md](./web.md) § Design system — light glass); every word is in the i18n catalog, en and zh-TW together; a group's name, an address, a permission string and an IP are data and print as they are.

- **One shell.** Under `/admin` the sidebar keeps its brand and its account button at the foot — the account menu, the settings dialog and the language dialog work as they do on Files — and its nav changes: a line *Admin console* (管理後台) with *Back to Files* (回到檔案) to `/files`, then one entry per console page the account can read, each with its own glyph. In nav order: *Overview* (總覽, `layout-grid`), *Users* (使用者, `users.read`), *Redeem codes* (兌換碼, `codes.read`), *Jobs* (工作, `list-checks`) and *Usage* (用量, the `dashboard` glyph Settings' Usage has), the Overview, Jobs and Usage all `jobs.read`, then *Groups* (群組, `groups.read`), *Audit* (稽核, `audit.read`) and *Settings* (設定, `settings.read`), the last — the order fixed in `app/lib/admin.ts`.
- **The way in** is the account menu's *Admin console* item ([web.md](./web.md) § The account menu), shown while `GET /api/me` answers `console: true`, opening `/admin`.
- **`/admin`** is the *Overview* for an account that holds `jobs.read`, and replaces itself with the first console page, in nav order, that any other account can read.
- **Every console page runs two route middlewares**, `authed` and then `admin`. `admin` loads `GET /api/admin/me` once (`useAdminConsole`, in memory only, cleared on sign-out and when the signed-in account changes). A 404 there shows Nuxt's Not Found page — the `/admin` HTML is a client-rendered shell the server answers 200 for, so the API's 404 is what enforces it — and so does an account that can read no console page: one in no group, or only in groups that grant no `.read`. A page whose area the account cannot read is replaced by the first one it can.
- **Signing in again.** While `reauth_required` is true — on loading, or after a 403 `reauth_required` from any route while a page is open — the page shows one full-panel state in place of its content and reads nothing more: the title *Sign in again to use the console* (重新登入才能使用管理後台), one line saying the console asks for it `reauth_hours` hours after a sign-in, and a primary *Sign in again* (重新登入). The button keeps the console path it is on for after the sign-in (`keepAfterSignIn`, the return path the sign-in page takes once, held in `sessionStorage` until then) without its search (`q`), which may be someone's address; it signs out (`POST /api/auth/logout`, so the old session row goes instead of lingering for its 30 days) and opens `/api/auth/login?locale=<locale>`; where the dev sign-in exists — the probe the sign-in page already makes — it signs in through it instead and goes back to the kept path.
- **Errors.** A 401 is handled as everywhere: the session is cleared and the sign-in page opens. A 403 `permission_denied` reloads `GET /api/admin/me`, so the nav and the buttons follow what the account holds now, and shows its message where the action was taken. A 409 says its `reason` in the catalog's words. A 404 from a change to a group reads the groups again: when the group is gone — another operator deleted it — the page selects what is left and says *This group no longer exists*; when it is still there, a 404 for an address says the person must sign in to Ema Paper once first, and one for removing a member who has already left closes the dialog as done. Any other failure of `GET /api/admin/me` — offline, the API restarting — opens the page on *Couldn't open the admin console* with *Retry* in its place, at the same path. The groups or a group's members failing to load say so where they would be, with *Retry*; the audit log's failure is said above its table, under the toolbar's *Refresh*. A refusal inside a dialog stays in the dialog, and a dialog with a request in flight cannot be dismissed — the rules of the account-deletion dialog ([web.md](./web.md) § Deleting the account).
- **Nothing is cached.** Console data is never written to `localStorage` or `sessionStorage`: it names other people. The one thing kept there is the path *Sign in again* returns to, without its search. A page keeps its filter, its search, its page, its selected group and its date range in the route query, so Back and a reload return to them.
- **Overview** (`/admin`, `jobs.read`). The toolbar holds *Refresh*; the large title *Overview* with *{date} (UTC) · {n} accounts · updated {time}* beside it — the UTC day the figures count, the accounts, and when the page last read them. ## Configuration

| Var | Meaning |
|---|---|
| `OWNER_EMAILS` | the Google addresses that join the owner group when they sign in with the address verified (§ Groups), comma-separated, each trimmed and lower-cased, empty items ignored. Empty (`""`, the default) = no console (§ Off until configured). Removing an address removes no one |
| `ADMIN_REAUTH_HOURS` | how old a session may be, from its sign-in, for the console (12); above 0, or the API and the worker refuse to start |
| `ADMIN_PAGE_SIZE` | the rows one page of a console list holds, and the most `page_size` may ask for (50); 1–500, or the API and the worker refuse to start |
| `ADMIN_GRANT_VALID_DAYS` | how many days a credit grant is valid when the dialog changes nothing (365, as long as a top-up pack lasts); 1 to `ADMIN_GRANT_MAX_DAYS`, or the API and the worker refuse to start (§ Users and grants) |
| `RUNTIME_SETTINGS_CACHE_SECONDS` | how long the API and the worker keep the settings the database overrides before reading its rows again (30); above 0, or the API and the worker refuse to start (§ Settings) |
| `ADMIN_GRANT_MAX_CREDITS`, `ADMIN_GRANT_MAX_DAYS` | the most one grant may give: credits (1000000; 1 to 2,147,483,647, the most a pack's `credits` column holds) and days — of a plan, or of a credit grant's validity (3650; 1 to 36,500, a century, so a date it reaches stays one PostgreSQL and Python can hold); a sanity cap against a slip of the keyboard, not a budget |
| `ADMIN_PROBE_TIMEOUT_SECONDS` | how long an overview read waits for each of the two catalogs, Kano Proxy's and Kano Pay's, which it asks at the same time — so about the longest a slow upstream adds to the page (5); above 0, or the API and the worker refuse to start (§ Overview, jobs and usage) |
| `ADMIN_USAGE_MAX_DAYS` | the most days one usage read may span, `from` to `to` included (366: a year, a leap day included); at least 90 — the Usage page's longest range, so none of its segments is refused — or the API and the worker refuse to start |
| `ADMIN_FAILED_WINDOW_HOURS` | how many hours back the overview counts failed jobs, its *Failed in the last {n} hours* tile (24); 1–8760, a year — a far larger value would put the window's start before the first date the API can count from and fail every overview read — or the API and the worker refuse to start |

`OWNER_EMAILS` and the `ADMIN_*` settings are used by the API alone, `RUNTIME_SETTINGS_CACHE_SECONDS` by the API, the worker and the CLI, but all are checked with every other setting wherever the settings load: a value out of range stops the worker (and `python -m sightread.codes`) too, not just the API. A changed `.env` reaches the api container only when the container is recreated: `docker compose -f docker-compose.production.yaml up -d --no-deps api` (with the overlay's `-f` on a host behind a front proxy); `docker compose restart` keeps the environment the container was created with ([deployment.md](./deployment.md) § Release flow). The production compose file also sets `FORWARDED_ALLOW_IPS: "*"` on `api` for the audit log's addresses (§ The audit log).
