# Web (Nuxt control plane)

The web app configures, issues and observes — and on `/files` it is also where a person parses a document by hand, without a terminal. That is one addition to what it does, not two: it still runs no parsing and implements no upload endpoint. The browser posts the file straight to FastAPI's control plane and the same `jobs.intake` sequence `/v1/parse` runs takes it from there ([api.md](./api.md) § Why the web upload is a control-plane route). What the Nuxt server never handles is a document. It also *renders* a finished result, because reading what came back is observation, not a second data plane.

## Stack

Nuxt (latest stable) + TypeScript + `@nuxtjs/i18n` (en, zh-TW; en is the source catalog), pnpm. No UI framework and no CSS framework — hand-rolled primitives over the design tokens in `app/assets/css/main.css`, styled in each SFC's own scoped block. There is no Tailwind, no utility layer, and no second component library.

## Design system — Graphite

An editorial system, not a card dashboard: serif headings, hairline rules instead of card borders, cool-gray paper, and a single steel-blue accent.

- **Tokens** in `app/assets/css/main.css`, as plain custom properties on `:root` — this app's one convention. The color ramp is paper / paper-sunken / rail / rail-active / desk for surfaces, ink / ink-soft / muted / faint for text, line / line-soft / line-strong / hair / edge for rules, and one `--accent`. Spacing, radius, type, control heights and the table rhythm are tokens too: a raw hex, a raw `padding: 13px` or a raw `font-size: 15px` inside a component is the same class of bug. Every color is declared in both `:root` theme blocks and nothing outside them names a color; the light values are the design's, the dark block is a derived inversion of the same ramp.
- **Accent discipline is the core rule.** Steel blue appears only on data and the controls that commit it: cost figures, usage meters, the brand mark, primary buttons, the succeeded status dot, active page markers in the result viewer, the active locale's underline, focus rings, and the context menu's highlighted row. Never on headings, borders, backgrounds or decoration.
- **Type**: `Source Serif 4` (Google Fonts, `opsz 8..60`, fallback Georgia) for page titles, panel headings, metrics and the result viewer's headings; the system sans stack — `Noto Sans TC` included, the app is bilingual — for UI and body; `ui-monospace` for model ids, key prefixes, URLs, bboxes and code. Every figure carries `font-variant-numeric: tabular-nums`.
- **Geometry**: 3px radius on controls, 0 on panels and dialogs. 1px borders. Two shadows: `--shadow-dialog` on dialogs and the mobile drawer, and `--shadow-menu` on the context menu. The menu is the design's one deliberate exception to flat square paper — see below.
- **Two scroll axes on every screen.** One layout, `default`: a non-scrolling `100dvh` grid of a 236px sidebar and a content region. The content region is itself a grid of a `clamp(200px, 20vw, 320px)` left rail — eyebrow, serif title, then either headline figures or the screen's primary action, scrolling on its own — and a right data region, which is either one full-height scrolling panel or a split of two independently scrolling ones (the lower takes `--paper-sunken`, and the two are divided by a 1px rule, not a gap). Nothing puts a whole screen on one scrollbar. `UiScreen full` drops the rail track entirely for a screen with no margin to write in — `/files`, and `/agents` while Kano Proxy is not connected (a screen with one control has nothing to write beside it): a page that simply omits its rail would still leave the column standing empty. `min-width: 0` on the grid tracks and the flex panels is load-bearing: without it a table forces the region wider than the viewport instead of scrolling inside its panel.
- Below 900px the rail collapses above the data region and the sidebar goes behind a focus-trapped drawer. The sign-in page is full-bleed and owns its own frame (`layout: false`), sharing tokens only.
- **Primitives** in `app/components/ui/`: `Panel` (header + independently scrolling body, no border/radius/shadow, optional `sunken`), `PageHeader` (the rail's eyebrow + serif title block), `DataTable` (the only table markup — `min-width` + nowrap so it scrolls in place, sticky header on an inset rule, per-column alignment, no border on the last row), `Modal` (square, and able to host a grid-bodied dialog as well as a form; `size="full"` fills the viewport, which only the result viewer asks for), `Button` (accent / secondary / ghost / danger, `icon-only`, three sizes), `TextInput`, `Select`, `Field` (label-less with an `aria-label` where the design has no visible label), `CopyField`, `CopyButton`, `UsageBar` (a 3px square accent meter), `StatusDot`, `EmptyState`, `Banner`, `Skeleton`, `Spinner`, `ConfirmDialog`, `ContextMenu` (a floating list of items opened at a point — teleported to `<body>`, positioned by the pure `app/lib/menu.ts` so it flips at a viewport edge instead of being clipped, arrow-key navigable, dismissed by Escape, a click outside, or a scroll. **Nothing is highlighted when it opens**: focus lands on the menu itself, not on its first item, because the highlight is the pointer's — a menu that opens with a row lit is claiming the pointer is on that row, and the lit row stays lit for as long as the menu is up. `focusFirst` is the exception, set when the menu was opened from the keyboard, where the highlight is the cursor. An item is a button, or a real link when it carries `to`, and one of a set of choices carries `checked`; an optional `header` names what the menu is about). Three callers: the library's right-click, History's right-click (§ History), and the sidebar's account row (§ The account menu). `Icon`. There is no `Card` and no `Badge`: the design has no cards, and a count is panel-header meta text. The library adds no primitive: its parse meter is `UsageBar` (a meter is a meter), and the two things it does need — `FolderTree` (the flattened, expandable tree the folder picker is made of — its only caller) and `MoveDialog` (the folder picker: Move on `/files`, Add to Files on `/history`) — are page components in `app/components/`, beside `ResultViewer`, because only the library's two doors have a tree to draw.
- **`ContextMenu` is the one surface built like the platform's rather than like this app's.** Everything else here is flat square paper; a menu that shared that geometry reads as pasted into the page instead of floating over it. So: `--radius-menu` corners, a near-opaque `--menu-surface` (98% — enough for the blurred edge of the page to read as depth, never enough for text to shimmer through text) under a `backdrop-filter` blur (fully opaque where blur is unsupported), a hairline `--menu-edge`, the two-part `--shadow-menu` (a tight contact shadow for the edge, a wide soft one for the height), items inset inside the padding with their own `--radius-menu-item`, and a 120ms scale-in from whichever corner the pointer opened it at — restarted by hand when a second right-click reuses the same element, and off under `prefers-reduced-motion`. The highlighted row is filled with the accent, the only place the accent covers a surface: it is the action about to be committed, which is what the accent is for. A destructive row fills with `--danger` instead.
- **Icons** are Lucide paths on a 24 grid at stroke 1.75, inlined in `Icon.vue` — never a package, never a remote sprite, never inline SVG at a call site. Icon-only controls carry `label` (= aria-label + tooltip); a destructive action either keeps its visible word or, when icon-only, is backed by a `ConfirmDialog` whose title and message carry it.
- **Motion**: 120–160ms on color and background only. No hover elevation anywhere — hover is a text-color shift to the accent on links and a background shift on nav and list rows.
- Icons ship as three files in `public/`: `favicon.svg` (the source mark — the `scan-text` glyph reversed out of an accent rounded square), `favicon.ico` (16/32/48, generated from it) and `apple-touch-icon.png` (180). All three are declared in `nuxt.config.ts`, and the FastAPI consent page declares them too. The `.ico` is not redundant: clients that do not take SVG — connector webviews among them — request `/favicon.ico`, and when that answers a blank placeholder they fall back to whatever icon they already hold for the parent domain.

## The account menu

The sidebar's foot is one button — the avatar (the Google `picture` when one is stored, the identity's first letter otherwise), the name, and a caret — opening `UiContextMenu`, the same floating surface the library's right-click opens. Nothing else in the sidebar is a control.

- **What it holds, and nothing more:** the signed-in address as a header line (a fact, not an item), **Agent**, **Language**, and **Sign out** under a rule. No help, no upgrade, no product tour — this app has none of those, and a menu padded out with rows that lead nowhere is worse than a short one.
- **Language is one row opening a dialog** (`LanguageDialog`), not locales listed inline and not a submenu — a submenu is a second floating surface to position and dismiss, and the choice deserves room to be read. The dialog is a grid of options that reflows to the width it is given; each is a real link (`switchLocalePath`, so you stay on the page you were reading) saying its language in *that* language over the same name in the one you are reading now — the first line for whoever is looking for their own language, the second for whoever cannot read the first. The current one carries the accent check on the selected-row surface the nav already uses.
- **Sign-out moved inside.** It used to be an icon beside the row, which made the foot two controls and put the session's most destructive action one stray click from the name. It is now the last item, below the rule, where a desktop app puts it.
- **Pressing the row while the menu is open closes it.** The menu dismisses on a press anywhere outside itself, which lands before the row's own `click` — so the row ignores a click that arrives within 200ms of a dismissal, or it would reopen what the press just closed.

## Files — the library

A file manager over parse results: folders that nest like directories, and one file per result (`documents` + `folders`, [database.md](./database.md)). A document is a name, a place in the tree and a pointer at the job that produced it — never a second copy of the markdown.

- **One read, then local navigation.** `GET /api/library` returns every folder and every document for the account at once, and opening a folder is a computed filter, not a request. A library is small (rows, not documents — the bytes are long gone), and a per-folder fetch would put a spinner between a click and a list that was already in memory.
- **One pane, no sidebar.** The screen is the folder you are in and nothing else: no rail, no persistent tree beside the list. You go down by opening a folder row and back up through the breadcrumb in the panel header, which is also a drop target per level — the same two moves a single-pane file manager gives you. The tree still exists where a tree is the point: inside the move dialog, as the picker. Losing the sidebar costs the at-a-glance shape of the whole library and the drag straight into a folder three levels down; what it buys is a screen with one thing on it.
- **Every action is in one menu.** This screen has no action buttons at all — no Upload, no New folder, no per-row rename/move/delete icons. Uploading, making a folder, renaming, moving and deleting are opened the way a desktop file manager opens them: right-click (or long-press on touch) on a row, or on the empty space of the list. A row's menu acts on that row (Open · Rename, Move · Delete); the list's own menu acts on the folder that is open (Upload, New folder). Refresh is not in either: the list re-reads itself while anything is parsing, and the panel header keeps its refresh control for the rest. Left-click keeps meaning what it meant — a folder opens, a document's name opens the result viewer — so the menu adds a surface rather than replacing one. **The cost is stated rather than designed away:** an account with an empty library sees a screen with nothing to click, and the first upload has to be discovered through the menu or through drag-and-drop. That is the trade this screen accepts to have one interaction instead of three.
- **A menu is not mouse-only.** A right-click is one of three routes into the same menu, and the other two are why it can be the only action surface: a long press on touch (500 ms, cancelled by a 10px drag, and it eats the click that would otherwise open the row), and `Shift+F10` or the Menu key on whatever is focused — a row's name button, or the list itself, which takes a tab stop for exactly this reason. Inside it, arrows and Home/End move, Enter selects, Escape closes and focus returns to what opened it.
- **Uploading is a client-side queue, because the server has a real limit.** `MAX_JOBS_PER_USER` (2) is a cap on *running* jobs, so posting five files at once earns three 429s. The page treats a 429 as back-pressure rather than an error: files upload one at a time, a refused one waits and retries, and every file is a row from the moment it is dropped — its own local row until the server answers with a document id. A request that never reached the server at all is treated the same way, because a dropped connection halfway through a large upload is the case where making someone find the file again hurts most. Nothing is silently dropped and nothing needs re-picking. A file is refused before it is sent only when the server would refuse it too — the same media-type-then-extension judgement intake makes, from the two lists `GET /api/me` returns. Retrying costs nothing twice: the same bytes, still parsing, answer with the job already running rather than a second one ([jobs.md](./jobs.md) § Dedup), which is also what makes uploading one document into two folders one parse and two files.
- **Progress is polled, not streamed.** While any document is `queued` or `running`, the page re-reads `GET /api/library` every 2 s and stops when none are. One request refreshes every row's status and `pages_done`; the alternative is one SSE connection per running document for a number that changes a handful of times per job.
- **Reading it is the point.** A document's name opens the result viewer below, including while the parse is still running: the dialog shows the document as pending and fills in the moment the poll says a result exists, rather than caching the 404 it would get for asking early. A *single* upload that finishes while its folder is still open opens itself, because "upload it and read it" is the whole flow; a batch does not — five dialogs racing each other is not a feature.
- **Moving.** Drag a row onto a folder row in the list, or onto a breadcrumb — the latter is how a file goes back up a level. Those are the two targets a single-pane screen can offer, and they only reach one level down or any level up; anything further is the menu's Move, which is the picker and knows the whole tree. The live drop target is the one place in the app where the accent touches a border, and it is deliberate: it exists only while a drag is in the air, and a drop target you have to squint at is a file in the wrong folder. Drag-and-drop is invisible to a keyboard and to assistive tech, so it is never the only route: the row's menu has Move, which opens a picker over the same tree.
- **The picker can make the folder it needs.** Its footer carries *New folder* on the left, away from the confirm button. It opens a name field under the tree, prefilled and selected, which creates the folder **inside the folder currently selected** — the field's label says which — and then selects the new one, so a move or an add into a folder that does not exist yet is one dialog rather than a trip back to the list. Enter creates, Escape closes the field without closing the dialog, and a failure shows in the dialog's own banner. Creating is refused for a destination the item could not be moved into anyway (a folder's own subtree). The new folder is real the moment it is created: cancelling the move afterwards leaves it in place, as a desktop save dialog's New Folder does. A folder refuses to move into its own subtree, in the client and again on the server.
- **`dragover` decides everything** (`app/lib/dnd.ts`). It fires continuously on exactly one innermost element and bubbles to the window, so the handler nearest the pointer *claims* the event and the window clears whatever went unclaimed — which is also what un-highlights a target that has been left. `dragleave` is used nowhere on this screen: it fires for every child element a pointer crosses and bubbles like everything else, so a row built from an icon and a name reports "left" halfway across itself, and browsers disagree about what `relatedTarget` holds on a drag. Three consequences worth knowing: the window swallows a file dropped outside every target, because the browser's default there is to navigate to the file and take the page — and the upload queue in it — with it; the window carries `dragend` too, since a row can be replaced by a poll mid-drag and its own never arrives; and the flags a *file* drag sets expire on a timer, because a drag from the desktop can be carried out of the window without leaving this page a single event it can trust.
- **Names behave like a file system's.** Unique within their folder — folders and files in one namespace, so a folder cannot be called what a file beside it is called — and a collision is resolved rather than rejected: the server appends ` (2)` on upload, on a new folder and on move. A rename that would collide is the one case that answers 409, because there the name is the thing the user just typed and silently changing it would be a lie.
- **A drop lands where the page said it would.** While files are being dragged, the overlay names the open folder, so a folder row or a breadcrumb under the pointer does not quietly take them somewhere else — it lets the drop through to the list. Rows of the library itself are the opposite: they are exactly what a folder row accepts.
- **A dialog with a request in flight cannot be dismissed.** Its controls are already disabled while one runs; `UiModal`'s `busy` closes the two routes around them, Escape and the scrim. Closing would not stop the request — a delete would land after the reader thought they had backed out of it.
- **A dialog reports its own failure.** A rename that collides, a move that races, a delete that fails: the dialog stays open, so the message belongs inside it. A banner on the page behind the overlay reads as the button having done nothing at all.
- **A file can be linked to.** `/files?document=<id>` opens the folder that holds the document and lights its row for a moment, scrolled into view — how History's *Show in Files* lands. The query is consumed on arrival (replaced away), so a refresh or a later visit opens at the top level as usual. An id that is not in the library, deleted in another tab, opens the top level and nothing else.
- **No instructions anywhere on this screen.** The drop target, the empty folder and the menu items say what they are — a screen that needs a sentence explaining how to use it is a screen that has not been designed yet. The empty state is a state, not a tutorial: it says the folder is empty and stops there, exactly as it did when there was a button under it.

## History — filing a parse

History lists every parse, and most of them never entered through the library — an API call or a connector parse has a result but no file. The row's context menu is how one becomes a file, without uploading the same bytes again.

- **Same menu, same routes in.** Right-click, a 500 ms long press on touch, or `Shift+F10` / the Menu key on a row's filename — exactly the library's three routes, so nothing new to learn between the two screens. The panel has no list menu: History has nothing to create.
- **What it holds:** **Open** (the result viewer, the same as clicking the name), **Add to Files…**, and **Show in Files** when the parse is already in the library. Add stays available on a parse that is already filed — one parse in two folders is a legitimate library, the same as uploading one file twice — so the marker below is what prevents an accidental duplicate, not a disabled row.
- **A failed parse cannot be filed.** It has no result, and a file that opens to an error is a dead entry in someone's library. The row is shown disabled rather than hidden, so the menu has the same shape on every row. A queued or running parse can be filed: the library already tracks progress and the viewer already reads partials.
- **Add to Files is the move picker.** `MoveDialog` with its title and button saying *Add to Files* / *Add*, over the same tree. It opens on the folder last chosen in this page load, because filing a batch of API parses is usually filing them into one place, and on the top level otherwise. Any folder is a valid destination, the top level included, and the picker's *New folder* (§ Files) makes one on the spot. The name is the job's filename, with the library's ` (2)` rule on a collision. Failure stays inside the dialog, as on Files.
- **A filed parse says so.** A faint folder glyph after the filename marks a row that has at least one file, titled with the folder it lives in. It is the answer to "did I already file this?", and it is what appears when Add succeeds — the dialog closes and the mark is the confirmation, with *Show in Files* now in the menu. Color is not involved: the glyph is `--faint`, because it is a fact about the row, not data.
- **The library is read alongside the jobs.** `GET /api/library` is fetched with `GET /api/jobs` and joined on `job_id` in the client; it is the same small read the Files screen makes, and it gives the picker its tree without a request between the menu and the dialog. A library that fails to load leaves History fully usable: the marks are missing and Add / Show in Files are disabled, rather than the page failing for a feature most rows never use.
- **Show in Files** goes to `/files?document=<id>` (§ Files). A parse filed more than once goes to the most recently added file.

## Result viewer

Opened from a document on `/files` (`GET /api/library/documents/{id}/result`) or a filename on `/history` (`GET /api/jobs/{id}/result`) — one component, two callers, because a parsed document reads the same however it was started. **A full-screen dialog** (`UiModal size="full"`): every other dialog in the app is a box over the page you were on, but this one is not an interruption to a screen — it is the thing you came to read, and a 1040px box in the middle of a 27" display makes a document look like a receipt. Its header carries the filename, the `model · N pages · bbox format` line, and a Markdown / JSON toggle.

- **It reads as a document, not as UI.** The prose is set on its own two sizes (`--text-read` / `--text-read-sm`) rather than the dense UI scale the rest of the app uses, because this is the one surface that is read continuously instead of scanned. The column is **70% of the pane, centered** — on a very wide display that is wider than a typographer would set prose, and it is the width the reader asked for.

- **Markdown** is the default tab: one continuous scroll of the whole document. **The document itself never carries page labels** — a reader checking a transcription reads it as a document, not as a stack of pages — but the page grouping is real (a figure's crop is addressed by the page it came from) and it is offered as **an optional rail**: the header's panel toggle opens a column of page buttons, each with its figure count, which scrolls the document and tracks it back. The rail starts closed and the choice is remembered for as long as the page is loaded, so it is opened once and stays open across every document you then open. Navigation is a thing you ask for; a page number printed through the prose is a thing you cannot decline.
- **The rail and the find bar float over the document; they never reflow it.** Both are absolutely positioned inside the pane, so opening either leaves every line of text exactly where it was — a reader who opens a search to find the paragraph they are looking at must not have that paragraph move first. The centered column is what gives the rail its room: at 70% there is a margin on the left for it to sit in. `app/lib/markdown.ts` turns the result's markdown into ordered blocks per page: the `<!-- page: N -->` markers split pages, and within a page `##`/`###` headings, GFM tables in either form (the outer pipes are optional, so the separator row is what identifies one), `-`/`1.` lists including wrapped items and the number they start at, `$$` display-math (fenced on its own lines, or with the dollars sharing a line with the formula — `$$x = 1 \tag{1.6}$$` is how most models write a numbered equation) and fenced code blocks (whose line breaks and indentation are their content), table-of-contents runs (below), `![fig](sightread://p…)` placeholders with the caption on the next line, and paragraphs each become a block. Parsing is client-side because the API returns the document as one markdown string (docs/parsing.md § Page markers).
- **Math renders through KaTeX.** Prose, headings, list items, table cells and captions are split on `$…$` spans (`parseInline` in `app/lib/markdown.ts` — a span opens on `$` + non-space, closes on non-space + `$`, and never ends before a digit, so "$5 and $6" stays prices. **The closer is the first `$` at brace depth zero**, not simply the first one: TeX nests math inside text, so `$\text{\sout{$E'_v$}}$` is one formula — closing on the first dollar cut it in half and handed KaTeX an unbalanced fragment, which fell back to source and left the whole line reading as raw TeX. An escaped `\$` opens nothing), and each span is typeset by KaTeX (`app/lib/math.ts` — rendered with `throwOnError` **on** and the exception caught, so a failure falls back to the whole formula's source rather than KaTeX's inline red error text; the CSS and its bundled fonts ship with the app, nothing remote). Display `$$` blocks are typeset the same way in display mode; a block KaTeX cannot parse at all falls back to the verbatim `<pre>` it always was, because wrong glyphs are worse than visible TeX. **Repairs are tried before that fallback, and only for a formula that already failed** — source KaTeX accepts is never rewritten. Three slips account for nearly every formula it rejects in a transcribed book, each with one unambiguous reading (`app/lib/math.ts`): a block that is a single `aligned` environment with `\tag` on its rows — a numbered derivation, which TeX's one-tag-per-display rule rejects — is re-typeset as `align`, the same layout with a number per row, and rows the page left unnumbered get `\notag` so `align` does not invent numbers for them; a command with arguments used as a bare script (`V^\boldsymbol{\pi}`) gets the braces that were meant; and an equation printed across two lines and transcribed as two blocks, whose `\left\{` opens in one and `\right\}` closes in the next, gets TeX's own null delimiters (`\right.` / `\left.`) so each half compiles. The rendered inline span carries its original TeX in `data-tex` and a display block carries its `$$…$$` source in `data-md` — what copy-as-markdown reads back. A display block scrolls **sideways only**: a tall formula — a `\begin{cases}`, a stacked fraction — expands the block to its full height instead of being handed a vertical scrollbar, because a formula is one object and half of it behind a scroll gesture is not a formula anyone can read.
- **A table of contents keeps its lines.** Markdown joins consecutive lines into one paragraph, which is right for wrapped prose and wrong for a contents page: a book's `1.1 Sequential decision making . . . . . 13` lines arrive one per line with no blank line between them, and joined they read as one run-on paragraph of dots. A run of lines in which any line ends in a dot leader and a page number (`. . . . 13`, `.....iv`) is therefore a `toc` block: one row per line, the title on the left, the page number on the right, and the leader drawn by CSS instead of printed as characters — so it fills whatever width the column has rather than wrapping. A line of such a run without a leader (`**1 Introduction** **13**`, a chapter row) still splits off a trailing page number; one without any number is a title-only row. Copy hands each row back as its source line, leader characters included (the leader element carries them in `data-src`), rows joined by single newlines as the model wrote them. Find-in-document sees titles and page numbers, not dots.
- **Inline markdown renders as text, not source.** Within the same inline pass, `**strong**`, `*em*` / `_em_` (underscores only at word boundaries, so `usage_log` stays text), `` `code` `` spans and `<br>` line breaks become real elements — table cells like `**96.5**` and `UniVLA<br>(Ours)` read as the table meant them to. Nesting parses (`_**Abstract**_`), each rendered element carries its exact source in `data-src` for copy, and emphasis that straddles a math span keeps its source characters. **Backslash escapes are consumed, not printed**: a transcription of a reference list arrives full of `\[87]`, and GFM says that is `[87]` — a backslash before ASCII punctuation makes the character literal and disappears itself, while a backslash before anything else (`C:\path`) is an ordinary one and stays. This is the one shape whose copy is not character-exact: an escape leaves no element to hang `data-src` on, so `\[87]` copies back as `[87]`, which re-renders identically.
- **A wide table scrolls by itself.** The prose column is a fixed fraction of the pane, so a table with more columns than that gets its own horizontal scrollbar (an `overflow-x` wrapper per table) instead of stretching the page or crushing its cells.
- **Ctrl+F finds in the document.** The header's magnifier opens a find bar over the document (Ctrl/Cmd+F does the same while the viewer has focus, and the browser's own find is suppressed only there — the viewer is a scroll region inside a dialog, and the native bar cannot reach into it usefully). Enter and Shift+Enter step through the hits, the counter reads `n / total`, Escape closes the bar without closing the dialog.
  Matches are painted with the **CSS Custom Highlight API**, not by wrapping hits in `<mark>`: the rendered document is never rewritten, so the `data-src` / `data-tex` sources copy-as-markdown reads back cannot be cut in half by a search. Every hit takes the accent as a wash and the current one takes it solid (`--find`, `--find-current`). A browser without the API still steps and scrolls through the hits, just without the paint.
  Two things it deliberately does not search: KaTeX subtrees (a typeset formula is a tree of per-glyph spans plus a hidden MathML twin — searching it yields fragments and doubled hits) and the JSON tab (the browser's own find is the right tool on a `<pre>`, and Ctrl+F is left alone there). A match may span elements — a phrase running through a bold word is one hit — because the search runs over the document's text with an offset map back into its nodes, not node by node.
- **Ctrl+C copies markdown.** A `copy` listener on the document pane serializes the selection back to markdown (`app/lib/copy.ts`): pipe tables from the selected rows and cells, headings at their source depth (the viewer draws two sizes but `data-level` keeps the original `#…` count), list markers, `$$`/fenced blocks verbatim, figure placeholders with their caption, inline math from `data-tex`, display math from its block's `data-md` (always the fenced form, whichever form the source used — it re-renders identically), and rendered emphasis/code/`<br>` from `data-src`. A selection inside one paragraph copies as the plain text it looks like; a selection inside a code or display-math block copies verbatim, line breaks and indentation kept; anything structural copies as source a markdown editor will re-render. The serializer walks the cloned selection fragment, so a partial table selection yields a valid partial table.
- **A running parse reads page by page.** The control plane answers with a partial result while a job runs (docs/api.md § Partial results), and `/files` re-fetches it on the same 2 s poll that tracks the row's progress — so opening a parsing document shows the pages that exist, a progress note in the header (`pages_done / page_count`), and a skeleton where the next page will land, rather than one spinner until the whole document is done. When the poll says the job finished, the final result replaces the partial one and nothing partial is ever cached.
- A job whose pages partly failed still finishes as `succeeded` and simply omits them, so the markdown view leads with a banner naming the missing pages when `result.errors` is non-empty. A degraded document must not read as a complete one.
- **Known limitation**: the parser is flat. A nested list renders as one level — the items survive, the hierarchy does not — and a code fence is closed by any fence rather than a matching one, so a `~~~` block containing a literal ``` line ends early. These are deliberate: this reads a known set of block shapes rather than implementing GFM, and every shape added so far has revealed the next one it does not know. Rendering the result through a real GFM parser is the alternative, and it is a dependency and sanitisation decision of its own rather than something to bolt on here (KaTeX for math is the one such decision already made).
- **Figures render as the stored crop, centered in the column** with the caption under them — a crop is narrower than the measure far more often than not, and left-aligning it hangs it off an edge the text does not share. The pipeline persists each figure's crop (docs/parsing.md § Figure crops) and the viewer loads it from the caller's own figure route — `/api/library/documents/{id}/figures/{page}/{bbox}` on Files, `/api/jobs/{id}/figures/{page}/{bbox}` on History — addressed by the page and bbox the placeholder already carries. The caption under a figure is the caption the page carried and nothing else: a figure the page gave no caption gets no caption line, and the generated `figN` name and the bbox are addressing detail rather than something a reader was asked to read. Copy is unaffected — the figure's `data-md` still carries the whole `![fig](sightread://p…)` placeholder with its coordinates. A crop that 404s (results parsed before crops existed, or a crop that failed) falls back to the dashed placeholder frame in the same slot: an old result must not render as a grid of broken images. While a parse is still running that failure is provisional — a partial result can expose a placeholder a beat before the worker has written its crop — so each new snapshot forgets past failures and retries, and only a failure that outlives the final result stays a placeholder.
- **JSON** replaces the body with the pretty-printed result on the sunken surface.

### Editing

The document is editable as soon as it opens; there is no mode to enter. What the viewer renders is the document's **editable copy** from the user's workspace (`GET /api/library/documents/{id}/content`, [workspace.md](./workspace.md)), not the parse result — the result stays what the JSON tab shows. Every block is markdown: clicking a paragraph, heading, list, table, formula or caption turns that one block into a monospace textarea holding its source; leaving it (blur, Escape, Ctrl/Cmd+Enter) renders it again. `app/lib/markdown.ts` keeps each block's source lines (`src`) for this, and `serializeDocument` joins the blocks and page markers back into the one markdown string the API stores, so a round trip through parse → serialize is byte-stable for every shape the parser knows. Saves are automatic: a change marks the header's one-word status *Editing*, a debounce of 1.2 s sends `PUT …/content` with the `base_revision` the document was loaded at, *Saving…* then *Saved*; a **409** reloads the content and tells the reader the document changed underneath them (another tab, or the agent); a block editor open at that moment is closed and its draft dropped, since the block it was editing may no longer be where it was — the notice says the document changed. A save that fails for any other reason keeps the reader's text as unsaved work — a reload replaces only what is saved — so the next edit retries it, closing the viewer retries it once more (a save still in flight when the viewer closes and failing after it is retried once as well), and nothing typed is lost to a reload in between. The `edit` event of an open conversation reloads the content the same way, so an agent's edit appears in place.

### Notes

A second column, toggled by the header's notes icon (remembered like the rail), holding the document's `notes.md`: rendered markdown until clicked, a plain textarea while editing, saved with the same debounce and `base_revision` rule through `PUT …/notes`. No title row, no toolbar — the column is the notes.

### The agent panel

A third column, toggled by the header's agent icon, is the `chat` agent's thread about this document ([chat.md](./chat.md)). At its top a conversation title with a chevron opens the document's conversation list and *New conversation*. The thread renders `messages` plus the live `chat_events` stream: the user's turns right-aligned on the sunken surface; the assistant's text; its between-tool notes (`thinking` events) as muted one-liners; each tool call as one mono line (`bash ls figures`, `view_page 3`) with a check or a cross when its result arrives; each `edit` as a diff card — removed lines on the danger wash, added lines on the accent wash — whose footer says *Applied* with a **Revert** text button (`POST …/revisions/{commit}/revert`; after it, *Reverted* and **Apply again**; both wait while a turn is running, since the route refuses a revert under an unfinished turn). The composer is one rounded field (18px radius, the one rounded control in the app besides the context menu) holding a two-row textarea, an attach control at the left and a round accent send button at the right; Ctrl/Cmd+Enter sends. Sending posts the message (`POST /api/conversations/{id}/messages`), appends it locally and opens the SSE stream from the last seen `seq` — for the conversation the message was sent to: a reader who switched threads while the send was in flight finds it in the thread it belongs to, not the one now open; a turn error renders in the thread as a red line, and the composer is disabled while a turn is running except for **Stop** (`cancel`). The selection, when there is one in the document at send time, goes with the message as `selection`. The panel subscribes with `useConversationStream` (`app/composables/useConversationStream.ts`), which owns reconnects and the `after` cursor.

Both columns live inside the dialog beside the document pane and never float over it: they take their width from the pane, and closing either gives it back. Scrollbars are hidden on all three regions (they still scroll); the document column keeps its 70 % measure of whatever width remains.

## Rules

- Auth state via `GET /api/me`; unauthenticated → sign-in page; signed-in on `/` → `/files` (locale-aware, client-side). Login is a plain link to `/api/auth/login` (server redirect flow, no client OAuth).
- The web app calls only `/api/*`, plus the two full-page navigations of the server redirect flows (`/api/auth/login`, `/api/kano/connect`). Session cookie, `credentials: include`, custom `X-Requested-With` header on mutations (CSRF pairing with SameSite=Lax).
- Frontend renders only what the backend returns — empty states are real states, never fabricated sample data.
- Uploads never pass through a Nuxt route. `/files` posts its multipart body to `/api/library/documents`, which Caddy sends to FastAPI like every other `/api/*` request; there is no server route, no Nitro handler and no Node buffer in the path. The one local-development caveat is the dev proxy rather than an exception to that: `nuxt dev` pipes `/api` to `localhost:8000` so the session cookie stays same-origin, and it streams the body through without touching it. `curl` and connector instructions still live on `/keys` and `/connect` — the library is for reading a document, not for learning the API.
- Every control has a visible focus ring: a 2px accent outline at 2px offset, never removed, never replaced per component.
- **A tab left open across a deploy moves to the new build by itself.** The authed pages are client-rendered and long-lived — `/files` is a tab people keep for days — so without this a release changes nothing for them until they happen to reload, and a fix to the viewer looks like it never shipped. The app compares its own build id with `/_nuxt/builds/latest.json` (Nuxt's app manifest; nothing new is served) whenever the tab becomes visible, and also listens to Nuxt's own periodic check. Once a newer build exists the page reloads at the first moment that costs nothing: immediately if the page is idle, on the next route navigation (as a full load of the target), or when the page's last *hold* is released. A hold is how a page says "not now": `/files` holds while its upload queue is non-empty and while the result viewer is open, and `/history` while the result viewer or the Add to Files picker is open, because a reload would drop files still waiting to upload, lose the reader's place, or close a dialog mid-choice. A failed check is silence, never an error — the next one will do (`app/lib/build-update.ts`, `app/plugins/build-update.client.ts`).
- The browser tab title is the site name (`app.name`) on every page, set once in `app.vue` — authed pages do not set per-page titles, so the tab reads "Sightread" across tab switches. The sign-in page alone overrides it with its SEO title.
- i18n: every user-visible string goes through the catalog; en and zh-TW ship together. Locale switching lives on the sign-in footer and, once signed in, behind the account menu's Language row (§ The account menu) — real links, since the locale lives in the URL. A locale's own name comes from the i18n config; its name in the language being read comes from the catalog (`language.<code>`), so adding a locale means adding that line to every catalog. The sign-in link passes the locale to `/api/auth/login`, which returns the visitor to the same one ([auth.md](./auth.md) § 1).
