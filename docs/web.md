# Web (Nuxt control plane)

The web app configures, issues and observes — and on `/files` it is also where a person parses a document by hand, without a terminal. That is one addition to what it does, not two: it still runs no parsing and implements no upload endpoint. The browser posts the file straight to FastAPI's control plane and the same `jobs.intake` sequence `/v1/parse` runs takes it from there ([api.md](./api.md) § Why the web upload is a control-plane route). What the Nuxt server never handles is a document. It also *renders* a finished result, because reading what came back is observation, not a second data plane.

## Stack

Nuxt (latest stable) + TypeScript + `@nuxtjs/i18n` (en, zh-TW; en is the source catalog), pnpm. No UI framework and no CSS framework — hand-rolled primitives over the design tokens in `app/assets/css/main.css`, styled in each SFC's own scoped block. There is no Tailwind, no utility layer, and no second component library. Two libraries do one job each: KaTeX typesets math, and TipTap 3 (headless, over ProseMirror) is the in-place editor (§ Editing) — it brings no styles or components, and draws with the same `md-*` classes as the renderer (`app/assets/css/markdown.css`).

## Pages

The sidebar lists two screens, Files and History: they are the work. Everything you configure once — the agent, API keys, the MCP connector, usage, theme and language, the account — lives in the **settings dialog** behind the account menu (§ The account menu), one section each, so the nav never fills with things you open twice a month.

### Search engines

What a crawler reads is built with the public pages, at `nuxt build`, from one value: the public origin.

- **The origin.** `WEB_URL` reaches the build — `docker-compose.production.yaml` passes it to the web image as a build argument — because the public pages are prerendered there and their links are fixed then, not when they are served. It is the i18n `baseUrl`, so every public page's canonical link, `hreflang` alternates and `og:url` are absolute (Google ignores a relative `hreflang`), and `runtimeConfig.public.siteUrl` for the rest of this section. A build without it, a local one, keeps those links relative, writes `robots.txt` without a `Sitemap` line and an empty sitemap.
- **`/robots.txt`** (prerendered, from `shared/seo.ts`): one rule for every crawler, none named — AI search and training crawlers are treated like any other. They are kept off the authed pages (`/files`, `/history`, `/settings` and their `/zh-TW` forms, shells that send a signed-out visitor to sign in), the sign-in redirect (`/api/auth/`), the data plane (`/v1/`), the authorization server (`/oauth/`) and the MCP endpoint (`/mcp`), and pointed at the sitemap. The rest of `/api/` stays open on purpose: the pricing and policy pages render from `/api/billing/catalog` and `/api/site`, and a crawler that runs scripts needs them to see the plans and the contact line.
- **`/sitemap.xml`** (prerendered, from `shared/seo.ts`): the public pages — `/`, `/pricing`, `/terms`, `/privacy`, `/refund` — in both locales, each entry listing its `en` and `zh-TW` alternates and `x-default` (the English page). `nuxt.config.ts` prerenders the same list (`PUBLIC_PATHS`), so a page added there is public in both locales and in the sitemap at once.
- **Structured data.** Both home pages carry one `WebSite` object — `name` the catalog's `app.name`, `url` the origin's home page — which is what Google reads a site's name from, and every page carries `og:site_name`. No `FAQPage`: Google stopped showing FAQ rich results in May 2026. No `SoftwareApplication`: its rich result needs ratings or reviews the service does not have.

## Design system — light glass

Apple's own look, held back: solid white content, the system font, continuous rounded corners, and Liquid Glass only on the controls and navigation that float over the content — never on the content itself, and never glass on glass. The reference is the design canvas's mixed version (the reader of *F iPad*, the library of *E Mac*); dark mode is the same structure in Apple's dark appearance (*G*).

- **Tokens** in `app/assets/css/main.css`, as plain custom properties on `:root` — this app's one convention. The color ramp is paper / paper-sunken / rail / rail-active / desk for surfaces, ink / ink-soft / muted / faint for text, line / line-soft / line-strong / hair / edge for rules, `--fill` and `--fill-strong` (the system's translucent grays, behind a secondary button, a chip, a segmented control's track), the glass set (`--glass`, `--glass-pane`, `--glass-blur`, `--shadow-glass`, `--shadow-pane`), and one `--accent`. Spacing, radius, type, control heights and the list rhythm are tokens too: a raw hex, a raw `padding: 13px` or a raw `font-size: 15px` inside a component is the same class of bug. Every color is declared once, as `light-dark(<light>, <dark>)`, and nothing outside the token block names a color. The light values are Apple's (white paper, `#1d1d1f` ink, `#6e6e73` secondary text, `#e5e5ea` separators, `#0071e3` blue); the dark values are Apple's dark appearance (`#1c1c1e` paper, `#f5f5f7` ink, `#0a84ff` blue), not an inversion. Text tokens clear WCAG AA (4.5:1) on `--paper` in both. One surface token belongs to the result viewer alone: `--block-selected`, the wash a block selection draws (§ Editing, *Keyboard block selection*) — between `--rail` and `--rail-active` in both appearances. It is neutral rather than the accent because selecting blocks commits nothing, and an accent wash already means a place the viewer led the reader to (`--accent-wash`, `--find`); a selection drawn in the same hue would read as one more of those.
- **Theme.** Light and dark are both first-class, and the reader chooses. `:root` carries `color-scheme: light dark`, so with no choice made every `light-dark()` token follows the system; `<html data-theme="light">` or `"dark"` pins `color-scheme` to one side and every token with it. The choice is the settings dialog's *Theme* control (`useTheme`: `system`, `light` or `dark`, kept in `localStorage` as `sightread.theme`, `system` meaning no attribute), and an inline script in `<head>` reads the same key before first paint so a pinned theme never flashes the other one. The only other color-scheme-dependent values in the app, the Google button's prescribed light and dark variants on the sign-in page, are `light-dark()` pairs too, so they follow the same pin.
- **The accent marks what is chosen, pressed or about to be committed** — the system blue, and only there: primary buttons, the selected row of a focused list (§ Files), the library's folder glyphs, a toolbar toggle that is on (a 14 % accent tint under the glyph in the accent), the sidebar's glyphs, links, meters, the brand mark, the reader's own message in the agent panel, focus rings, the context menu's highlighted row, and the line a dragged block will land on — which, like the library's drop target (§ Files), exists only while a drag is in the air. Never on headings, borders or body text. Status has its own hues — green for succeeded, the system gray for queued, cyan for running, red for failed — as dots beside a word, never as the only signal.
- **Type**: the system font everywhere — `-apple-system, BlinkMacSystemFont, system-ui` (SF Pro on Apple platforms, Segoe UI on Windows, Roboto on Android), then `PingFang TC` and `Noto Sans TC`, the app being bilingual; `ui-monospace` for model ids, key prefixes, URLs, bboxes and code. No web font is loaded. A screen's large title is 28px bold at −0.022em, a dialog's title 17px semibold, a section heading inside a screen 20px bold; UI and table text is 14px, secondary text 12–13px in `--muted`, and the reader's prose has its own two sizes (§ Result viewer). Labels are sentence case: nothing is set in tracked capitals. Every figure carries `font-variant-numeric: tabular-nums`.
- **Geometry**: continuous rounded corners, concentric where one shape holds another. `--radius-xs` 4px (a key cap, a highlight), `--radius-sm` 6px (a gutter control in the document), `--radius` 8px (fields and plain controls), `--radius-md` 10px (list rows, chips), `--radius-lg` 14px (grouped lists, banners, menus), `--radius-xl` 20px (dialogs), `--radius-card` 28px (the sidebar, the reader's cards, a plan card); buttons, toolbar controls and segmented controls are capsules (`--radius-full`). Rules are 1px, and half a pixel in a glass edge. Shadows: `--shadow-glass` on a floating control, `--shadow-pane` on the sidebar and the reader's cards, `--shadow-dialog` on dialogs and the mobile drawer, `--shadow-menu` on the context menu, on the floating pieces built from its surface (below) and on the result viewer's drag card.
- **Glass is for what floats; content is solid.** One recipe, as Apple's Liquid Glass guidance asks: a translucent fill (`--glass`: white at 72 % in light, `rgb(54 54 58 / 72%)` in dark) under `backdrop-filter: var(--glass-blur)` (`blur(24px) saturate(180%)`), a one-pixel top highlight, a half-pixel edge and a soft shadow (`--shadow-glass`). It is on the toolbar capsules and round buttons (the screens' toolbars, the reader's header), the selection toolbar, and — denser, as `--glass-pane` with `--shadow-pane` — the sidebar and the reader's notes and agent cards. It is never on a document, a list, a dialog or a form, and nothing glass sits on glass: a button inside a card or the sidebar is a plain fill. Where `backdrop-filter` is unsupported the same surfaces are opaque (`--paper`, `--rail`). The context menu is its own surface, opaque rather than glass (below).
- **The frame.** One layout, `default`, a non-scrolling `100dvh` window on `--paper`: the sidebar is a floating glass pane inset `--space-4` from the window's top, left and bottom, 236px wide and `--radius-card` round, and the content region takes the rest. A screen (`UiScreen`) is a **toolbar row** (floating controls, `--control-height-lg` high: the screen's actions at the right, a segmented control at the left where it has one), then the **large title** (`UiPageHeader`: the screen's name — or the open folder's breadcrumb — with what is beside it, a count or a tally, in `--muted`), then the screen's content, which scrolls on its own under the list's sticky column header and its hairline while the toolbar and title stay. Nothing puts a whole screen on one scrollbar above the breakpoint. There are no rails: the margin column of the previous design is gone, and what it held — History's tally — is the line beside the title. `min-width: 0` on the grid tracks and the flex children is load-bearing: without it a table forces the region wider than the viewport instead of scrolling inside its panel.
- Below 900px the sidebar goes behind a focus-trapped drawer — the same glass pane, sliding in from the left — opened from a menu button in a slim top bar, and a screen is one scroll. The public pages — sign-in, pricing, the policies — are full-bleed and own their frame (`layout: false`, `PublicShell`): the public bar, a translucent glass bar that stays at the top as the page scrolls under it (the mark and name; at the right the page's name and *Sign in* as the bar's one small accent capsule), the page on `--desk` with its cards on `--paper`, and the public footer.
- **Primitives** in `app/components/ui/`: `Screen` (the toolbar row, the large title and the scrolling content of a signed-in screen), `PageHeader` (the large title and what is beside it), `Panel` (a scrolling body under an optional header, no border or shadow), `Capsule` (a glass capsule of a toolbar's icon buttons — the screens' toolbars, the reader's header — a toggle that is on in the accent tint, a button whose menu is open filled), `Segmented` (the system's segmented control: inline, a `--fill` track with the chosen segment raised on `--segment`; or `glass`, the toolbar's 44px capsule — *Files · Trash*, *Theme*, the Agent section's tabs), `DataTable` (the only table markup, drawn as Finder's list — sentence-case 12px column headers in `--muted` over a hairline, `--row-height` rows with `--radius-md` ends and no stripes — a row fills with `--fill-weak` only under a pointer that hovers, and otherwise only in a state its caller draws, such as Files' selection; `min-width` + nowrap so it scrolls in place, a sticky header, per-column alignment), `Modal` (`--radius-xl`, opaque, its header a 17px title and a round close button, and able to host a grid-bodied dialog as well as a form; `size="full"` fills the viewport, which only the result viewer asks for, and `back` draws the close as a round back button at the header's left), `Button` (capsules: accent / secondary on `--fill` / ghost / danger, `icon-only` round, four sizes, `lg` being the toolbar's 44px), `TextInput`, `Select`, `Field` (label-less with an `aria-label` where the design has no visible label), `CopyField`, `CopyButton`, `UsageBar` (a 6px rounded accent bar on `--fill`), `StatusDot`, `EmptyState`, `Banner`, `Skeleton`, `Spinner`, `ConfirmDialog`, `ContextMenu` (a floating list of items opened at a point — teleported to `<body>`, or into the dialog's panel when it opens inside a `Modal`, because `aria-modal` hides everything outside the panel from assistive tech and the dialog's Tab trap counts it as outside; positioned by the pure `app/lib/menu.ts` so it flips at a viewport edge instead of being clipped, arrow-key navigable, dismissed by Escape, a click outside, or a scroll outside it. It is never taller than the viewport: a menu that would be scrolls inside its own edge, so its last items stay reachable. **Nothing is highlighted when it opens**: focus lands on the menu itself, not on its first item, because the highlight is the pointer's — a menu that opens with a row lit is claiming the pointer is on that row, and the lit row stays lit for as long as the menu is up. `focusFirst` is the exception, set when the menu was opened from the keyboard, where the highlight is the cursor. An item is a button, or a real link when it carries `to`, and one of a set of choices carries `checked`; an optional `header` names what the menu is about). Its callers: the library's right-click, History's right-click (§ History), the sidebar's account row (§ The account menu), the agent panel's conversation list, the result viewer's More button (§ Result viewer), and the result viewer's block menu (§ Editing). Besides `header`, a menu about one thing can carry `facts` — label/value rows under the header, values in `.mono` where they are identifiers, wrapping rather than ellipsized — for the facts a single header line cannot hold; they take no focus and do nothing, like the header, and are the menu's `aria-describedby`, so a screen reader reads them when the menu opens rather than skipping them on the way to the items. An item can also carry a `shortcut` — text drawn right-aligned in `--faint`, in the mono face (`shortcutMono`) when it is markdown or a command rather than a key, and a key not drawn at all on a coarse pointer, which has no keyboard to press it on — and `labelMono` with `description`: the label in the mono face, followed on the same line by a second text in `--muted`, cut with an ellipsis and whole in the row's tooltip — a skill's name and what it does, as the composer's command menu, the slash menu and the selection toolbar's skill list draw them. And `children`, a submenu: a second surface flown out beside its row, to the right or to the left where the viewport has no room (`placeSubmenu` in `app/lib/menu.ts`), top-aligned with the row — or, where neither side has room, as on a phone, over its parent, `--space-2` down and in, so the row it came from stays in sight. The row carries `aria-haspopup="menu"` and `aria-expanded`. It opens on a press, on ArrowRight or Enter with its first item highlighted, or when the pointer rests about 150 ms on the row; a pointer crossing other rows on its way there does not close it: another row takes over only once the pointer has rested on it for about 300 ms, so a diagonal path to the submenu does not lose it on the way. ArrowLeft or Escape goes back to the row rather than closing the whole menu. The submenu is the menu's own second surface, teleported beside it rather than drawn inside, where the menu's scrolling box would clip it; the menu counts it as inside — a press, a scroll or a right-click in it closes nothing — and the arrow keys move within whichever surface holds focus. A scroll of the menu itself closes the submenu, since it takes the row out from beside it, and focus that was in the submenu goes to the menu. The block menu's *Turn into…* is the one submenu. The account menu's reason against one (§ The account menu) still holds where it was made — a choice that deserves room to be read gets a dialog — and a submenu is the right shape only for a short list of parallel choices under one action, which would otherwise double the parent's length. `Kbd` — a key cap: `--paper`, an `--edge` hairline, `--radius-xs`, `--text-2xs` in `--muted` — whose text always comes from the shortcut helper below, never typed at a call site. `Icon`. There is no `Badge`: a count is muted text beside a title. The cards there are — the reader's two, the pricing page's plans, the sign-in card — are styles of the pages that draw them, not a primitive. The library adds no primitive: its parse meter is `UsageBar` (a meter is a meter), and the two things it does need — `FolderTree` (the flattened, expandable tree the folder picker is made of — its only caller) and `MoveDialog` (the folder picker History's *Add to Files* opens) — are page components in `app/components/`, beside `ResultViewer`, because only a door into the library has a tree to draw.
- **`ContextMenu` is the platform's menu.** `--radius-menu` corners, an opaque `--menu-surface` (`#fafafc`, `#2c2c2e` in dark — not glass: a translucent menu let the rows under it read through its own), a hairline `--menu-edge`, the two-part `--shadow-menu` (a tight contact shadow for the edge, a wide soft one for the height), items inset inside the padding with their own `--radius-menu-item`, and a 120ms scale-in from whichever corner the pointer opened it at — restarted by hand when a second right-click reuses the same element, and off under `prefers-reduced-motion`. The highlighted row is filled with the accent: it is the action about to be committed, which is what the accent is for. A destructive row fills with `--danger` instead. The result viewer's other floating pieces are built from the same tokens, for the same reason — each floats over the document rather than being part of it: the slash menu, the outline's panel, the hint bar, the status note and the return pill (§ Result viewer, § Editing); the find bar and the selection toolbar are glass capsules (above), and the agent panel's reply toolbar, over the agent's glass card, is the menu's surface in the capsule's shape. A switch (`role="switch"`) is the system's: a capsule track, `--fill-strong` off and the accent on, its white knob sliding across.
- **Shortcuts are labelled for the platform.** One pure helper (`app/lib/shortcuts.ts`) writes every key a label, a hint or a `Kbd` shows — Apple's symbols on Apple platforms (`⌘⇧↑`, `⌘/`, `⌘[`), `Ctrl+Shift+↑`, `Ctrl+/`, `Ctrl+[` elsewhere — and one predicate reads the modifier off a key event: Meta on Apple platforms, Ctrl elsewhere, with Ctrl accepted on Apple platforms too for a key the browser there leaves alone. A label naming a key the reader's keyboard does not have teaches the wrong habit, and two hand-written spellings drift apart in the first release that adds a third.
- **Icons** are Lucide paths on a 24 grid at stroke 1.75, inlined in `Icon.vue` — never a package, never a remote sprite, never inline SVG at a call site — and named in `IconName` (`app/lib/icons.ts`). Icon-only controls carry `label` (= aria-label + tooltip); a destructive action either keeps its visible word or, when icon-only, is backed by a `ConfirmDialog` whose title and message carry it. **One action, one glyph**: an action on the document has the same glyph on every surface it appears on — a block's menu, the selection toolbar, the slash menu, an outline row — and no two of those actions share one, so a reader who has learned one surface reads the others.
- **Motion**: 120–240ms, on color, background, opacity and a few pixels of scale or slide — the context menu's scale-in, the find bar's and the outline panel's 4px slide, the drawer's slide, the reader's document re-centring when a card opens or closes — none under `prefers-reduced-motion`. No hover elevation anywhere: hover is a fill (`--fill` on a capsule, `--rail` on a row, and the translucent `--fill-weak` on a table's row and on a row on the menu surface, where an opaque `--rail` could match what is under it) or a text-color shift to the accent on a link.
- Icons ship as three files in `public/`: `favicon.svg` (the source mark — the `scan-text` glyph in white on a rounded square of the light accent, lighter at the top, as the system draws an app icon; `AppBrand` draws the same blues, `--mark-top` and `--mark-bottom`, in both appearances, so the tab and the page show one icon), `favicon.ico` (16/32/48, generated from it) and `apple-touch-icon.png` (180). All three are declared in `nuxt.config.ts`, and the FastAPI consent page declares them too, each with the mark's version as a query (`?v=2`): a browser keeps a site's icon in a store apart from the HTTP cache and fetches it again only when its URL changes, so the version is raised in both places whenever the icons change. The `.ico` is not redundant: clients that do not take SVG — connector webviews among them — request `/favicon.ico`, and when that answers a blank placeholder they fall back to whatever icon they already hold for the parent domain.

## The account menu

The sidebar's foot is one button — the round avatar (the Google `picture` when one is stored, the identity's first letter on a gray disc otherwise), the name, and an up-down chevron — opening `UiContextMenu`, the same floating surface the library's right-click opens. Nothing else in the sidebar is a control.

- **What it holds, and nothing more:** the signed-in address as a header line (a fact, not an item), then **Upgrade** on Free or **Usage** on a paid plan (once `GET /api/me` has answered), **Settings**, **Language**, and **Sign out** under a rule. No plan and no balance in the menu: the balance is the Usage section's and the composer's notice's (§ The agent panel), and a figure that changes with every turn is noise in a menu opened to go somewhere. **Upgrade** goes to the pricing page (§ Pages, `/pricing`), where the plans are presented and the checkout starts; **Usage** opens the settings dialog on *Usage*, where the paid plan is managed (§ Pages, `/settings/usage`); Settings opens it on *General*, both over the screen the menu is on. The menu itself never starts a checkout, so it needs no catalog read. No help, no product tour — this app has none of those, and a menu padded out with rows that lead nowhere is worse than a short one. Upgrade is the exception because the way to a bigger plan is otherwise three clicks deep.
- **Language is one row opening a dialog** (`LanguageDialog`), not locales listed inline and not a submenu — a submenu is a second floating surface to position and dismiss, and the choice deserves room to be read. The dialog is a grid of options that reflows to the width it is given; each is a real link (`switchLocalePath`, so you stay on the page you were reading) saying its language in *that* language over the same name in the one you are reading now — the first line for whoever is looking for their own language, the second for whoever cannot read the first. The current one carries the accent check on the selected-row surface the nav already uses.
- **Sign-out moved inside.** It used to be an icon beside the row, which made the foot two controls and put the session's most destructive action one stray click from the name. It is now the last item, below the rule, where a desktop app puts it.
- **Pressing the row while the menu is open closes it.** The menu dismisses on a press anywhere outside itself, which lands before the row's own `click` — so the row ignores a click that arrives within 200ms of a dismissal, or it would reopen what the press just closed.

## Files — the library

A file manager over parse results and markdown documents: folders that nest like directories, and one file per result or per markdown document (`documents` + `folders`, [database.md](./database.md)). A document is a name, a place in the tree and a pointer at the job that produced it — never a second copy of the markdown — or, for a markdown document, no job at all: its text is its workspace copy ([workspace.md](./workspace.md) § Markdown documents). **It works the way the desktop's file manager does — Finder's model, with ⌘ read as Ctrl off Apple platforms** — because that is the one model every reader already has: a click selects, a double click opens, the keys are the ones their hands know, nothing that can be undone asks first, and a deleted file goes to a Trash.

- **One read, then local navigation.** `GET /api/library` returns every folder and every document for the account at once — and what is in the Trash, beside them — and opening a folder is a computed filter, not a request. A library is small (rows, not documents — the bytes are long gone), and a per-folder fetch would put a spinner between a click and a list that was already in memory.
- **Two places, one pane each.** At the toolbar's left a segmented control, **Files** and **Trash**, the Trash's segment carrying how many items it holds (`role="tablist"`, ← and → between the two). Files is the folder you are in and nothing else: no persistent tree beside the list. You go down by opening a folder row and back up with Esc, ⌘↑ or the breadcrumb that is the screen's large title, which is also a drop target per level — the moves a single-pane file manager gives you. Losing a tree costs the at-a-glance shape of the whole library and the drag straight into a folder three levels down; spring-loading (*Moving*) gives the second back, and what the trade buys is a screen with one thing on it. **The toolbar's actions are the menus' own**: *New document*, *New folder* and *Refresh* in a glass capsule, then the accent *Upload…* (on Trash, *Empty Trash*), each doing what the same item of the list's menu does, so the commonest four are one press away without a right-click.
- **A click selects; a double click opens.** A click on a row selects it; ⌘-click adds a row to the selection or takes it out, ⇧-click selects the run from the row clicked last, and a click on the list's empty space clears it. A double click opens: a folder in place, a document in the result viewer. Every action takes the selection, so five files are picked once and then trashed, copied or dragged together. Selected rows are drawn as Finder draws them: filled with the accent, their text white, while the list holds focus; with focus elsewhere (a dialog, the toolbar) they keep a neutral `--rail-active` fill, so the selection never vanishes and the accent stays the mark of where the keys go. **On a touch screen a tap opens**, as it always has: a coarse pointer has no double click and no modifier keys, and selecting first would put a second tap between the reader and every file. A long press opens the row's menu for that row.
- **The keyboard is Finder's.** Read at the window, so the keys work after a click without anything holding focus, but never from a text field, an open menu, a dialog or the result viewer, which own their keys. On Files:
  - ↑ and ↓ move the selection, ⇧↑ and ⇧↓ extend it, Home and End go to the first and the last row, and ⌘A selects every row. Typing the first letters of a name selects the first row starting with them — case-insensitive, begun again after a one-second pause.
  - ⌘↓ opens the selection, and so does Return off Apple platforms. Esc and ⌘↑ open the folder above, with the folder just left selected, so Esc pressed again climbs to the top and ↓ goes back down. Esc at the top level does nothing.
  - Return renames on Apple platforms, Finder's key, and F2 everywhere, Explorer's.
  - ⌥⌘N makes a new folder. ⇧⌘N, Finder's own, opens the browser's private window and never reaches the page.
  - ⌘C copies, ⌘V pastes copies, ⌥⌘V moves what was copied here, and ⌘D duplicates.
  - ⌘⌫ moves the selection to the Trash, and so does Delete, Explorer's key.
  - ⌘Z undoes, ⇧⌘Z redoes, and so does Ctrl+Y off Apple platforms.

  The menus show the same keys beside their items, written for the platform (§ Design system, *Shortcuts are labelled for the platform*): `⌘⌫` on a Mac, `Delete` elsewhere.
- **The menus act on the selection.** Right-click on a selected row opens the menu for every selected row; on a row outside the selection it selects that row first, as Finder does. The row's menu: **Open** (⌘↓) and **Rename** (↩, or F2), for one row only — *Open* disabled on a parse queued or still running, **Retry failed pages…** added on a failed one (**Retry…** when no page is missing, as after a failed format check), and **Re-convert…** on one whose parse succeeded with no re-convert on its way, beside the retry and the dismissal of a failed one (*A parsed document can be re-converted*, below) · **Copy** (⌘C) and **Duplicate** (⌘D) · **Move to Trash** (⌘⌫, or Delete). The list's own menu, opened on its empty space, acts on the folder that is open: **Upload…**, **New document**, **New folder** (⌥⌘N) · **Paste** (⌘V), which names how many items it will paste and is disabled with nothing copied, and **Move N items here** (⌥⌘V), there only while something is copied. Refresh is not in either: the list re-reads itself while anything is parsing, and the panel header keeps its refresh control for the rest. **The cost is stated rather than designed away:** an account with an empty library sees a screen with nothing to click, and the first upload has to be discovered through the menu or through drag-and-drop. That is the trade this screen accepts to have one interaction instead of three.
- **A menu is not mouse-only.** A right-click is one of three routes into the same menu: a long press on touch (500 ms, cancelled by a 10px drag, and it eats the click that would otherwise open the row), and `Shift+F10` or the Menu key with the list focused — the list takes a tab stop for exactly this reason — which opens the menu for the selection, under its first row, or the list's own with nothing selected. Inside it, arrows and Home/End move, Enter selects, Escape closes and focus returns to what opened it.
- **Nothing pops up for a file operation.** No dialog names, moves or deletes anything on this screen:
  - **New folder** and **New document** make the item at once — *New folder* or *Untitled*, with the library's ` (2)` where the name is taken — select it and open its name for editing, as Finder and Explorer do. A new document is not opened: it is opened as any other, once it has its name.
  - **Rename** turns the name into a field in its row, with the name before its extension selected (a folder's whole name). Return or a click anywhere else keeps the new name, Esc puts the old one back; an empty or unchanged name sends nothing. The window losing focus — another app, a system dialog — does not end the edit; the field has focus again on the way back. A name already taken in the folder keeps the field open, the name selected for retyping, with the server's message over the list.
  - **Move to Trash** happens at once, with no question, and the status note says so with *Undo*.
  - Only the two deletes nothing can undo — *Delete Immediately* and *Empty Trash* — ask first, in a strip over the Trash's list rather than a dialog (*The Trash*).
- **Copy and paste.** ⌘C keeps the selected rows on the page's own clipboard — not the system's, which has no way to hold a library row — until the page reloads, and the status note says *Copied 2 items*. ⌘V in any folder makes copies there and selects them ([api.md](./api.md) `…/copy`: a document with its text, notes, original and images as they are now, a folder with everything live under it; the parse is shared, not repeated, and conversations stay with the original), with ` (2)` where the name is taken; the clipboard stays, so a second ⌘V makes a second set. ⌥⌘V moves the copied rows into the open folder instead and empties the clipboard — Finder's *Move Item Here*, and the keyboard's route for moving. ⌘D copies the selection into its own folder. A copy the server refuses — a folder into its own subtree, a workspace at its quota — stops there, with the server's message over the list.
- **Undo.** ⌘Z undoes this page's last file operation and ⇧⌘Z redoes it, as Finder's Edit menu does: Move to Trash and Put Back undo each other; a move moves back, to its old name too when the destination had suffixed it; a rename renames back; a copy, a paste, a duplicate, a new folder or a new document goes to the Trash. The status note says *Undone* or *Redone*. At most 50 steps, gone when the page reloads. A step that fails because the library changed elsewhere — the item deleted in another tab, its old name taken since — is dropped with the server's message over the list, never retried. *Delete Immediately* and *Empty Trash* are not undoable, which is why they are the two that ask.
- **The status note** is the result viewer's (`PaneFoot`, § Editing *Undo and the status note*), at the foot of the list and with its timing — a note carrying *Undo* stays until the next action, or for 8 s, held while the pointer rests on it; any other for about 1.6 s: *Moved 2 items to the Trash · Undo (⌘Z)* (*已將 2 個項目丟到垃圾桶 · 復原 (⌘Z)*), *Put back 2 items · Undo (⌘Z)*, *Copied 2 items*, *Undone*, *Redone*, *Deleted 2 items for good*, *Emptied the Trash*, and *Put it back to open it* for a double click in the Trash. A move, a rename, a paste or a new item shows itself in the list and has no note.
- **Size is what a document takes.** The *Size* column is the document's share of the storage (`storage_bytes`, [workspace.md](./workspace.md) § Quota): its original once, its text and notes, its inserted images and whatever a command wrote in its directory, never the service's copies of them — so a markdown document has a size too, and a folder's documents add up to what Usage counts for them. A row still uploading shows the bytes it is sending; a folder shows none, nor does a document while the workspace cannot be measured.
- **The Trash.** Its tab lists each item trashed itself — a folder counts once, with everything inside it — under the title *Trash*, with **Empty Trash** in the panel header (a danger text button, disabled while the Trash is empty), in four columns: *Name*, *Original location* (the folder Put Back returns the item to: a folder glyph and the folder's name, the whole path in the tooltip, *Home* for the top level), *Size* (a document's share of the storage, as on Files; a folder's item count) and *Date trashed*, the latest first. Its rows select and take the keys as on Files. The menu: **Put Back** (⌘⌫) and **Delete Immediately** (⌥⌘⌫, Delete off Apple platforms, the Recycle Bin's key); the list's own menu holds **Empty Trash**. Put Back returns the item to where it came from, or to the nearest folder above it that is still live, with ` (2)` where the name is taken there ([api.md](./api.md)), and the note says so with *Undo*. *Delete Immediately* and *Empty Trash* open a strip at the top of the list — *Delete 3 items for good? This can't be undone.* over *Cancel* and *Delete for good*, the second a danger button — which Esc or *Cancel* closes; nothing is deleted until it is answered. Nothing in the Trash opens (the server answers 404 for all of it, [api.md](./api.md)): a double click on a trashed item says, in the note, to put it back first.
- **Uploading is a client-side queue, because the server has a real limit.** `MAX_JOBS_PER_USER` (2) is a cap on *running* jobs, so posting five files at once earns three 429s. The page treats a 429 as back-pressure rather than an error: files upload one at a time, a refused one waits and retries, and every file is a row from the moment it is dropped — its own local row until the server answers with a document id. A request that never reached the server at all is treated the same way, because a dropped connection halfway through a large upload is the case where making someone find the file again hurts most. Nothing is silently dropped and nothing needs re-picking. A file is refused before it is sent only when the server would refuse it too — the same media-type-then-extension judgement intake makes, from the two lists `GET /api/me` returns. Retrying costs nothing twice: the same bytes, still parsing, answer with the job already running rather than a second one ([jobs.md](./jobs.md) § Dedup), which is also what makes uploading one document into two folders one parse and two files. A row still uploading is not selectable: it has nothing to act on yet.
- **A parse the balance cannot cover is refused before it queues** (402 `insufficient_credits`, [billing.md](./billing.md) § Refusals): the upload's row leaves the queue and a dialog says what the document needs, what is left and when the period resets (the error's `need`, `remaining` and `period_end`), with *Cancel* and **See plans** — the pricing page (§ Pages, `/pricing`), where *Upgrade* is. The figures never show a negative balance: an overdrawn period reads 0 ([billing.md](./billing.md) § A chat turn). The page count is the server's (it is read from the file once uploaded), so there is no confirmation before the upload: a parse that fits runs, and what it cost is History's once it is settled (a document's `credits` is null while its reservation is pending, which is the whole of a queued or running parse). The dialog is `CreditsDialog`, the same one the agent panel opens on a refused send.
- **A markdown document is written here or uploaded.** *New document* makes *Untitled* in the folder that is open and opens its name for editing (*Nothing pops up for a file operation*); a name already taken takes the ` (2)` suffix a new folder would. A `.md` or `.markdown` file goes up through the same queue as a PDF and becomes a markdown document instead of a parse — capped at `markdown_max_bytes` rather than `upload_max_bytes`, refused here first from `GET /api/me` like any other file, and opened by itself like a single upload. Its row has no status, pages or size: there is no parse to report on, and an empty cell says so better than a made-up *Succeeded*.
- **Progress is polled, not streamed.** While any document is `queued` or `running`, the page re-reads `GET /api/library` every 2 s and stops when none are. One request refreshes every row's status and `pages_done`; the alternative is one SSE connection per running document for a number that changes a handful of times per job.
- **A failed parse is retried, never opened.** A parse with a failed page has no result ([parsing.md](./parsing.md) § Vision-only conversion), and its row says what a retry would send: *N pages failed* in the danger tone (`failed_pages`), or plain *Failed* when no page is missing. Opening it — a double click, ⌘↓, the menu's *Open*, a link to it — opens the **retry dialog** instead of the result viewer, and its menu carries *Retry failed pages…* as well (*Retry…* when no page is missing, and the dialog's title is then *Retry*). The dialog lists the pages a retry sends (`GET /api/library/documents/{id}/pages`), each as a tile: the page as the original shows it (`…/pages/{n}/image`), its number, why it failed and which model failed it — a page never reached says so — twelve tiles at most, then a count of the rest; above them, the job's own error when no page carries one — a failed format check said in the reader's language, with its reason in the words a page's reason has (`the format check failed (<reason>)`, [parsing.md](./parsing.md) § Format check). Under them, **Model** — the parse agent's fallback when one is set, else the model the job last ran, picked from the same live catalog as the Agent page; left out when no page is missing, as after a failed format check, since such a retry sends no page to a model — and one line: only these pages are sent, the rest are kept, and the document opens once every page has succeeded; with no page missing, that none is sent again and the document opens once the retry succeeds — or, while the format check is on (the check agent's `auto_check`, read from `GET /api/agents` with the fallback), that the document is checked again, with the check's settings on the Agent page, and opens once the check succeeds, since a retry checks with the settings of its moment ([parsing.md](./parsing.md) § Format check). Under it, in every case, that the retry reserves the parse's credits again and is charged only if it succeeds ([billing.md](./billing.md) § A parse). The buttons are *Cancel* and *Retry page N* / *Retry N pages* (*Retry* when no page is missing); a failure (the parse no longer failed, no original kept) shows inside the dialog, and a balance that cannot cover the credits (402) closes it into the credits dialog an upload's refusal opens. A retry puts the row back to *Queued* at once, and the document opens by itself when the retry succeeds, as a single upload does; a single upload that fails opens the dialog by itself in the same way, and so does a retry that fails again.
- **A parsed document can be re-converted** ([jobs.md](./jobs.md) § Re-converting a document). *Re-convert…*, in the menu of a document whose parse succeeded and has no re-convert on its way, opens a dialog: the model to run, from the live catalog with the parse agent's own selected, and one paragraph on what happens — the version open now stays until the new one is ready and is then replaced, edits made meanwhile are replaced too and stay in its revisions, and the notes stay. While the new parse runs, the row's status column says so in place of its own — *Re-converting* with its progress, *Checking format* past its last page — and the page polls as for any running parse; everything else about the row is as before, and the document opens on the version it has. Its result viewer says under the header that it is being re-converted, on which model, and what happens to edits. When the swap lands, an open viewer starts over on the new version, read again, and the status note says it was re-converted. A failed re-convert is said on the row in the danger tone, *Re-convert failed*, and its menu carries **Retry failed pages…** (**Retry…** when no page is missing) — the retry dialog on the re-convert's pages, error and model — **Dismiss re-convert**, and *Re-convert…* again, which replaces it; opening the document still opens the version it has.
- **Reading it is the point — once there is all of it.** Opening a document opens the result viewer below. A parse opens only once every page has succeeded, as a reader never opens a document with a page missing ([parsing.md](./parsing.md) § Vision-only conversion): a queued or running row is not opened — its status and progress are what there is to see, and a running parse past its last page that is being checked says *Checking format* (`checking`, [parsing.md](./parsing.md) § Format check): its menu's *Open* is disabled, and a double click, ⌘↓ or a link to it only says, in the status note, that it opens once every page is done (once its format is checked, while it is *Checking format*) — and a failed one opens the retry dialog (above). A *single* upload that finishes while its folder is still open opens itself, because "upload it and read it" is the whole flow; a batch does not — five dialogs racing each other is not a feature.
- **Moving.** Drag the selection — or a row outside it, which is then selected alone — onto a folder row, onto a breadcrumb, or onto the list of the folder that is open. **Folders spring open**: a drag held over a folder row or a crumb for 0.8 s opens that folder under the pointer, as Finder's do, so a drag goes down any number of levels and drops in the list it opened. Holding ⌥ as it drops (Ctrl off Apple platforms) copies instead of moving, and the drop effect says so. A drag dropped on the **Trash** tab moves what it carries to the Trash. The live drop target is one of the few places the accent touches a border — with the agent panel's drop zone and the result viewer's drop line (§ Editing), each a drop indicator — and it is deliberate: each exists only while a drag is in the air, and a drop target you have to squint at is a file in the wrong folder. Drag-and-drop is invisible to a keyboard and to assistive tech, so it is never the only route: Copy, then *Move N items here* in another folder, is the same move from the menus or from the keys.
- **`dragover` decides everything** (`app/lib/dnd.ts`). It fires continuously on exactly one innermost element and bubbles to the window, so the handler nearest the pointer *claims* the event and the window clears whatever went unclaimed — which is also what un-highlights a target that has been left, and what cancels a folder's spring-loading timer when the drag moves off it. `dragleave` is used nowhere on this screen: it fires for every child element a pointer crosses and bubbles like everything else, so a row built from an icon and a name reports "left" halfway across itself, and browsers disagree about what `relatedTarget` holds on a drag. Three consequences worth knowing: the window swallows a file dropped outside every target, because the browser's default there is to navigate to the file and take the page — and the upload queue in it — with it; the window carries `dragend` too, since a row can be replaced by a poll mid-drag and its own never arrives; and the flags a *file* drag sets expire on a timer, because a drag from the desktop can be carried out of the window without leaving this page a single event it can trust.
- **Names behave like a file system's.** Unique within their folder — folders and files in one namespace, so a folder cannot be called what a file beside it is called — and a collision is resolved rather than rejected: the server appends ` (2)` on upload, on a new folder or document, on a copy and on a move, and on Put Back. A rename that would collide is the one case that answers 409, because there the name is the thing the user just typed and silently changing it would be a lie. A name in the Trash takes no room: a new file can take the name of a trashed one at once.
- **A drop lands where the page said it would.** While files are being dragged, the overlay names the open folder, so a folder row or a breadcrumb under the pointer does not quietly take them somewhere else — it lets the drop through to the list. Rows of the library itself are the opposite: they are exactly what a folder row accepts.
- **A failure is said over the list.** A rename that collides, a move that races, a paste the server refuses: the message is a banner at the top of the list, closed by its own button or replaced by the next action's — nothing on this screen has a dialog to hold it.
- **Where the reader is lives in the URL.** The open folder is `?folder=<id>` (none at the top level) and the document open in the result viewer is `?doc=<id>`, beside whatever else the query holds (`?settings=`). Opening a folder or a document pushes a history entry, so the browser's Back closes the viewer, then walks back up the folders it came down, and Forward goes the other way; closing the viewer by its own X or Escape goes back the same way when the entry before is the same place without the document, and drops `doc` otherwise (the viewer opened from the URL itself, or Settings opened over it in between). A refresh or a pasted address opens the same place once the library has loaded: a folder that is not in the library opens the top level, and a `doc` that cannot be opened — not in the library, still parsing, or failed, whose opening is its retry dialog — is dropped from the URL. A folder that goes away in another tab replaces its entry with the top level rather than adding one. The Trash tab stays out of the URL.
- **A file can be linked to.** `/files?document=<id>` opens the folder that holds the document, selects its row and lights it for a moment, scrolled into view — how History's *Show in Files* lands. The query is consumed on arrival (replaced away), so a refresh or a later visit opens at the top level as usual. An id that is not in the library — deleted, or in the Trash, in another tab — opens the top level and nothing else.
- **A block can be linked to.** `/files?document=<id>&block=<anchor>` — the address a block's *Copy link to block* reference carries (§ Editing) — reveals the row as `?document` does, then opens the document in the result viewer scrolled to the block: near the pane's top, washed like a located heading (§ The agent panel, *Section links*), the collapsed section holding it expanded first, and the way back set to the top of the document (§ Result viewer, *Outline, collapse and the way back*). **The anchor names a place without a page number**, because the reader never sees pages: a heading's own GitHub-style slug (`-1` for a repeat, numbered as section links number them), or, for any other block, the slug of the section it sits in — empty before the first heading — then `~`, which no slug contains, then the block's first words: its plain text with the markdown removed (a formula as its TeX), cut to 8 words or 60 characters; the anchor is URL-encoded. A block with no words of its own, a figure without a caption, is linked as its section. **Opening resolves in order** — the first block in that section whose plain text starts with those words, compared as a located passage is (§ Notes, *Locate*); else such a block anywhere in the document; else the section's heading; else the top — so a link survives edits above it and a block moved to another section, and degrades to the nearest place it can still name rather than to nothing. It is read once the document's copy has loaded (a parse still running is followed until it can be edited), and replaced out of the URL with `document`, so a refresh does not jump again. History has no links: it has no document to point into.
- **No instructions anywhere on this screen.** The drop target, the empty folder, the empty Trash and the menu items say what they are — a screen that needs a sentence explaining how to use it is a screen that has not been designed yet. The empty state is a state, not a tutorial: it says the folder (or the Trash) is empty and stops there.

## History — filing a parse

History lists every parse, and most of them never entered through the library — an API call or a connector parse has a result but no file. The row's context menu is how one becomes a file, without uploading the same bytes again.

- **Same menu, same routes in.** Right-click, a 500 ms long press on touch, or `Shift+F10` / the Menu key on a row's filename — exactly the library's three routes, so nothing new to learn between the two screens. The panel has no list menu: History has nothing to create.
- **What it holds:** **Open** (the result viewer, the same as clicking the name), **Add to Files…**, and **Show in Files** when the parse is already in the library. Add stays available on a parse that is already filed — one parse in two folders is a legitimate library, the same as uploading one file twice — so the marker below is what prevents an accidental duplicate, not a disabled row.
- **A failed parse cannot be filed.** It has no result, and a file that opens to an error is a dead entry in someone's library. The row is shown disabled rather than hidden, so the menu has the same shape on every row. A queued or running parse can be filed: the library already tracks progress, and the document opens there once every page has succeeded.
- **Add to Files is the move picker.** `MoveDialog` with its title and button saying *Add to Files* / *Add*, over the same tree. It opens on the folder last chosen in this page load, because filing a batch of API parses is usually filing them into one place, and on the top level otherwise. Any folder is a valid destination, the top level included, and the picker's *New folder* (below) makes one on the spot. The name is the job's filename, with the library's ` (2)` rule on a collision. Failure stays inside the dialog, as on Files.
- **The picker can make the folder it needs.** Its footer carries *New folder* on the left, away from the confirm button. It opens a name field under the tree, prefilled and selected, which creates the folder **inside the folder currently selected** — the field's label says which — and then selects the new one, so a move or an add into a folder that does not exist yet is one dialog rather than a trip back to the list. Enter creates, Escape closes the field without closing the dialog, and a failure shows in the dialog's own banner. Creating is refused for a destination the item could not be moved into anyway (a folder's own subtree). The new folder is real the moment it is created: cancelling the move afterwards leaves it in place, as a desktop save dialog's New Folder does. A folder refuses to move into its own subtree, in the client and again on the server.
- **A dialog with a request in flight cannot be dismissed.** Its controls are already disabled while one runs; `UiModal`'s `busy` closes the two routes around them, Escape and the scrim. Closing would not stop the request — a filing would land after the reader thought they had backed out of it.
- **A dialog reports its own failure.** A filing that fails, a folder the picker could not make: the dialog stays open, so the message belongs inside it. A banner on the page behind the overlay reads as the button having done nothing at all.
- **A filed parse says so.** A faint folder glyph after the filename marks a row that has at least one file, titled with the folder it lives in. It is the answer to "did I already file this?", and it is what appears when Add succeeds — the dialog closes and the mark is the confirmation, with *Show in Files* now in the menu. Color is not involved: the glyph is `--faint`, because it is a fact about the row, not data.
- **The library is read alongside the jobs.** `GET /api/library` is fetched with `GET /api/jobs` and joined on `job_id` in the client; it is the same small read the Files screen makes, and it gives the picker its tree without a request between the menu and the dialog. A library that fails to load leaves History fully usable: the marks are missing and Add / Show in Files are disabled, rather than the page failing for a feature most rows never use.
- **Show in Files** goes to `/files?document=<id>` (§ Files). A parse filed more than once goes to the most recently added file.

## Result viewer

Opened from a document on `/files` (`GET /api/library/documents/{id}/result`) or a filename on `/history` (`GET /api/jobs/{id}/result`) — one component, two callers, because a parsed document reads the same however it was started. **A full-screen dialog** (`UiModal size="full"`): every other dialog in the app is a box over the page you were on, but this one is not an interruption to a screen — it is the thing you came to read, and a 1040px box in the middle of a 27" display makes a document look like a receipt. **Its header carries the filename and nothing else of the parse**: no `model · N pages · bbox format` line and no save status beside it (§ Editing) — the title is what a reader looks up at, and a line of pipeline facts under it is read once and then sits there on every visit. The header is the reader's toolbar, floating on the page as the iPad's is: a round glass back button at the left that closes the viewer (`UiModal back`), the filename centred, and at the right one glass capsule of icon toggles — **Find**, **Notes**, **Agent** — and a **More** button (`ellipsis`). Each is named by its label (the tooltip and the accessible name), and a toggle that is on takes the accent tint (§ Design system). More is disabled until the result has loaded, since everything in its menu is the result, and a menu that grew under the pointer when the facts arrived would no longer fit where it was placed. It opens `UiContextMenu` under the button: the parse's facts as label/value rows (model, pages, bbox format, and the figure check once the result's figures went through one: how many passed it, or how many of them are unverified — the menu's `facts`, below the design system's note), then **Markdown** and **JSON** as a pair of `checked` choices — the two views were a segmented toggle in the header, and the JSON view is the contract a developer checks now and then, not a mode a reader flips while reading. A running parse still shows its progress note under the header (below): that is live state, not a fact.

- **It reads as a document, not as UI.** The prose is set on its own two sizes (`--text-read` / `--text-read-sm`) rather than the dense UI scale the rest of the app uses, because this is the one surface that is read continuously instead of scanned. The column is **70% of the pane, centered** — on a very wide display that is wider than a typographer would set prose, and it is the width the reader asked for.

- **Markdown** is the default tab: one continuous scroll of the whole document. **The document itself never carries page labels** — a reader checking a transcription reads it as a document, not as a stack of pages — and **the viewer offers no page navigation either**. The page grouping is real (a figure's crop is addressed by the page it came from, and a page marker still splits the document's blocks) but it is the pipeline's fact, not something the reader steers by: a reader finds a passage with Find and a section with the outline (*Outline, collapse and the way back*, below), and the agent says where it changed something by the section heading or the words it changed, never by a page number the reader has no way to see ([chat.md](./chat.md) § System prompt). A column of page buttons beside the document was tried and removed — it took the width of a column for a list most documents never needed.
- **The find bar floats over the document and never reflows it**: it is absolutely positioned inside the pane, so opening it leaves every line of text exactly where it was — a reader who opens a search to find the paragraph they are looking at must not have that paragraph move first. `app/lib/markdown.ts` turns the result's markdown into ordered blocks per page: the `<!-- page: N -->` markers split pages, and within a page `##`/`###` headings, GFM tables in either form (the outer pipes are optional, so the separator row is what identifies one), `-`/`1.` lists including wrapped items and the number they start at, `$$` display-math (fenced on its own lines, or with the dollars sharing a line with the formula — `$$x = 1 \tag{1.6}$$` is how most models write a numbered equation) and its LaTeX spelling `\[ … \]` (GPT models write it; the opener is `\[` alone on its line or a line its first `\]` ends, so a reference line `\[87] A. Author …` stays prose and `\[x^2\] and \[y^2\]` is prose holding two formulas) and fenced code blocks (whose line breaks and indentation are their content), table-of-contents runs (below), `![fig](sightread://p…)` placeholders with the caption on the next line, `>` blockquotes (below), a thematic break (`---`, `***` or `___` alone on its line — a page's footnote rule, so it is drawn as one: a short hairline at the start of the measure, never the setext heading CommonMark would make of `---` under a line, since a transcription's `---` is always the rule), and paragraphs each become a block. Parsing is client-side because the API returns the document as one markdown string (docs/parsing.md § Page markers). The format check reads a page's blocks by these same rules (`parsing/joins.py`, [parsing.md](./parsing.md) § Format check), so a change to them is made in both.
- **Math renders through KaTeX.** Prose, headings, list items, table cells and captions are split on `$…$` spans (`parseInline` in `app/lib/markdown.ts` — a span opens on `$` + non-space, closes on non-space + `$`, and never ends before a digit, so "$5 and $6" stays prices. **The closer is the first `$` at brace depth zero**, not simply the first one: TeX nests math inside text, so `$\text{\sout{$E'_v$}}$` is one formula — closing on the first dollar cut it in half and handed KaTeX an unbalanced fragment, which fell back to source and left the whole line reading as raw TeX. An escaped `\$` opens nothing. **The LaTeX spellings are math too**: `\( … \)` — GPT models' inline math, spaces inside allowed — and `\[ … \]` inside a line; the second only when what it holds reads as TeX (a backslash command, `^`, `_`, a brace or `=`), because `\[87\]` is how a markdown-escaping model writes the reference `[87]`. A backslash that is itself escaped opens nothing), and each span is typeset by KaTeX (`app/lib/math.ts` — rendered with `throwOnError` **on** and the exception caught, so a failure falls back to the whole formula's source rather than KaTeX's inline red error text; the CSS and its bundled fonts ship with the app, nothing remote). Display `$$` blocks are typeset the same way in display mode; a block KaTeX cannot parse at all falls back to the verbatim `<pre>` it always was, because wrong glyphs are worse than visible TeX. **Repairs are tried before that fallback, and only for a formula that already failed** — source KaTeX accepts is never rewritten. Three slips account for nearly every formula it rejects in a transcribed book, each with one unambiguous reading (`app/lib/math.ts`): a block that is a single `aligned` environment with `\tag` on its rows — a numbered derivation, which TeX's one-tag-per-display rule rejects — is re-typeset as `align`, the same layout with a number per row, and rows the page left unnumbered get `\notag` so `align` does not invent numbers for them; a command with arguments used as a bare script (`V^\boldsymbol{\pi}`) gets the braces that were meant; and an equation printed across two lines and transcribed as two blocks, whose `\left\{` opens in one and `\right\}` closes in the next, gets TeX's own null delimiters (`\right.` / `\left.`) so each half compiles. The rendered inline span carries its original TeX in `data-tex` and a display block carries its `$$…$$` source in `data-md` — what copy-as-markdown reads back. A display block scrolls **sideways only**: a tall formula — a `\begin{cases}`, a stacked fraction — expands the block to its full height instead of being handed a vertical scrollbar, because a formula is one object and half of it behind a scroll gesture is not a formula anyone can read.
- **A table of contents keeps its lines.** Markdown joins consecutive lines into one paragraph, which is right for wrapped prose and wrong for a contents page: a book's `1.1 Sequential decision making . . . . . 13` lines arrive one per line with no blank line between them, and joined they read as one run-on paragraph of dots. A run of lines in which any line ends in a dot leader and a page number (`. . . . 13`, `.....iv`) is therefore a `toc` block: one row per line, the title on the left, the page number on the right, and the leader drawn by CSS instead of printed as characters — so it fills whatever width the column has rather than wrapping. A line of such a run without a leader (`**1 Introduction** **13**`, a chapter row) still splits off a trailing page number; one without any number is a title-only row. Copy hands each row back as its source line, leader characters included (the leader element carries them in `data-src`), rows joined by single newlines as the model wrote them. Find-in-document sees titles and page numbers, not dots.
- **Inline markdown renders as text, not source.** Within the same inline pass, `**strong**`, `*em*` / `_em_` (underscores only at word boundaries, so `usage_log` stays text), `` `code` `` spans, `<br>` line breaks and `<sup>`/`<sub>` become real elements — table cells like `**96.5**` and `UniVLA<br>(Ours)` read as the table meant them to, and a paper's author line `THYAGATURU<sup>1</sup>` as a name with its affiliation mark. GFM has no superscript syntax of its own and GitHub renders these two tags, so a model asked for GitHub-flavoured Markdown writes them whenever it does not reach for `$^{1}$`. `<br>`, `<sup>` and `<sub>` are the only HTML tags read, and only bare (no attributes, any case): every other tag stays visible text, because rendering a transcription's HTML is a sanitisation decision this parser does not make. Nesting parses (`_**Abstract**_`, `**A<sup>1</sup>**`) and each rendered element carries its exact source in `data-src` for copy. **Emphasis may hold math**: a caption `**Figure 1: … $8\times 8$ patches …**` or an abstract in `*…*` with `$k$` inside is bold or italic around its formulas. The math spans are found first and stand in the text as one opaque character each while the emphasis is read, so a `*` or `_` inside a formula still never opens or closes emphasis, and an emphasis marker outside one still pairs across it. **Backslash escapes are consumed, not printed**: a transcription of a reference list arrives full of `\[87]`, and GFM says that is `[87]` — a backslash before ASCII punctuation makes the character literal and disappears itself, while a backslash before anything else (`C:\path`) is an ordinary one and stays. This is the one shape whose copy is not character-exact: an escape leaves no element to hang `data-src` on, so `\[87]` copies back as `[87]`, which re-renders identically.
- **A wide table scrolls by itself.** The prose column is a fixed fraction of the pane, so a table with more columns than that gets its own horizontal scrollbar (an `overflow-x` wrapper per table) instead of stretching the page or crushing its cells.
- **A blockquote is a block that holds blocks, one level deep.** A run of lines each starting with `>` is one `quote` block; its content — every line with the `>` and one space after it removed — is parsed as blocks of their own (paragraphs, headings, lists, display math, code, tables) and drawn as `blockquote.md-quote`: the inner blocks inset by `--space-3` behind a 2px bar in `--edge`, at whatever text size the surface sets. **One level**: a `>` inside a quote is that quote's text, as a nested list is one level (*Known limitation*). A reader makes quotes now — *Quote in notes* writes one (§ Notes), *Turn into* and `> ` make one (§ Editing) — so the parser reads what the editor can write; the notes are read by the same parser, and the editor's schema has the same node. A quote round-trips byte for byte like every other shape, and copy hands it back as `> ` lines. A heading inside a quote is quoted text, not a section of this document: the outline, collapse, section links and *Add context* do not see it.
- **Ctrl+F finds in the document.** The header's Find button opens a find bar over the document (Ctrl/Cmd+F does the same while the viewer has focus, and the browser's own find is suppressed only there — the viewer is a scroll region inside a dialog, and the native bar cannot reach into it usefully). Enter and Shift+Enter step through the hits, the counter reads `n / total`, Escape closes the bar without closing the dialog. A hit inside a collapsed section counts like any other, and becoming the current one expands that section, so stepping never lands on text the reader cannot see.
  Matches are painted with the **CSS Custom Highlight API**, not by wrapping hits in `<mark>`: the rendered document is never rewritten, so the `data-src` / `data-tex` sources copy-as-markdown reads back cannot be cut in half by a search. Every hit takes the accent as a wash and the current one takes it solid (`--find`, `--find-current`). A browser without the API still steps and scrolls through the hits, just without the paint.
  Three things it deliberately does not search: KaTeX subtrees (a typeset formula is a tree of per-glyph spans plus a hidden MathML twin — searching it yields fragments and doubled hits), the JSON tab (the browser's own find is the right tool on a `<pre>`, and Ctrl+F is left alone there), and the viewer's own controls drawn among the blocks — handles, collapse chevrons, fold notes, backlink markers, the drop line (§ Editing, § Notes). Those are Vue-rendered siblings of a block's rendering, never written into it, and each carries `data-chrome`, which every walk over the rendered text skips — find's, copy's serializer, the selection the agent reads, `selectionEdge`, locate's and a block link's first words: they are not the document, and *4 blocks collapsed* must never be a hit, a copied line or a passage's text. Find's `MutationObserver` ignores a mutation that only adds, removes or changes `data-chrome` elements, so a handle drawn and taken away under a moving pointer does not rescan the document. A match may span elements — a phrase running through a bold word is one hit — because the search runs over the document's text with an offset map back into its nodes, not node by node.
- **Ctrl+C copies markdown.** A `copy` listener on the document pane serializes the selection back to markdown (`app/lib/copy.ts`): pipe tables from the selected rows and cells, headings at their source depth (the viewer draws two sizes but `data-level` keeps the original `#…` count), list markers, `$$`/fenced blocks verbatim, figure placeholders with their caption, inline math from `data-tex`, display math from its block's `data-md` (always the fenced form, whichever form the source used — it re-renders identically), rendered emphasis/code/`<br>`/`<sup>`/`<sub>` from `data-src`, and a quote as `> ` lines over its inner blocks' markdown (`>` alone on a blank line). Blocks a collapsed section hides and `data-chrome` elements are skipped, so a copy across a fold copies what the reader sees. A selection inside one paragraph copies as the plain text it looks like; a selection inside a code or display-math block copies verbatim, line breaks and indentation kept; anything structural copies as source a markdown editor will re-render. The serializer walks the cloned selection fragment, so a partial table selection yields a valid partial table.
- **A running parse is read page by page on History only.** The control plane answers with a partial result while a job runs (docs/api.md § Partial results), and opening a running job on History shows the pages that exist, a progress note in the header (`pages_done / page_count`), and a skeleton where the next page will land, rather than one spinner until the whole document is done; reopening it reads the snapshot again, and nothing partial is ever cached. Files never opens a parse before every page has succeeded (§ Files), so a document there is always read whole.
- A result written before a failed page failed the whole job can still omit pages, so the markdown view leads with a banner naming the missing pages when `result.errors` is non-empty. A degraded document must not read as a complete one. A new result never needs it: a parse with a failed page has no result to open (§ Files).
- **Known limitation**: the parser is flat. A nested list renders as one level — the items survive, the hierarchy does not — a blockquote is one level deep, so a `>` inside a quote reads as that quote's text rather than a quote within it, and a code fence is closed by any fence rather than a matching one, so a `~~~` block containing a literal ``` line ends early. These are deliberate: this reads a known set of block shapes rather than implementing GFM, and every shape added so far has revealed the next one it does not know. Rendering the result through a real GFM parser is the alternative, and it is a dependency and sanitisation decision of its own rather than something to bolt on here (KaTeX for math and TipTap for editing, § Editing, are the two such decisions already made — and the editor deliberately reads markdown through this parser, not through one of its own).
- **Figures render as the stored crop, centered in the column** with the caption under them — a crop is narrower than the measure far more often than not, and left-aligning it hangs it off an edge the text does not share. The pipeline persists each figure's crop (docs/parsing.md § Figure crops) and the viewer loads it from the caller's own figure route — `/api/library/documents/{id}/figures/{page}/{bbox}` on Files, `/api/jobs/{id}/figures/{page}/{bbox}` on History — addressed by the page and bbox the placeholder already carries. **A figure keeps its own page**: its crop and the placeholder copy hands back are read from the page its placeholder names (`sightread://pN/…`, kept on the `fig` block as its `page`), not from the page the block now sits in — blocks move across page markers (§ Editing, *Moving blocks*), and a figure moved to another page must still show its crop rather than ask for one at coordinates on a page that has none. The parser reads a placeholder as a figure only when it names its page, so every figure block carries its own. The caption under a figure is the caption the page carried and nothing else: a figure the page gave no caption gets no caption line, and the generated `figN` name and the bbox are addressing detail rather than something a reader was asked to read. Copy is unaffected — the figure's `data-md` still carries the whole `![fig](sightread://p…)` placeholder with its coordinates. **A figure the figure check could not confirm** (`check: unverified` in the result's `figures`, matched by page and bbox, so a moved figure keeps it; [parsing.md](./parsing.md) § Figure check) carries a short note under its picture, *Crop not verified*: chrome (`data-chrome`), so it is never copied, found or read as the document's text. The crop stays as it is; the note only says the reader should judge it. A crop that 404s (results parsed before crops existed, or a crop that failed) falls back to the dashed placeholder frame in the same slot: an old result must not render as a grid of broken images. While a parse is still running that failure is provisional — a partial result can expose a placeholder a beat before the worker has written its crop — so each new snapshot forgets past failures and retries, and only a failure that outlives the final result stays a placeholder.
- **An inserted image renders as a figure does** — centered, its caption under it, the dashed frame when it cannot be loaded. It is the reader's own picture rather than a crop: `![alt](figures/img-<hash>.png)` with an optional caption line (`img` blocks, [workspace.md](./workspace.md) § Inserted images), loaded from `/api/library/documents/{id}/images/{name}` on Files. History has no document and no images route; there an image line is the frame. The parser reads only that shape as an image — `figures/img-`, sixteen hex digits, `.png` or `.jpg` — so a URL in a document, typed or written by an agent, stays text and nothing is fetched from elsewhere. Copy hands the line back; the alt text is not drawn, the caption is.
- **Reading aids on both doors, block actions on Files.** The Markdown view adds two kinds of thing to the document. The reading aids — the outline, collapsing a section and the way back after a jump (below) — are on History too, because they change nothing but the view. Everything that acts on blocks — the handle and its menu, dragging, keyboard block selection and its undo, the selection toolbar, the slash menu, excerpts and backlink markers, links to a block (§ Editing, § Notes) — is on Files only, and there only once the document's copy is editable. History has no document to change, no notes and no agent, and Ctrl+C already copies markdown there. Every rule of these that can be pure is, in framework-free `app/lib/*.ts` with vitest tests ([testing.md](./testing.md) § Frontend); the components only measure, draw and route events.
- **A markdown document opens straight onto its copy.** It has no result to fetch (the result route answers 404 for it): the viewer reads `GET …/content` at once and is editable from the start, with the same blocks, notes, agent and reading aids as a parsed document. It has no parse facts and no JSON, so More stays disabled, and no figure route — a `sightread://` placeholder pasted in reads as the dashed placeholder. **Pages it never had are not added**: `app/lib/markdown.ts` reads text before the first `<!-- page: N -->` marker as an unmarked first page and writes it back unmarked, so a document with no markers saves with none — an edit never puts `<!-- page: 1 -->` at the top of a reader's own file. A marker the reader types is a page like any parsed one.
- **JSON**, chosen from the header's More menu, replaces the body with the pretty-printed result on the sunken surface; the same menu's **Markdown** goes back, to where the reader was in the document. Find, Notes and Agent are hidden while it shows, as they were, and so is everything the Markdown view adds — none of it means anything over the contract.

### Outline, collapse and the way back

Three reading aids, on Files and History alike. None of them writes anything, and all three answer the same need: finding a place in a long document that has no page to steer by.

**The outline floats; it never takes width.** A column of page buttons beside the document was removed because it took a column's width (above), and the outline is the opposite trade. At the top left of the document pane, over the gutter (8px from the pane's left edge, about 64px from its top), it is a column of short ticks, one per heading — 16px for a `#` or `##` heading, 10px for `###` and deeper, 2px high and 8px apart, centered on one another, in `--edge`, the current section's in `--ink` — so the document's shape and the reader's place in it read at a glance and cost nothing. The whole is a `nav` named *Document outline* (*文件大綱*). The pointer resting about 150 ms on the ticks opens the **panel** over them — not at once, so a pointer only crossing the gutter on its way to a handle does not throw a panel over the text — and the pointer leaving the panel closes it. The panel is the menu surface (§ Design system), 264px wide, `--radius-menu`, and enters as the find bar does, with opacity and a 4px slide from the left over `--duration-fast` (none under `prefers-reduced-motion`): a faint header *Outline* (*大綱*), then a row per heading. A row is one 30px line cut with an ellipsis, the whole heading its tooltip — a `###` row 12px further in and in `--muted` — and the current row is semibold in `--ink` with a 2px `--ink` bar at its left (`aria-current="location"`), whatever its level. Hovered or holding focus, a row fills with `--fill-weak`, not the accent: it holds two more buttons, and an accent fill would claim the whole row is one action. The panel scrolls inside itself when long, held to the pane's height, and opens scrolled to the current row. **For the keyboard the ticks are one button** (*Outline*, `aria-expanded`). Focus on it alone opens nothing, so a reader tabbing past it into the document does not get the first lines covered; Enter, Space or ↓ opens the panel with focus on the current row. The rows are buttons in a list, Tab moves through them and their actions, and the panel stays open while focus is inside it: Escape closes it and returns focus to the button, where it stays closed, and Tab past the last action, or a press elsewhere, closes it as focus leaves.

- **A row's click is a jump.** The heading lands near the pane's top (`LOCATE_MARGIN_PX`, as a section link lands), any collapsed section holding it expands first, and the way back is set (below). It is not washed: the reader picked it by name, and it lands where their eye already is.
- **Row actions, on Files.** On hover or focus a row shows two icon buttons, 24×24 with 15px glyphs in `--faint` that turn `--rail-active` and `--ink` when hovered: **Translate this section** (*翻譯這一節*, `languages`; `ask({section, command: 'translate', send: true})`, shown only when a user-invocable `translate` skill exists) and **Add to the agent's context** (*加入 Agent 脈絡*, `message-circle-plus`; `ask({section})`), each opening the agent column (§ The agent panel, *Asked from the document*).
- **The current section** is `currentSection()` — the last heading above a third of the pane, the rule the composer's *Current section* already uses, so the two never disagree — recomputed on scroll in a frame callback.
- **Drawn only where it fits**: when the document has at least two headings (one heading has no shape to show), and when the gutter left of the column has room for it beside a heading's own controls — its chevron, and on Files its handle — about 40px past them. Otherwise it is not drawn, and the stacked layout under 900px never has that room. A thing that floats over the gutter must never cover what the gutter already holds.
- **The ticks fit the pane.** They run from their offset down to where the pieces at the pane's foot begin — the hint bar, the pill, the status note — and never under them. Each heading has its own tick while they fit 8px apart; past that the gap closes, down to 2px; past that only the `#` and `##` ticks are drawn, the current one being the tick of the `#` or `##` heading the current section falls under; and a document with more top-level headings than even that holds draws the `list-tree` glyph in their place, the same button. The ticks are a glance at the document's shape, not a list — the panel lists every heading and scrolls — and packed tighter they would be a texture rather than a shape. What the pointer rests on is the ticks' own box, or the glyph's, never the whole gutter.

**Collapse hides a section; it is a view, not an edit.** Each heading has a chevron in the gutter just left of its text: a 24×24 button named *Collapse section* / *Expand section* (*收合這一節* / *展開這一節*, the block menu's labels) with `aria-expanded`, `chevron-down` while open and `chevron-right` while collapsed, filled with `--rail` and inked when hovered. It is drawn on hover or focus within the heading; always on a touch screen (`hover: none`), which has no hover and, on History, no focus to give; and always while collapsed, so a fold is never invisible. Under 900px the gutter holds one control, not two, so on Files a heading's handle takes the chevron's place only while the heading is open in its editor, selected, moving or has its menu open — which is how a touch screen reaches a handle anyway (§ Editing) — and the chevron has it the rest of the time; on a phone the document keeps a 32px side padding on both doors, the room a 24px chevron needs. It hides the heading's section — the blocks after it up to the next heading of the same or a higher level, across page markers, the extent `sectionSource` reads — and under the heading a fold note in `--text-sm` and `--faint` reads *4 blocks collapsed* (*已收合 4 個區塊*), comments not counted. The note is itself a button, named for what pressing it does — *Expand section, 4 blocks collapsed* (*展開這一節，已收合 4 個區塊*) — and since it goes away as it expands, focus moves to the heading's block (on History, to its chevron) rather than falling to the page, where the next Escape would close the dialog. Nothing is written into the document: the collapsed headings are remembered in the browser (`localStorage`), per document on Files and per job on History, by their slugs — which survive the edits that move indices — and slugs the document no longer has are forgotten once it has loaded whole, never from a partial result, which lacks the pages still to come. Only the most recent 100 documents are kept, since `localStorage` is small and shared by everything the app keeps there. Hidden blocks are `[hidden]`, as the blocks an open editor holds are, so `.block` must never be given a `display`: an author `display` outranks the attribute, and collapsed and held blocks would both show.

- **What the reader cannot see is never acted on unseen.** Keyboard block selection and the editor's arrow navigation skip hidden blocks (`neighbour()` steps over them); a drag selection never opens an editor holding one (§ Editing, *Selecting is editing*); a copy across a fold copies what is visible; deleting a collapsed heading expands its section first and deletes the heading alone (§ Editing). Backspace at the start of a block whose previous block is hidden — the heading after a fold — expands that section before it joins, so the join happens in sight, and an emptied block hands its caret back to the previous visible block, never into a fold.
- **Nothing moved or typed disappears into a fold.** A section runs to the next heading of its level, so whatever lands after a collapsed section's last hidden block is inside it — where *Move down* past a fold puts a block, and *Move up* over the heading that follows one, and a drop on a collapsed row's lower half, and Enter at the end of a collapsed heading's own editor. When a move, a drop or an edit puts a block there, the section expands as it lands, so the reader keeps sight of the block and of focus. A heading of the section's level or higher ends the section, so one moved there lands outside it and keeps its own fold.
- **What leads into a fold opens it.** A find hit becoming current, an outline row, a section link, an excerpt's locate, a block link, and an agent edit that changes a block inside a collapsed section each expand the section holding the target. An agent edit is placed by comparing the reloaded blocks' sources with the ones before the reload. **They open the view, not the memory**: what is remembered is what the reader set with the chevron, the fold note and the block menu, so the next time the document opens it shows the reader's folds as they left them, however many a find or a long translation opened meanwhile.
- **A fold follows its heading through an edit.** Repeated headings are numbered in document order — *Exercises*, `exercises-1`, … — so deleting, moving or adding one, or renaming a heading, changes the slugs after it, and a fold kept by slug alone would move to another chapter or spring open as the rename is written back. So whenever the shown document changes — a block action, an edit, an undo, the agent's edit — the viewer pairs the blocks before and after (`followBlocks`): the blocks both versions open and close with keep their order; between them, a run moved past another is the same blocks rotated; anything else was replaced, and its headings are kept by their source, in order, a renamed one paired with the new heading between the same two kept ones where as many came as went. Each fold, remembered and shown alike, moves to its heading's new slug, and one whose heading is gone is dropped; one whose heading the document before did not hold yet — nothing loaded, or a page still to come — stays as it is, kept or forgotten once the document has loaded whole. Text alone cannot tell twins apart where one is deleted right before the other, and a document opened after an edit the viewer never saw has only its slugs to go by: there a fold can land on a repeated heading's twin, and that costs the reader one click.
- **Where the chevron goes.** On Files it sits between the heading's text and its handle, so a heading's handle is further out than a paragraph's. Where the gutter has no room for both — the stacked layout under 900px, 40px of padding — the chevron is not drawn, and collapsing is the block menu's and the fold note's; History, which has no handle, draws the chevron wherever its own 28px fit. On Files the chevron is not a tab stop, since the block menu has the same item and each block stays one tab stop; on History, which has no menu, it is.

**The way back after a jump.** A jump — an outline row, a section link in an answer, an excerpt's link in the notes, a block link — moves the reader somewhere they did not scroll to, and the place they left is the one most often wanted next. So after one a pill at the bottom center of the pane offers it: 32px high, `--radius-full`, the menu surface, `--text-sm`, holding the `corner-up-left` glyph, *Back to “1 Introduction”* (*回到「1 Introduction」*) — the section the reader was in before the jump, by the same `currentSection()` rule, or *Back to the top* (*回到開頭*) above the first heading — and its key in a `Kbd`, ⌘[ (Ctrl+[ elsewhere, `aria-keyshortcuts`). Its heading is cut with an ellipsis so the pill stays inside the pane, at most the pane's width less `--space-8`, the whole text its name; on a coarse pointer the `Kbd` is not drawn, since it would name a key the reader has no keyboard for. Its click or its key restores the reading position from before the jump and hides the pill; a pill pressed hands focus to the block at the restored position, since the control that held it is gone. That position is kept as the block at the pane's top and how far into it the reader was, not a raw `scrollTop`, since the jump may have expanded a section above it. The pill is replaced by the next jump, pointing back to where that one started, and hides when the reader scrolls back near that place themselves (within a third of the pane's height), switches to JSON, or closes the viewer. **One step, no history**: a back stack would be a second navigation system for a document that has none, and the step that matters is the last one. A backlink marker scrolls the notes, not the document, and sets none (§ Notes). The viewer takes ⌘[ from the browser for as long as it shows the Markdown view, pill or not: on Apple platforms it is the browser's Back, and a reader who has learned the key must not be thrown off the document by pressing it once too often. The pill shares the pane's foot with the hint bar and the status note (§ Editing): they stack upward — the hint bar lowest, then the pill, then the note — and never overlap. Alone, the hint bar stands `--space-4` above the pane's foot and the pill `--space-6`; stacked, each keeps `--space-2` from the one under it.

### Editing

The document is editable as soon as it opens; there is no mode to enter. What the viewer renders is the document's **editable copy** from the user's workspace (`GET /api/library/documents/{id}/content`, [workspace.md](./workspace.md)), not the parse result — the result stays what the JSON tab shows.

**Editing is in place, never in source.** Clicking a paragraph, heading, list, quote, table, display formula, code block or figure or image caption puts the caret where the click landed in that same block, drawn exactly as it was read; selecting text by dragging opens it with the same text selected (below) — the way Typora or Notion edit, not a textarea of markdown. Underneath, the clicked block becomes a rich-text editor (`app/components/RichEditor.vue`, TipTap 3 over ProseMirror) styled with the same `md-*` classes the rendered block uses, so opening it moves nothing; leaving it (blur, Escape, a click on another block — a blur that follows a press on one of the viewer's own controls among the blocks is not a leave, *The block handle and its menu*) renders it again. One editor is open at a time, because a parsed book can be thousands of blocks and one editor per block on load would be thousands of editors.

- **Markdown is typed, not shown.** The shortcuts turn into what they mean as they are typed: `# `, `## `, `### ` start a heading; `- ` or `* ` a bulleted list and `1. ` a numbered one; `**bold**`, `*italic*` / `_italic_` and `` `code` `` become the styled text when the closing marker is typed; `$x$` becomes a typeset formula; `$$ ` at the start of an empty line a display formula; ```` ``` ```` a code block; `> ` at the start of a top-level paragraph a quote — not in a list item or a table cell, which the parser reads as one line of text — which Backspace at its start lifts back out; and `/` in an empty paragraph opens the slash menu (*The slash menu*, below). Ctrl/Cmd+B, I and E do the same for a selection. Backspace straight after a conversion undoes it, the editor's own undo for an input rule. Superscript and subscript are marks as well (TipTap's own extensions), so an affiliation mark stays raised while its line is edited; Ctrl/Cmd+. and Ctrl/Cmd+, toggle them, and nothing typed turns into one. Lists stay one level — Tab does not nest — and so do quotes, whose schema node holds no quote of its own, because the parser reads both flat (§ Known limitation) and a nesting the reader cannot see again after leaving the block is not an edit.
- **Selecting is editing.** A drag that selects text in the rendered document opens the blocks it covers as one editor, with the same text selected, so Delete or Backspace removes it, typing replaces it and Ctrl/Cmd+B styles it — the selection is still a selection, so Ctrl+C, the selection toolbar (*The selection toolbar*, below) and the agent's `selection` read it as before. **The selection is carried into the editor by text position, not by screen point.** `selectionEdge` reads each boundary as three numbers — the block it lies in, the textblock within that block (a paragraph, a heading, a list item, a table cell, a code block's text, and these inside a quote, in reading order) and the character offset within that textblock, an inline formula and a `<br>` each counting as one character and a boundary inside a formula or a display block snapping to its nearer side — and `openSelection` hands them to the editor, which resolves the same three numbers in its own document: it holds the same textblocks in the same order, because it was built from the same parse. Resolving the screen point under each boundary instead (`posAtCoords`) went wrong wherever the editor draws a hair differently from the rendering — a formula typeset at another width, a table's cells — so a drag across a table with formulas, or across paragraphs after one, opened with a different stretch of text selected than the reader made; the toolbar acts on that selection, so it has to be exact. A single click still places the caret at its point, which is all a click has. A selection spanning several blocks deletes across them as one document would, joining the first block's head to the last block's tail. Only a run of rich-text blocks on one page opens: a selection that crosses a page marker, a contents page, a figure or a block a collapsed section hides stays a read-only selection — the first three because none has a place inside one rich editor, the last because an editor would show and change text the reader folded away. Left unchanged, the run is written back as nothing; changed, the blocks it held are replaced by the editor's text.
- **A formula stays typeset while it is edited.** Clicking an inline or display formula opens a small floating TeX field under it (the context menu's floating surface: opaque, hairlined, rounded); the formula above it re-renders on every keystroke, so the field is the source and the block is its live preview. Enter (inline) or Ctrl/Cmd+Enter (display), Escape, or a click away closes it. A display formula's `\tag` and every repair `app/lib/math.ts` applies are the viewer's, because the editor typesets through the same `renderTexHtml`.
- **Blocks behave as one document.** Enter at the end of a paragraph starts a new one in the same editor, and it becomes a block of its own when the editor closes; Backspace at the start of a paragraph or heading joins it to the text block before it on the same page (not across a page marker: one editor holds one page's blocks, and *Move up* is how a block crosses one — *Moving blocks*, below); ArrowUp on the first line and ArrowDown on the last move into the neighbouring visible block, caret and all (a collapsed section's hidden blocks are stepped over). Escape leaves the editor and selects the blocks it held (*Keyboard block selection*, below), so the keyboard keeps its place in the document instead of dropping it on the dialog. A figure's image and a contents page are the exceptions: the image is not text (its caption is edited like any paragraph), and a contents row's dot leader has no rich-text form, so a `toc` block opens as its lines in the prose face.
- **One parser, and only edited blocks are rewritten.** The editor never reads markdown with a parser of its own: `app/lib/richdoc.ts` builds its content from `parseResultMarkdown` and `parseInline` — so what the editor shows is exactly what the viewer renders, `$5 and $6` stays two prices, `\[87]` stays `[87]` — and writes it back with a serializer of its own. Every top-level node remembers the source it was built from and the canonical form of that source; on the way back a node whose canonical form is unchanged is written as its original bytes, and only a node the reader actually changed is written in the canonical form (one line per paragraph, `**` / `*`, `<sup>` / `<sub>` outside them, `-` / `1.`, fenced `$$`, pipe tables with `---` rules, `<br>` for a line break, `> ` before each line of a quote and `>` alone on its blank ones, the characters markdown would read as syntax backslash-escaped). That canonical rewrite of the edited block is the one normalisation editing makes; a block opened and left without a change is not written at all. TipTap's own markdown package is not used: it is beta, and its parser disagrees with this one on dollars, escapes and tables.
- **Copy from inside an open block is markdown too**: the editor's clipboard text is the same serializer's output, so Ctrl+C reads the same whether the block is open or rendered.
- **No spellcheck.** The editor sets `spellcheck="false"`, block and notes alike: a parsed paper is full of names, acronyms and Chinese a browser dictionary flags on every line (Firefox underlines the whole open block), and the squiggles say nothing about the parse.

An HTML comment that is not a page marker is a block of its own, kept in the source and drawn as nothing, so an edit elsewhere leaves it in the file. `app/lib/markdown.ts` keeps each block's source lines (`src`), and `serializeDocument` joins the blocks and page markers back into the one markdown string the API stores, so a round trip through parse → serialize is byte-stable for every shape the parser knows, laid out as a parse writes it — each page marker on its own line before its blocks, the blocks one blank line apart, no newline at the end; a copy spaced otherwise, which an agent's edit can leave, is written back in that layout by its first edit. A block emptied in the editor is deleted. A document with no block left to draw keeps a way back in — *Add text*, a control in the block's place that opens an editor past the last block, whose text `appendBlockSource` makes a new block (page 1, for a document with no page) — so the editable empty state is never the read-only one. A page emptied of its blocks draws nothing: its marker stays in the file, and the blocks around it are the way in, so a move or a delete that empties a page — one that held only a full-page figure is common — leaves no dashed *Add text* where the reader saw a figure, at a page boundary they never see. Saves are automatic and **silent while they succeed**: a debounce of 1.2 s after the last change sends `PUT …/content` with the `base_revision` the document was loaded at. The one-word status (*Editing*, *Saving…*, *Saved*) is still kept, in a `role="status"` live region, but it is drawn only when it is *Not saved* — beside the title, in the danger colour, over the banner that gives the reason — since a word that flips on every keystroke tells a sighted reader nothing an autosave has not already promised, and the one state that needs their attention is the one where it broke; a **409** of type `revision_conflict` ([api.md](./api.md)) reloads the content and tells the reader the document changed underneath them (another tab, or the agent); a block editor open at that moment is closed and its draft dropped, since the block it was editing may no longer be where it was — the notice says the document changed. A save that fails for any other reason keeps the reader's text as unsaved work — a reload replaces only what is saved — so the next edit retries it, closing the viewer retries it once more (a save still in flight when the viewer closes and failing after it is retried once as well — once for the document and once for the notes, each on its own), and nothing typed is lost to a reload in between. The `edit` event of an open conversation reloads the content the same way, so an agent's edit appears in place; a reload that arrives while a save is in flight — the save's revision is older than the agent's, so the fetched text is newer than the save's answer — is noted and repeated once the save has settled, per file, so the viewer never keeps a revision the next save would 409 against without having shown the change.

#### The block handle and its menu

**Every rendered block but a comment has a handle**, on Files: a 24×24 button with the six-dot `grip-vertical` glyph (16px, `--faint`) in the gutter left of the block's first line, 4px from the text, `--radius`, a grab cursor. The viewer draws it inside the block's `div.block`, positioned against the block and beside its rendering rather than in it, with `data-chrome`, so copy and find pass over it (§ Result viewer). **It exists only where it can be used now** — on the block under the pointer, the focused block, the blocks in the selection, the block whose menu is open and the one being dragged — and is drawn on demand rather than kept on every block at opacity 0: a column of grips beside every paragraph is the noise this reading surface refuses everywhere else, a screen reader would hear *Block actions* and a block's first words before every paragraph, and a book would carry a button per block. Hovered it fills with `--rail-active`, and while its menu is open it keeps that fill with the glyph in `--ink`. Its name is *Block actions: {name}* (*區塊動作：{name}*), the name `blockName` gives (*Moving blocks*, below) — *Block actions: “An attention function…”*, *區塊動作：公式 (1)* — with `aria-haspopup="menu"` and `aria-expanded`. It is `tabindex="-1"`: each block stays one tab stop — the block itself — and the keyboard opens the same menu with ⌘/ (*Keyboard block selection*). **Pressing it reaches nothing else.** Its `pointerdown`, `mousedown` and `mouseup` stop at it, so neither the block's press handler nor the pane's `mouseup` (`onBlockClick`) sees them, and no editor opens under a menu. Its default is never prevented, because a prevented press starts no native drag and the handle is `draggable`; so the press may take focus. The viewer notes a press on any of its controls among the blocks (`data-chrome`: the handle, the chevron, the fold note, a backlink marker) on `pointerdown`, before the blur it causes — Safari focuses no button on a click, so the blur's `relatedTarget` cannot be trusted — and an open editor's blur that follows such a press is not a leave, so nothing is written back or re-rendered under the press. The control's own action writes the editor back when it runs: the handle's click (`commitEdit`, then the menu) or its `dragstart`, and the chevron's, the fold note's or the marker's click. The blocks an open editor holds get one handle, beside the editor's first line; pressing it writes the editor back (`commitEdit`) and acts on the blocks the text became, found again by their source near where the editor was, as a click is (indices move on a commit). On a touch screen (`hover: none`) that is how a handle is reached: a tap opens the block's editor, and focus within it shows the handle. A heading's handle sits beyond its collapse chevron (*Outline, collapse and the way back*). On a phone (under 640px) the document's side padding on Files is `--space-8` rather than `--space-5`, the room a handle and a backlink marker need; a 20px gutter would push both off the pane.

**A click opens the block menu**; a press that drags moves the block instead (*Moving blocks*). The menu is `UiContextMenu`, named *Block actions* (*區塊動作*), beside the handle — to its right, top-aligned with the block, flipped up where there is no room below — with its first item highlighted when the keyboard opened it (`focusFirst`). While it is open the block takes the selection's wash and is the selection, without the hint bar, so it is plain what the menu acts on; the handle of a block already in a selection opens the menu for the whole selection, any other handle for its own block alone. A faint header names what it acts on — the block's kind, *Paragraph*, *Heading*, *Formula*, *List*, *Table*, *Code*, *Figure*, *Quote*, *Contents* (*段落*, *標題*, *公式*, *清單*, *表格*, *程式碼*, *圖*, *引用*, *目錄*), or *3 blocks* (*3 個區塊*) for a selection — and the items follow in four groups under rules:

1. **Ask the agent** (`message-circle`), labelled by what it asks about: *Ask the agent about this paragraph* (*問 Agent 這一段*), *about this section* for a heading (*問 Agent 這一節*), *about this formula* (*問 Agent 這個公式*), *about this block* for a list, a table, code, a figure, a quote or a contents run (*問 Agent 這一塊*), *about these blocks* for a selection (*問 Agent 這些區塊*). A heading adds its section as a section chip, exactly as *Add context* adds one (`ask({section})`, its text from `sectionSource`); anything else, a selection holding headings included, puts the blocks' markdown in the composer as the selection (`ask({selection})`). Nothing is sent: the agent column opens if it was closed and the composer takes focus, because the question is the reader's to write — unless a turn is running, when focus stays on the block (§ The agent panel, *Asked from the document*).
2. **Translate** (`languages`), labelled the same way (*Translate this paragraph*, *this section*, *this block*, *these blocks*; *翻譯這一段*, *翻譯這一節*, *翻譯這一塊*, *翻譯這些區塊*), with `/translate` in mono where a shortcut sits: the same request with `command: 'translate'` and `send: true` — sent at once only when nothing is running and the composer holds nothing else, otherwise left ready in the composer (§ The agent panel, *Asked from the document*). Offered only where `/translate` has something to translate: a paragraph, a heading, a list, a quote, a figure with a caption, or a selection holding one of them — never on a formula, code, a table, a contents run or a figure without a caption, which the translator leaves as they are ([chat.md](./chat.md) § Translation), since the item would start a paid turn that writes nothing. And shown only while the viewer's skills list (`listSkills()` filtered on `user_invocable`, read when the copy becomes editable and again as each block or slash menu opens) holds a `translate`; hidden while it loads and when there is none, since a command that may not exist is not offered. A menu shows the list as it was last read: a read that answers while a menu is open changes the next one, never the open one, for the reason the header's More waits for the facts (§ Result viewer) — a menu that grew under the pointer would no longer fit where it was placed.
3. **Quote in notes** (`notebook-pen`, *引用到筆記*): the blocks' source as an excerpt (§ Notes, *Excerpts*).
4. **See the excerpt in notes** (`quote`, *看筆記裡的摘錄*), only in a block's own menu and only when the block carries a backlink marker: what the marker does (§ Notes, *Backlink markers*), here for the keyboard and the screen reader, which the marker — no tab stop — leaves without a route.
5. **Copy as Markdown** (`copy`, *複製為 Markdown*, ⌘⇧C): the blocks' source joined by blank lines — a figure's placeholder and caption included — to the clipboard as text, confirmed with *Copied*.
6. **Copy link to block** (`link`, *複製區塊連結*): a reference to the block, never a bare address. The block's name as its handle names it (*“Routers, firewalls and load balancers…”*, *Formula (3)*, *Figure “…”*) linking to `/files?document=<id>&block=<anchor>` on the app's own origin and in the current locale (§ Files, *A block can be linked to*), written to the clipboard as markdown (`[“…”](https://…)`) and as HTML, so pasted into a markdown file it is a citation and pasted into a rich text field a link labelled with the words; pasted into this document's notes it becomes a chip that locates the block (§ Notes, *Quotes and section links*). For a selection, the reference of its first block. Confirmed with *Link copied*.
7. **Turn into…** (`repeat`, *轉換成…*) with a chevron, opening a submenu (*Turning a block into another*, below).
8. **Move up** (`arrow-up`, *上移*, ⌘⇧↑) and **Move down** (`arrow-down`, *下移*, ⌘⇧↓), disabled at the document's first or last visible block.
9. **Collapse section** / **Expand section** (`chevron-down` / `chevron-right`, the chevron's own glyph for the state it changes; *收合這一節* / *展開這一節*), on a heading only.
10. **Delete** (`trash`, *刪除*), in the danger colour: removes the blocks. A collapsed heading is deleted alone — its section expands first — so nothing out of sight is removed.

Ask and Translate are the first group; the items that lead to the notes or the clipboard the second; Turn into, the moves and Collapse the third; and Delete stands alone under the last rule.

**A collapsed section is its heading, except to a move.** In a selection, a collapsed heading's row stands for the heading alone for every action but a move: *Copy as Markdown*, ⌘C, *Quote in notes*, *Ask*, *Translate* and *Turn into* take the heading line, as a copy across a fold copies what is visible. A move — the menu's, ⌘⇧↑ or ⌘⇧↓, a drag — carries the whole section, since what the reader sees as one row moves as one, and *Delete* expands the section and removes the heading alone, so nothing out of sight is removed. On its own, a collapsed heading is asked about and translated as its whole section, by the section chip items 1 and 2 add for any heading.

**Focus after the block menu.** When the menu closes, chosen from or not, focus goes to the first of the blocks it acted on, found again by their source: after *Delete* the block now in their place, as the Delete key leaves it (*Keyboard block selection*); after a move or *Turn into* the moved or converted blocks; after *Collapse* or *Expand* the heading. The exceptions are the actions that move focus themselves — *Ask*, to the composer (§ The agent panel, *Asked from the document*), and *See the excerpt in notes* chosen from the keyboard, to the notes. A menu opened from the keyboard, or over a selection the keyboard made, leaves those blocks selected, with the hint bar; one the pointer opened on a lone block leaves it focused and nothing selected, the selection having been only the menu's. `UiContextMenu`'s own restore is not enough here: what had focus when the handle was pressed is often the editor that opening the menu wrote back, or the notes or the composer, where the ⌘Z the status note offers would undo something else.

**Every action that changes the document takes the path every edit takes**: `commitEdit()` first, the blocks found again by their source, the document rewritten through the parse and `serializeDocument` so everything else keeps its bytes, then saved — so the 409 and the agent's reload treat a block action as any other edit, with one difference: **a block action is saved at once**, not after the typing debounce. It is one deliberate change rather than a run of keystrokes, and the less time it waits, the less room an agent writing the document meanwhile — a translation writes for minutes — has to turn it into a 409. A save that meets one drops it with the notice that the document changed underneath, as unsaved typing is dropped, and its undo goes with it (*Undo and the status note*); the reader sees the document as it now is and can make the move again. **A reload closes what was open over the blocks** — the block menu and its submenu, the selection toolbar and its skill list, a drag in the air — since the blocks they named may have moved, and keeps a block selection only where every one of its blocks is found again by its source.

#### Turning a block into another

*Turn into…* opens a submenu of **Paragraph** (*段落*), **Heading** (*大標題*, `##`), **Subheading** (*小標題*, `###`), **Bulleted list** (*項目清單*, `-`), **Numbered list** (*編號清單*, `1.`), **Quote** (*引用*, `>`), **Display formula** (*公式區塊*, `$$`) and **Code** (*程式碼*, ```` ``` ````), each with its markdown in mono where a shortcut sits and the block's current kind checked — a `#` heading checks *Heading*, and a selection checks a kind only when every block in it has that kind. The text kinds — paragraph, heading, list, quote, formula, code — can be turned; on a figure, a table or a contents run the item is disabled, since none of them has one text to carry over. A selection turns each block it can and leaves the rest as they are.

**A conversion is a pure function over a block's source** (`convertBlock(src, to)` in `app/lib/richdoc.ts`), built through the same parser and serializer as editing, so what it writes reads back as exactly the block it meant:

- Paragraph, heading and subheading turn into one another keeping their inline text — emphasis, formulas and all.
- A paragraph or a heading becomes a one-item list; a list becomes one paragraph (or heading) per item; a bulleted list turned numbered counts from 1, and a numbered one turned bulleted drops its numbers.
- *Quote* wraps the block's source in `> ` lines. A quote turned into a paragraph is unwrapped, its inner blocks becoming blocks again; turned into a heading or a list it is unwrapped and each inner block turned as a selection's would be.
- A paragraph whose whole text is one inline formula becomes that formula as a display block; any other text becomes a display formula whose TeX is the text as written (a list's items one per line, code's text as it stands).
- *Code* takes the block's markdown source as its text verbatim — a formula's `$$` and a quote's `>` included — because code is where markdown is shown rather than read.
- A formula or a code block turned into a paragraph becomes literal text, escaped so it reads back as the same characters — except that a formula keeps its `$…$`, and so stays a formula, inline, its lines joined by spaces since an inline formula cannot break a line. Turned into a heading or a list it goes through that paragraph first.

Only the converted block is rewritten, in canonical form; the rest of the file keeps its bytes, and a conversion to the kind a block already is writes nothing.

#### Moving blocks

**A move is a pure splice** (`moveBlocks(markdown, run, to)` in `app/lib/markdown.ts`: parse, splice, `serializeDocument`): a contiguous run of blocks goes before or after another block, and everything not moved keeps its bytes. **Moves cross page markers**: pages are the pipeline's fact, not the reader's, and ordering the document is the reader's. The markers stay where they were — a page a move empties keeps its marker and draws nothing, as any emptied page does (§ Editing) — and what a block still needs its page for travels with it: a figure keeps its own (§ Result viewer). **A move steps over one visible item.** A comment travels with the block before it, so it is never stranded and never counted as a step (one at the head of a page, with no block before it there, stays put); a collapsed section is one item, so *Move down* steps past the whole fold — into the section, which runs to the next heading of its level, so the section expands as the block lands (*Outline, collapse and the way back*); and moving a collapsed heading moves its whole section, because what the reader sees as one row moves as one — an expanded heading moves alone, being one row. After a move from the keyboard the moved blocks stay selected and in view, and every move says *Moved* (*Undo and the status note*).

**Drag to reorder.** The handle is `draggable`; dragging it moves its block, or the whole selection when its block is in one.

- **What is dragged.** The drag image is a small card rather than the browser's screenshot of the block: the grip glyph and the block's first line, one line with an ellipsis, at most 280px, on `--paper` with an `--edge` hairline, `--radius` and the menu's shadow. In the air the moving blocks stay in place at opacity 0.4, so the reader still sees what they picked up.
- **Where it lands.** A **drop line** marks it: a 2px `--accent` line in the gap between two blocks, across the column, with an 8px ring (a 2px accent border on `--paper`) at its left end. Before or after is the pointer against the hovered block's vertical middle, and a collapsed section is one row here too. A drop inside the moving run, or where it would move nothing, draws no line and does nothing. The pane scrolls by itself while the pointer is near its top or bottom edge.
- **What a screen reader hears.** A polite live region names the target as it changes — *Moving: drop after {name}* (*搬移中：放到{name}之後*), so *Moving: drop after “3.2 Attention”* (*搬移中：放到「3.2 Attention」之後*) — by `blockName` (`app/lib/blocks.ts`), the one naming the handle uses too. It returns one of two things: a bare label for a block named by its kind — a formula as *Formula (1)* (*公式 (1)*) by its `\tag` and *Formula* (*公式*) without one — or a block's words in the locale's quotation marks from the catalog (“…” in en, 「…」 in zh-TW), the ellipsis inside the marks when the words are cut: a heading's text, anything else's first words, and a figure's caption's first words after *Figure* (*圖*). The templates take the name as it comes and add no marks of their own.
- **What it carries.** `dragstart` writes an open editor back first, so no editable surface is under the drag and the run is the document as it stands. As on Files, `dragover` decides (`app/lib/dnd.ts`, a `block` claim; no `dragleave`). The drag carries a custom type with the run and the blocks' markdown as `text/plain`, so dropped on another text field — the composer, the notes — it inserts the markdown, as a copy and paste would. The notes column is not a special target (quoting is the menu's job), and the agent panel's drop zone, which answers to files only, stays down. An answer block dragged from the agent panel carries the same type with no run, and one of its own: the document takes it as a copy on the drop line, never as a move (§ The agent panel).
- **Ending it.** Escape, or a drop outside the document, cancels. A copy's drop line whose drag ended out of the viewer's sight — its source gone from the page first, as an answer's block is when the answer is stored — goes at the next pointer move. Touch screens do not drag: *Move up* and *Move down* in the menu are the single-pointer alternative a dragging movement needs (WCAG 2.5.7).

#### Keyboard block selection

Blocks can be selected as whole blocks — the run a move, a delete, a copy or a question acts on — from the keyboard, or by opening a block's menu. A selection is always one contiguous run of visible items, a collapsed section being one, and may cross page markers as moves do.

- **Entering.** Escape in an open block editor closes it, as before, and selects the blocks it held — the blocks its text became — with focus on the first. A block focused with Tab becomes a selection of one at its first arrow key, which selects it rather than moving past it, so the reader sees where they are before anything moves, or at a block shortcut, which then acts on it. Opening a block's menu with the pointer selects that block while the menu is open, without the hint bar.
- **The look.** Selected blocks take `--block-selected` with `--radius`, drawn as a layer behind the block reaching 4px past it above and below and 6px to each side — the located heading's technique (a `::before` on the block), so the text does not move. The focused block also has the focus ring when focus came from the keyboard.
- **Keys**, with focus on a selected block and no editor open. ↑ and ↓ select the previous or next visible block. ⇧↑ and ⇧↓ extend or shrink the selection from its anchor. ⌘⇧↑ and ⌘⇧↓ move the selection one visible item (*Moving blocks*). ⌘/ — and Shift+F10 and the ContextMenu key, the library's menu keys — opens the block menu for the selection at the focused block's handle. Enter opens the focused block's editor with the caret at its end. Delete or Backspace deletes the selection, and focus moves to the block now standing in its place (the one before it, at the document's end), selected as one so the keyboard keeps a place — or to *Add text*, when no block is left. ⌘⇧C copies the selection as markdown, and so does ⌘C — the plain key for a browser that keeps ⌘⇧C for its developer tools. ⌘Z and ⇧⌘Z undo and redo block actions. Escape clears the selection and stops there rather than closing the dialog; with nothing selected, Escape closes the dialog as before. A click anywhere else clears it. Escape thus steps out one layer at a time — editor, selection, dialog — and each layer's handler stops the key, since the modal's own Escape listens on `document`.
- **The hint bar.** While a selection made from the keyboard exists, a bar at the bottom center of the pane — the menu surface, `--radius-menu`, `--text-xs` in `--faint`, each key a `Kbd` — reads *↑↓ Select · ⇧↑↓ Extend · ⌘⇧↑↓ Move · ⌘/ Menu · Esc Cancel* (*選擇 · 擴大選取 · 搬移 · 選單 · 取消* after the same keys), and a polite live region says *3 blocks selected.* (*已選取 3 個區塊。*) as the count changes. It is a legend, not a control: it takes no pointer focus from the document, hides with the selection, and wraps on a narrow screen. A selection made by the pointer has no hint bar — that reader has the menu.

#### Undo and the status note

**Block actions have an undo of their own.** Move, delete, turn into, drag and *Quote in notes* happen outside any editor, so no editor's history holds them. The viewer keeps its own: ⌘Z (Ctrl+Z) while no editor is open and focus is in the document pane undoes the last block action — the file it changed, the document or the notes, put back as it was before it and saved like any edit — and ⇧⌘Z (Ctrl+Shift+Z, Ctrl+Y) redoes it. Undo and redo select what they put back in the document and scroll it into view, since an undone move can land off screen; a step on the notes scrolls the notes to it and washes it instead. **A step undoes only while its file is exactly what the action left.** A change to a file that is not itself a block action — typing in a block or in the notes, an agent's edit, a reload — clears every step on that file, undo and redo alike, because putting text back over a change the stack never saw would silently undo that change too; a stale step is removed, never skipped. Steps on the other file stay, still in order: a move in the document can be undone after the reader has typed in the notes, an excerpt quoted before that typing cannot. Each step keeps its file, the span the action changed — where it starts, the text it removed, the text it put there; a move is two — and a hash of the text it left, which is what *exactly* is checked against, so the stack holds spans rather than copies of a book that may be 8 MiB (`app/lib/blocks.ts`). A document step starts from the file as `serializeDocument` writes it, which the action writes anyway: on a copy spaced otherwise its first action rewrites the layout of the whole file, and a span over that would put back, select and scroll to every block; from the rewritten text, the span is the action's own blocks. At most 50 steps, far past any run a reader takes back, per open document, gone when the viewer closes.

**The status note.** An action with nothing else to show confirms in one short line at the foot of the pane — the hint bar's surface, centered, `--text-sm` in `--ink` — for about 1.6 s, in a polite live region: *Copied* (*已複製*), *Link copied* (*已複製連結*), *Moved* (*已搬移*), *3 blocks deleted · Undo (⌘Z)* (*已刪除 3 個區塊 · 復原 (⌘Z)*) with *Undo* a text button, *Already in notes* (*筆記裡已有這段摘錄*), and *Undone* / *Redone* (*已復原* / *已重做*). A copy the browser refuses — the clipboard write rejected — says *Couldn't copy* (*無法複製*), never *Copied*. **A note that carries *Undo* stays until the reader's next action, or for 8 s**, and the pointer resting on it holds it longer: on a touch screen it is the only way back, with no ⌘Z and no hover, and 1.6 s is too short to reach it after a delete. Every counted string has its plural forms in the en catalog — *1 block deleted · Undo (⌘Z)*, *1 block selected.*, *1 block collapsed* — and one form in zh-TW. A plain Ctrl+C of a text selection stays silent, as copying is everywhere; the note is for the copies that otherwise show nothing — a block's and the toolbar's. It stacks above the hint bar and the return pill, never over them (*Outline, collapse and the way back*).

#### The selection toolbar

**A text selection gets a toolbar.** A non-collapsed selection in the document pane — over rendered blocks, or inside the open block editor, which is where a drag usually ends up (*Selecting is editing*) — shows a toolbar over its first line, centered on it, flipped below the selection when it would leave the pane's top: a glass capsule with 4px of padding (§ Design system), its buttons 32px capsules in `--text-sm`, an icon and a word each, a hovered button on `--fill`. Its buttons are **Ask the agent** (*問 Agent*, `message-circle`), **Quote in notes** (*引用到筆記*, `notebook-pen`), **Copy** (*複製*, `copy`), a rule, and **Skills** (`square-slash`, with its word — a list of skills is named as one, never hidden behind an ellipsis), which opens a list of the user-invocable skills under the toolbar, named *Run a skill on the selection* (*對選取執行 Skill*): each row the skill's glyph, its name in mono and its description as in the slash menu, each sent with the selection and its command (`ask({selection, command, send: true})`). The name is never cut for the description: it keeps its width, up to most of the row, and the description takes what is left, ending in an ellipsis. There is no Translate button: `translate` is one of the skills, listed only when the selection touches a block it translates (*The block handle and its menu*, item 2). Skills is shown only when there is a skill to list.

- **It stays inside the pane.** Centered on the selection's first line, it is shifted to stay `--space-2` inside the pane's edges; where it is still wider than the pane, as on a phone in English or on a narrower one in Chinese, its buttons drop their words, which stay their names, as the viewer's header does under 640px. On a coarse pointer it sits under the selection instead, the side the platform's own selection callout leaves free.

- **When it shows.** On the pointer's release, never during a drag — a toolbar chasing a selection that is still being made is in the way of the drag making it — and once a keyboard selection has stopped changing for about 300 ms, so it does not flicker under each Shift+arrow. It follows the selection as the pane scrolls, and hides when the selection collapses, the editor closes, or the selection leaves the pane. It is drawn in the pane over the document, never inside the scroller, whose `mouseup` would otherwise take a press on it for a press on a block.
- **It keeps the selection.** Pressing a button does not move focus (`mousedown` is prevented, as on the agent panel's reply toolbar), so an open editor stays open until the action itself closes it or moves focus — an ask writes it back first and, unless a turn is running, moves focus to the composer (§ The agent panel, *Asked from the document*). The buttons are not tab stops: the toolbar is a pointer surface, and the keyboard reaches the same actions on whole blocks through the block menu and copies any passage with ⌘C. A passage smaller than a block has no keyboard route to *Ask*, a skill or *Quote in notes* in this release; the cost is stated rather than hidden.
- **What it reads is markdown.** Inside the editor the selection's markdown is the editor's own clipboard serializer over its selection (`selectedMarkdown()`, which `RichEditor` exposes: `sliceToMarkdown` over its own selection); over rendered blocks it is the fragment walk Ctrl+C makes, factored out of `onCopy` into one function both use (`selectionMarkdown`). *Ask the agent* puts it in the composer as the selection chip; a skill sends it with its command (`ask({selection, command, send: true})`, once the save has answered, § The agent panel, *Asked from the document*); *Quote in notes* writes an open editor back first and makes it an excerpt in the section the selection starts in, as the document then has it — a heading renamed in the draft is named as renamed — with focus on the first block the editor became, where ⌘Z takes the excerpt back (§ Notes); *Copy* writes it to the clipboard and says *Copied*.
- **The skill list is part of the toolbar.** It is drawn under the toolbar's right edge, 300px wide or the pane's width where that is narrower, shifted to stay `--space-2` inside the pane and flipped above the toolbar where the pane has no room below, and like the toolbar's buttons it takes no focus (`mousedown` is prevented): the selection and an open editor stay exactly as they were while it is open, and the toolbar stays with them. A second press on Skills closes it, and so does anything that hides the toolbar. The passage a skill is sent is read at the moment its row is pressed, as the other buttons read theirs.

#### The slash menu

**Typing `/` in an empty paragraph at the top level of an open block editor** — not in a list item, a table cell or a quote — opens a menu under the slash, and so does a full-width `／` an input method commits there, which a reader writing Chinese may type in its place. It is the menu surface, 300px wide or the editor's width where that is narrower (`min(300px, 100%)`, as the TeX field is held), at most about 432px high with its own scroll, flipped above the line where the pane has no room below — standing on its bottom edge there, so a filter that shortens it keeps it against the line. It is a child of the editor's root, as the TeX field is, so focus never leaves the editor and the block stays open: a `listbox` named *Slash commands* (*斜線指令*), with a group for each header, whose highlighted row the editor names as its active descendant, as the composer does for its command menu. **What follows the slash filters it**: the conversions by prefix over keywords in English and Chinese alike, whatever the interface language (`/標` finds the headings, `/引` and `/quote` the quote; the keywords are matching data in `app/lib/slash.ts`, the labels come from the catalog), the skills by `matchCommands` (`/tr` finds `translate`). **The filter is read only outside a composition.** Chinese is typed through an input method, and a keyword like 標 arrives only when it is committed — the keys before it (`ㄅㄧㄠ`, `biao`) match nothing — so while a composition runs the menu keeps the rows of the last committed filter, and neither closes nor picks; the committed text then filters it. ↑ and ↓ move, the first row highlighted since the menu opened from the keyboard; Enter or Tab applies; Escape closes it — only it, the editor stays open — and leaves the typed text; Backspace past the slash, or a click elsewhere, closes it; a committed filter that matches nothing closes it, and only a newly typed slash opens it again. It has no footer of key hints: the keys are the ones every menu answers to.

- **Turn this block into** (*轉換這一塊*): Paragraph (`type`), Heading `##` (`heading-2`), Subheading `###` (`heading-3`), Bulleted list `-` (`list`), Numbered list `1.` (`list-ordered`), Quote `>` (`text-quote`), Display formula `$$` (`sigma`), Code ```` ``` ```` (`code`), Table (`table`) and, where images can be inserted (*Images*, below), Image (`image`), each its glyph, its label and its markdown in mono where a shortcut sits. Applying removes the typed `/query` and turns the empty paragraph into that block with the caret in it: a display formula opens its TeX field, and a table is three columns with a header row and one body row, the caret in the first header cell; Image opens the file picker, and the paragraph becomes the image once it has uploaded.
- **Skills · Run on this block** (*Skills · 對這一塊執行*): the user-invocable skills, fetched as the menu opens and *Loading…* until they arrive, as in the composer's command menu — each its glyph, its name in mono after a slash, as the composer's command menu draws it (`/translate`), and its description. The glyph is the action's own where the viewer has one — `languages` for `translate`, as on every other surface, `square-function` for `fix-math`, `image` for `check-figures` — and the composer's command glyph, `square-slash`, for any other skill. Applying removes the `/query`, writes the editor back, and asks the agent with that command and the editor's text — its markdown, the emptied slash line gone — as the selection (`ask({selection, command, send: true})`), opening the agent column; it goes once the save has answered, under the rules every sending ask follows (§ The agent panel, *Asked from the document*). Only in the document's block editor, and only when the editor holds text besides the slash line: there is nothing to run a skill on otherwise. `translate` is listed only when that text holds something it translates (*The block handle and its menu*, item 2).

Anywhere else — a code block, a heading, a paragraph with text in it, the TeX field — `/` is just a character. The notes editor has the same menu with the conversions only (§ Notes).


#### Images

**A picture goes into the document or the notes three ways**, all on Files (History has no document to hold one): the slash menu's *Image* row (`/image`, `/圖片`), which opens the file picker; a paste of image files — a screenshot copied to the clipboard — into an open editor; and image files dropped on the rendered document, on the drop line a dragged block draws (*Moving blocks*), or on the notes, between their blocks. A paste that also carries text is the text's: a spreadsheet or a word processor puts a picture of what it copied on the clipboard beside the text, and the text is what was meant.

- **Each file is uploaded first** (`POST /api/library/images`, [api.md](./api.md)) — PNG, JPEG, WebP, GIF or HEIC, at most `limits.image_max_bytes`, checked in the browser before it is sent — and lands as one block per file, `![name](figures/img-<hash>.png)`, its name the file's without the extension. While it uploads the editor says *Uploading image…* (*正在上傳圖片…*) in a polite live region; a refusal is said on the status note (*Undo and the status note*): the server's message, or *The image is larger than {size}* (*圖片超過 {size}*) for a file the browser already knows is too large.
- **An image lands where it was put, whatever moved while it uploaded.** Its place is held by the blocks around it — the one it follows and the one it precedes, by their markdown, the nearest of several alike, compared without the spacing at their ends — and found again once the file is in: a drop's line is read after an open draft is written back, which may make that draft more blocks or fewer (a draft emptied away leaves the line where the block was, on its page), and the reader may edit while the files upload, or the notes reload under their editor (an excerpt quoted, the agent's write). A place at a page's edge stays on that page: before a page's first block is not after the last block of the page before. An image whose editor closes before it has uploaded — the reader moved to another block, or closed the notes — still lands, in the document or the notes, where it was to go — by the blocks around it in the editor, or around the editor in the document when it held no other — as its own block action. In the document it waits while anything holds blocks by their place — another block's editor, a handle's menu, a drag, the selection toolbar — and lands once none does, after whatever closed the last of them has acted: landing writes the document, which would close the editor the reader is typing in, and moves every block after it down a place. A block that held focus keeps it, found again by its markdown. In the notes it goes in between their blocks, the rest of the text kept as written. One still uploading when the viewer closes or turns to another document is not added, and the files after it are not sent; one already uploaded and waiting lands as the viewer closes. Where neither neighbour is left it goes at the end.
- **The block editor stays open across the picker.** The file chooser takes focus from the page, which would otherwise read as the reader leaving the block: until the picker answers — a file, or cancelled — a blur is not a leave, and focus comes back to the editor after it.
- **In an editor an image is one atom** — the image and its caption drawn as the document draws them, the caret stepping over it and Backspace deleting it whole, its markdown kept byte for byte — as a figure dropped into the notes is. Its caption is edited in the document, where a click on it opens the caption's editor as a figure's does.
- **The text never fetches.** The image's address is the document's route, built by the viewer from the name the line carries; nothing in the markdown is ever used as a URL.

### Notes

A card at the document's left, toggled by the header's Notes button (whether it is open is remembered in the browser, `localStorage`, across every document you then open and across visits), holding the document's `notes.md`, edited in place exactly as the document is (§ Editing) — the same rich editor, the same typed markdown shortcuts, the same formula field, the same slash menu with its conversions and *Image* only (the notes have no agent to ask about themselves from there), and the same rule that only changed blocks are rewritten — except that the whole file is one editor, always open, since notes are short and written rather than read. An empty file shows a faint placeholder line. Saved with the same debounce and `base_revision` rule through `PUT …/notes`; a reload of the notes (another tab, the agent) replaces the editor's content only while nothing in it is unsaved. The card's head is its name, *Notes*, and a button that closes it; under that, no toolbar — the rest of the card is the notes.

**The side columns keep a hierarchy of their own.** The document draws two heading sizes, which is right at reading size and flat in a 320px column: there a `#` title, a `##` section and a `###` subsection came out within a pixel of each other, each with the same gap around it as a list item. So the notes and the agent's answers (the `md-side` class in `app/assets/css/markdown.css`, on the notes editor and on each answer) draw three levels: a `#` heading is the column's title, in the display face at `--display-sm`; a `##` heading opens a section — the UI face at `--text-base`, semibold, under a hairline rule (`--line`) with `--space-4` above the text, except as the first block, where a rule would only underline the column's top edge; a `###` heading or deeper is a label in the UI face at `--text-sm`, semibold, `--ink-soft`. List items sit `--space-1` apart rather than `--space-2`, so the gaps between sections are what read as structure. Only the side columns: the document keeps its two sizes, and a copy still hands each heading back at its source depth.

**Excerpts.** *Quote in notes* — on the selection toolbar or a block's menu (§ Editing) — appends the passage to the notes as an **excerpt**: a blockquote of the passage, every line prefixed `> ` and blank lines `>`, then a paragraph that is only a section link to the section the passage is in — its heading's text and slug, the shape answers use:

```
> We suspect that for large values of $d_k$, the dot products grow large in magnitude, …

[3.2.1 Scaled Dot-Product Attention](#321-scaled-dot-product-attention)
```

- **Where it goes.** At the end of the notes' **Excerpts** section — a `##` heading reading *Excerpts* or *摘錄*, in either language whatever the interface's, case and spacing ignored, ending at the next heading of the same or a higher level. Without one, the section is made at the end of the notes in the reader's language (`## Excerpts` / `## 摘錄`). A reader's excerpts gather in one place they can find and move as a whole, and a heading in the other language is still theirs, so a reader who switches language does not grow a second section.
- **What is quoted.** The passage's markdown: a selection's, or a block's source from the menu. A passage before the first heading has no section: its link reads *Beginning of the document* (*文件開頭*) with the bare anchor `#` (`[Beginning of the document](#)`), which locate reads as the whole document. Every quote within the passage is unwrapped first and every figure in it is given as its caption, a figure with none left out, so the excerpt stays one level and holds only text: a `>` inside it would read as text, and a figure's placeholder inside a quote as a line of literal placeholder (§ Result viewer). A passage that is only such a figure has nothing to quote, and *Quote in notes* is disabled.
- **Never twice.** An excerpt whose passage is already in the notes is not added again: a blockquote anywhere there whose whole text equals the passage, compared as locate compares — equal, not containing it, so one sentence of a paragraph quoted whole can still be quoted on its own, and the section is not compared. The existing one is scrolled to and washed instead, as a new one would be, and the status note says *Already in notes*.
- **Then the notes show it.** The notes column opens if it was closed, scrolls the excerpt into view and washes it once (700 ms, the located heading's wash, drawn as an editor decoration rather than written into the text). The notes are saved like any notes edit, and the append is a block action the viewer's undo takes back (§ Editing, *Undo and the status note*). It is appended to the notes' text, which the open notes editor takes as a reload of its source kept out of its own history (`addToHistory: false`; the steps before it map away across the replaced text), so its caret and its undo start over, and an excerpt has one undo, the viewer's, rather than two that disagree about it. The reader is in the document at that moment, not in the notes.

All of it — the excerpt's markdown, where it goes, the duplicate check — is pure, in `app/lib/excerpts.ts` (`excerptMarkdown`, `appendExcerpt`).

**Quotes and section links in the notes.** The notes editor's schema has the document's quote (§ Result viewer): a blockquote node holding blocks, one level, started by `> ` at a line's start and lifted out by Backspace at its start, drawn as a 2px `--edge` bar on the left with a `--space-3` inset at the column's text size. And a **section link** anywhere in the notes — under an excerpt or not — is drawn as the answers' chip (§ The agent panel, *Section links*): the locate glyph and the heading on the rail surface, pressed (`--rail-active`, `--ink`) while the document shows what it located. In the editor it is one inline atom (`sectionLink`) that keeps its markdown source byte for byte: the caret steps over it and Backspace deletes it whole, since half a link is neither a link nor the text it was. `richdoc.ts` reads section links for the notes only (`parseInline` with `cites`); in the document a link stays the text it was — answers and notes are where links are read. **An excerpt's link stays a chip while its passage or its heading can be found.** An excerpt's link is a section link right after a quote, and the passage is the excerpt's own anchor — the heading only says where the search starts — so renaming a heading (an OCR slip fixed in *3.2.1 Scaled Dot-Product Atention*) leaves every excerpt under it working, as the markers leading the other way keep working. Only when neither can be found is it drawn as the heading's plain text, the same atom, and a click on it does nothing; the matcher that draws the markers says which (`matchExcerpts`). A section link with no quote before it follows the answers' rule, plain text once its heading is gone, and the *Beginning of the document* link (`#`) always resolves. An excerpt's link paragraph sits `--space-1` under its quote with its chip's glyph aligned to the quote's text, so the two read as one excerpt rather than a quote and a stray link. A click on a chip **locates**, and so does Enter with the chip selected, as Enter on a selected formula opens its field. **A block reference is a chip too.** *Copy link to block* (§ Editing) pasted into the notes — the markdown link to this document's `/files?document=<id>&block=<anchor>` — is rewritten as the editor reads it to `[name](#anchor)`, the anchor as the address carried it, so the notes keep a reference and not an address. It is drawn as a chip while the anchor still resolves (§ Files, *A block can be linked to*), and a click on it reveals the block as opening the link does: near the pane's top, washed, its fold opened, the way back set. A link to another document stays the text it was.

**A block dragged into the notes lands as blocks.** The handle's drag (§ Editing, *Moving blocks*), or an answer block's (§ The agent panel), dropped on the notes inserts the blocks' markdown as whole blocks — rendered, between the notes' blocks, before or after the block under the pointer by its vertical middle, at the end of empty notes — never into the middle of a paragraph, where dropped text would land as text. A figure arrives whole — its placeholder and caption, drawn in the notes as its crop from the document's figure route — and so does an inserted image; a page marker does not arrive at all. An excerpt still takes a figure as its caption: a quote holds only text. The document keeps its block: a drop on the notes is a copy, and the notes are saved like any notes edit.

**The notes' blocks have handles, and move by them.** Only the notes card asks for this (`RichEditor`'s `blocks`); the Agent section's instructions and check editors, the same editor, stay as they were. The card's left padding is `--space-8` (32px) rather than `--space-5`, a gutter for the document's handle (§ Editing, *The block handle and its menu*) drawn as an answer's is (§ The agent panel): the six-dot grip in `--faint`, 20×24, 4px from the text and level with the unit's first line, filled with `--fill` when hovered and while its menu is open, its glyph inked then.

- **What moves is a unit**: a top-level block — a paragraph, a heading, a whole list, a quote, a table, a formula, code, a figure or an image — except that **an excerpt is one unit**: a quote right before a paragraph that is only a section link, the pairing `matchExcerpts` reads (*Excerpts*), has one handle and always moves, copies and is deleted whole, so a passage never parts from its link. An empty line and a comment have no handle, having nothing to carry. The units, the gap a drop lands in, the moves and the unit selection are pure over the editor's document (`app/lib/note-blocks.ts`).
- **One handle at a time**, on the unit the pointer is over or level with — in the gutter, or in the gap under a unit, that unit stays, so the pointer on its way to the handle keeps it — and on the unit whose handle is pressed, whose menu is open, that is selected or that is being dragged. A change to the text hides it until the pointer moves again. On a touch screen (`hover: none`) it is on the caret's unit while focus is in the notes. It is a `div` with `role="button"`, draggable, `tabindex="-1"`, named *Block actions: {name}* (*區塊動作：{name}*) by `blockName` — an excerpt by its quote — with `aria-haspopup="menu"` and `aria-expanded`.
- **The drag** carries a type of its own (`application/x-sightread-notes-block`) and no `text/plain`, so the copy a document or answer block makes when it is dropped on the notes (above) is untouched and nothing else takes it — the document, the composer and other text fields ignore it. Its picture is the document's drag card, and in the air the unit stays in place at opacity 0.4. The document's drop line — the 2px `--accent` line with its 8px ring — marks the gap it lands in, before or after the unit under the pointer by its vertical middle, midway between two units; the gaps either side of the unit itself would move nothing, so they draw no line and a drop there does nothing. A polite live region names the target as the document's does (*Moving: drop after {name}*). Escape cancels.
- **A move** is one editor transaction — the unit deleted, then inserted at the gap — and one step of the notes editor's own history, so ⌘Z in the notes takes it back; it is saved as any notes edit is, on the debounce with `base_revision`. Focus returns to the notes with the caret at the start of the moved unit, and the status note says *Moved* (§ Editing, *Undo and the status note*), without an *Undo*, which belongs to the viewer's own stack. Two lists that become neighbours stay two in the editor and may read back as one list on the next load, as markdown reads them; the move is still one undo.
- **The menu.** A click on the handle opens `UiContextMenu` beside it, named *Block actions*, its header the unit's kind as the document's menu names it (*Paragraph*, *Heading*, *List*, *Quote*, …) or *Excerpt* (*摘錄*); while it is open the unit takes the selection's look. Its items: **Locate in document** (`locate`, *在文件中顯示*), on an excerpt only, doing what a click on its chip does — disabled while the link is drawn as plain text; then **Move up** and **Move down** (*上移*, *下移*, ⌘⇧↑, ⌘⇧↓), one unit each, disabled at the first and the last; **Copy as Markdown** (*複製為 Markdown*), the unit's source, confirmed with *Copied* in the status note (*Couldn't copy* when the clipboard refuses); and **Delete** (*刪除*) in the danger colour, alone under the last rule, which the status note says as *1 block deleted*. There is no *Turn into*: the slash menu's conversions turn an empty paragraph, not a block with text in it, and a second set of conversion rules for the notes is not worth having. When the menu closes on a choice or Escape, focus returns to the notes with the caret in the unit acted on — after a delete, the unit now in its place — or, when the keyboard opened it, with that unit selected; a press elsewhere or Tab leaves focus where it went.
- **The keyboard.** Escape with a text caret in the notes selects the caret's unit whole, where it is, scrolling nothing — the unit is on screen already: drawn as the document's selection, `--block-selected` on a layer `--space-1` past it above and below and `--space-2` to each side, with `--radius`, the browser's own highlight hidden. With a unit selected, ⌘⇧↑ and ⌘⇧↓ move it one unit and keep it selected; ⌘/, Shift+F10 and the ContextMenu key open its menu with the first item highlighted; Delete or Backspace deletes it and selects the unit now in its place; Enter puts the caret at its end, and ⇧↵ and ⌘↵, a line break elsewhere, do nothing; ⌘C copies it as markdown; an arrow key leaves it for the text beside it; typing does nothing to it — except through an input method, whose composition the browser starts before the editor can hold it back, so it replaces the unit as it would any selection, and ⌘Z puts the unit back. Escape again leaves the notes as Escape did before, and focus leaving the notes puts the caret back at the unit's start. ⌘⇧↑ and ⌘⇧↓ are never taken from a text caret, where macOS selects to the start or the end of the text.
- **Unchanged.** Excerpts appended and washed, `focusBlock` and every route into the notes address top-level blocks, which units only group. Section-link chips, block-reference paste, drops from the document and the answers, a reload of the notes while nothing in them is unsaved — which closes an open menu and ends a drag, as the document's reload does — image slots and backlink markers work as they did.

**Locate.** Clicking an excerpt's link scrolls the document to the passage and washes the passage's own text for 700 ms, then lets it fade over `--duration-slow` where the browser animates a highlight's colour (elsewhere the wash simply ends): the find highlight's accent wash (`--find`), painted through the CSS Custom Highlight API under its own name (`sightread-locate`) and never by rewriting the DOM, for the reason find never does (§ Result viewer). The passage is the quote right before the link, found by its text — markdown removed, formulas compared by their TeX, spacing ignored (`findPassage` in `app/lib/excerpts.ts`) — within the linked section first, then anywhere, over the same text walk find makes but with each formula read as its TeX. A passage no longer there leads to its heading, washed like a located heading; with neither there, the chip is plain text already (above). An open block editor is written back first, so the passage is looked for in the rendered blocks, where each formula carries its TeX — an editor's formula views carry none. A link with no quote before it locates its heading, as an answer's does. A collapsed section holding the target expands first, and the jump sets the way back (§ Result viewer, *Outline, collapse and the way back*). A browser without the Highlight API washes the passage's block instead, as a located heading is washed.

**Backlink markers.** A document block holding a passage quoted in the notes gets a small marker beside its last line, in the right gutter: 24×24, the `quote` glyph at 14px in `--faint`, filled with `--rail-active` and inked when hovered, named *See the excerpt in notes* (*看筆記裡的摘錄*). A passage that runs over several blocks is marked on the block it ends in, and a passage the document holds twice is marked once, on the block locate lands on — the first match in the linked section — so a marker and a locate never disagree. Clicking the marker opens the notes column if it was closed, scrolls the notes to that excerpt and washes it once, leaving focus where it was; a block quoted by several excerpts leads to the first, and each further click to the next. The marker is `tabindex="-1"`, like the handle, since one tab stop per block leaves no room for a gutter button: the keyboard's and the screen reader's route is the block menu's *See the excerpt in notes* (§ Editing). Chosen from the keyboard, it moves focus into the notes editor at the start of the excerpt, so what was reached is read out; chosen with the pointer, it does what the marker does. **Markers are computed, never stored**: a pure matcher over the notes and the document (`matchExcerpts` in `app/lib/excerpts.ts`, the comparison locate makes) feeds the viewer, which draws them as `data-chrome` siblings of the block's rendering. Nothing is written into `doc.md` — the file the agent and the translators edit — and copy, find and the agent's `selection` never see them. A marker leads into the notes, not around the document, so it sets no way back.

### Column widths

The notes and agent cards open at 320px and 360px and are **resized by dragging the grip on their inner edge** — the notes card's right, the agent card's left: a 5×40px pill in the 16px gap between the card and the document, the whole gap the hit area, a column-resize cursor, the pill darkening and growing to 56px while hovered, dragged or focused. The grip is also a focusable `separator` (with `aria-valuenow`): ArrowLeft and ArrowRight move the edge by 16px, with Shift by 64px; a double-click returns the card to its default. Widths are clamped — notes 240–560px, agent 300–640px — and the document pane keeps at least 360px, so a card dragged past that stops rather than squeezing the document out. Like the cards being open, the widths are remembered in the browser — saved when the reader drags, steps or resets a grip, never when the window clamps a card, so a visit on a narrow window does not shrink the width chosen on a wide one. Below 900px the cards stack under the document, full width, and the grips are not drawn.

### The agent panel

A card at the document's right, toggled by the header's Agent button (remembered like the notes), is the `chat` agent's thread about this document ([chat.md](./chat.md)). At its top a conversation title with a chevron opens the document's conversation list and *New conversation*; beside it a *New conversation* button and one that closes the card. The head is the card's heading, the thread scrolling under it. A conversation opened with a turn still queued or running is followed from the start (`expectTurn` on load, with that turn's id), so a stream dropped before its `turn_start` arrives is reopened rather than left showing *working* until the panel is reopened; the stream knows the turn it waits for by id, so the terminal events of earlier turns it replays from 0 do not end the wait, which would leave a drop before the live turn's `turn_start` read as idleness. The thread renders `messages` plus the live `chat_events` stream: the user's turns right-aligned in an accent bubble with white text, exactly as typed (line breaks kept, nothing interpreted — as in Claude's own chat); the assistant's text as markdown through the viewer's own parser and `MdBlock`, so `$G_t$`, a `$$` display formula, a list, a table or `**bold**` reads as it would in the document rather than as its source; its tool calls, and the notes between them (`thinking` events), as **steps**. The run of steps between two texts of an answer is one **step group**, shown as a one-line summary of what it did, counted by kind — *Read 5 times · searched once · edited 7 times* — with a chevron that opens it; while its turn is live the group is open — the trailing one, and any with a call still running beside a later item — and its summary is the step in flight (*Editing the document · step 9*, with a spinner), and a message that ran a command opens its answer's first group with a *Use skill NAME* step. A step is one line — a glyph for its kind, a verb, its target in mono and a detail — read off the call by the client, never the raw tool name or a command's boilerplate (`app/lib/steps.ts`): a shell command loses a leading `cd "<path>" &&` or `;` and is read by its first program — `sed -n A,Bp FILE`, `head`, `tail` and `cat` as *Read FILE · lines A–B*, `grep` and `rg` as *Search PATTERN · FILE*, `ls` and `find` as *List*, `wc` as *Count*, anything else as *Run* with the program named; the editor's `view` is *Read*, `str_replace` and `insert` *Edit*, `create` *Create*, each with the file's name, and a write with the lines its diff added (`+N`, in the accent). The workspace's file names are the agent's business, not the reader's: the document's own `doc.md` and `notes.md` are named for what they are — *document* and *notes* (*文件*, *筆記*), in the body font rather than mono — in a step's target, its *in …* detail, the live summary and a diff card's footer; any other file keeps its name; `view_page` is *View page N*, `view_figure` *View figure · page N*, `skill` *Use skill NAME*. A finished step carries a check (accent) or a cross (danger), a running one a spinner. Opening a step shows its detail on the sunken surface: for a shell step the whole command with a copy control, the output (the tool result's text, scrolling past a few lines) and its exit; for a write the diff card — removed lines on the danger wash, added lines on the accent wash, wrapped rather than scrolled sideways, each line as tall as its wrapped text (the lines stack as blocks in the card's scrolling box, so a wrapped line is never squeezed to one row and drawn over the next) — whose footer says *Applied* with a **Revert** text button (`POST …/revisions/{commit}/revert`; after it, *Reverted* and **Apply again**; both wait while a turn is running, since the route refuses a revert under an unfinished turn; the card's state — reverted or not, and the commits that undo and redo it — is kept per tool call for as long as the page is open, so switching conversations and back finds the card as it was left rather than offering to revert the original commit a second time). Edits are undone one at a time, from each edit's own diff card; a finished answer carries no summary of its edits and no turn-wide revert. A `subagent` call is a **subagent card** rather than a step — the card's border, the subagent's name in mono, its task, then how many steps it has taken, how long it has run (live, counted from when the panel first saw it start, since events carry no time; once stored, the record's `elapsed_ms`) and what it does now (live) or what it reported (done); it starts closed, running or not — a turn of thirteen translators is thirteen lines, not thirteen step lists — and a click opens its own steps — from the `parent` events while it runs, from the result's `subagent` record once stored — and the report it returned. A step of a subagent that wrote opens like a step of a group: its diff card with **Revert**, or a shell step's command and output. The last answer of a finished turn has a copy control under it, which copies its markdown. The composer is one rounded field (18px radius, the one rounded control in the app besides the context menu) holding, top to bottom, what goes with the message — the reply's quote as a chip (*Reply* and the passage, cut to one line, with a remove control), then the attachments as thumbnails and file chips, each with a remove control, a progress meter while it uploads and the reason in the danger hue when it was refused — then a two-row textarea, and a foot of the attach and command controls at the left and a round accent send button at the right. **Attachments**: the attach control opens the file picker (`limits.attachment_extensions`, several at once); files **dropped anywhere on the panel** are attached the same way — while something is dragged over it the panel shows a drop zone, a dashed accent outline over the whole column saying *Drop to attach* with the accepted kinds and the size cap — and so is a pasted image. Each file is checked against `limits.attachment_max_bytes` and `limits.attachments_per_message`, then uploads at once (`POST /api/attachments`, its progress from the request's upload events), a refused one staying as a chip with the reason until removed; Send waits for the uploads in flight and is sent with `attachments`. While a send is posting, its attachments' remove controls are disabled, since the server is claiming them. A panel that closes deletes its unsent attachments, but not those of a send already posted: that send keeps them, and deletes them only if it is refused; a send still waiting for its uploads is dropped with the draft. In the thread a message's attachments sit above its bubble: images as square thumbnails (`GET …/attachments/{index}`), files as chips naming the file. **Reply**: selecting text inside an answer shows a small floating toolbar over the selection — **Reply** and **Copy** — the context menu's opaque surface and shadow in a capsule's shape, a hovered button on `--fill`; *Reply* puts the passage in the composer as the quote — as the answer's markdown, so a formula stays `$…$` rather than the rendered glyphs — and focuses the textarea, and the message is sent with `quote`; in the thread the quote sits above the reader's bubble, muted, after a reply glyph, cut to one line. **Commands**: `/` typed at the start of an empty composer, or the command control, opens a menu over the field — the context menu's surface, its first row highlighted since it opened from the keyboard — of the skills that can be run as commands (`user_invocable`: the name in mono, the description, the argument hint) and, under *Conversation*, `/new`; typing filters it, ↑ and ↓ move, Enter or Tab picks, Escape closes, and an input method's composition never picks. The list is fetched each time the menu opens, and the latest fetch is the one shown. Until the first has come back the menu says *Loading…*; while any is in flight Enter and Tab pick only a skill already listed, and otherwise wait for the answer, so a command typed meanwhile is neither sent as text nor answered by `/new`. A picked skill becomes a mono chip at the start of the field with its description beside it, the textarea taking its arguments with the argument hint as placeholder; Backspace in an empty textarea removes the chip. The message is sent with `command`; in the thread it is the chip followed by the arguments. `/new` starts a new conversation. **Enter sends and Shift+Enter starts a new line**, as in Claude's own chat; Ctrl/Cmd+Enter sends too. An Enter that confirms an input method's composition (Chinese, Japanese) only confirms it — a key event with `isComposing` set, or the legacy `keyCode` 229, never sends. Sending posts the message (`POST /api/conversations/{id}/messages`), appends it locally and opens the SSE stream from the last seen `seq` — for the conversation the message was sent to: a reader who switched threads while the send was in flight finds it in the thread it belongs to, not the one now open, and the composer is cleared all the same, since the text and selection were accepted there and are no draft of the thread now open; a turn error renders in the thread as a red line, and the composer is disabled while a turn is running except for **Stop** (`cancel`). The selection, when there is one in the document at send time, goes with the message as `selection`: it is read on the pointer's way into the composer (before the click collapses it) and on keyboard focus — but not on a press or a focus that starts inside the composer itself (Send, a chip, the textarea again), which would otherwise read a collapsed selection and drop the passage just as the message goes out, and each reading replaces the last — a reading that finds no selection clears the one before, so a passage the reader selected, then deselected, is never sent as context; the focus that follows a pointer capture is skipped, since by then the click has collapsed what the pointer already read. What is read is the passage's text, a line per block and a tab between a table's cells, with each formula as its TeX source (`$…$`, from the `data-tex` copy reads too), never the glyphs KaTeX drew and the MathML it hides beside them, which would reach the model as a column of single letters — nor the viewer's own controls drawn among the blocks (`data-chrome`) or a block a collapsed section hides. The panel subscribes with `useConversationStream` (`app/composables/useConversationStream.ts`), which owns reconnects and the `after` cursor.

**Context chips.** What goes with the message besides its text is a row of chips at the top of the field, above the quote and the attachments, under a group label for screen readers (*This message's context*): first a **+** control (*Add context*), then a faint, fixed **This document** chip — the conversation is about it, and the chip carries nothing of its own — then the selection, when one was read, as a chip with the passage's first words cut to one line and a remove control (the reading rule above is unchanged; the chip now shows what will go instead of a character count), then each **section** the reader added, as *3.2 Attention (whole section)* after the heading glyph (*H*), with a remove control. *Add context* opens a menu above the **+** control, held to the room there — a long outline scrolls inside it rather than covering the control and the draft: *Current section* (the section the document is scrolled to) and then the document's headings, each adding its section — sent as `sections`, its markdown from the heading to the next heading of the same or a higher level, or `null` text when that is past `limits.selection_max_chars` ([chat.md](./chat.md) § What a user message carries). A heading too long for its row or chip is cut with an ellipsis, its full text the tooltip; one longer than `limits.section_heading_max_chars` is clipped to it before it is sent, so a paragraph a parse mis-tagged as a heading cannot get the whole message refused. At most `limits.sections_per_message`: the headings are disabled at the cap, and a section already added is checked rather than added twice. In the thread, a sent message's selection and sections sit under its bubble as the same chips, without remove controls.

**Asked from the document.** The reader's view puts things in the composer through one call, the panel's `ask` (`AskRequest`: `selection`, `section`, `command`, `send`), which a block's menu, the selection toolbar, an outline row's actions and the slash menu make (§ Editing, § Result viewer): a passage becomes the selection chip, a section a section chip exactly as *Add context* adds one, a command the command chip as if picked from the menu, and focus goes to the textarea (below). The viewer opens the column first when it is closed, and asks once the panel has mounted. A passage asked for this way is markdown — a block's source or the selection's markdown, formulas as `$…$` — not the plain reading the composer makes of a selection on its own (above): the reader chose blocks, and the agent should see them as the document has them. A command sent with a passage or sections runs on them alone, whatever its own text says of an empty range ([chat.md](./chat.md) § Skills, *A command keeps to what it was sent with*), so an action labelled *this block* never starts a run over every page.

- **A sending ask sends only what it just put there.** With `send`, the message goes at once only when nothing is running and the composer holds nothing besides what the ask put there: no draft, no command, and no selection, section, quote or attachment from before. A command must act on what the reader just pointed at, never on a chip left over from earlier — a section added with *Add context* or a selection left there would be translated beside the section an outline row's *Translate this section* asked for, each a piece of its own ([chat.md](./chat.md) § Translation, *Range*). Otherwise what was asked joins what is there and everything waits for Send, where the reader can see it; a draft is never sent for the reader.
- **An ask that sends waits for the save.** Before it posts, the viewer writes an open editor back and flushes the pending saves of the document and the notes, and it sends once both have answered: the turn context then names the revision the reader sees, and the passage the agent is sent is in the file it reads. Otherwise a paragraph typed and run through the slash menu's `/translate` at once would anchor the translator on words not yet saved, and the reader's save, landing after the agent's write, would meet a 409. A save that fails or meets a 409 leaves the ask in the composer unsent, under the save's own banner; a message the server refuses leaves it there too, under the composer's error, and it waits there like any ask that does not go, with focus (*Where focus goes*). An ask that does not send writes an open editor back first too, so a section's text is read from what the reader sees — an outline row's ask finds its heading again where the written-back draft leaves it.
- **Where focus goes.** An ask that waits in the composer gives it focus; one that goes at once leaves focus in the document where the reader was — on the block, for the block menu, and on the first block an open editor became when the ask wrote it back — since there is nothing left to type and the textarea is disabled while the turn runs. For the same reason, **while a turn runs an ask still lands but takes no focus**: its chips are set and the column opens, focus stays in the document as it does for an ask that goes at once, and a sending ask waits for Send.
- **A passage too long to send is shown, not sent.** A selection chip past `limits.selection_max_chars`, asked for or read, says so in the danger hue, as a refused attachment does, and Send stays disabled until it is removed; a sending ask waits rather than go out to be refused with a 400. It is never cut, since a cut passage would pass for the whole one. A long run is better asked about by its sections, which go without their text past the cap.
- **A section the composer cannot take is never dropped silently.** With `limits.sections_per_message` sections already in the composer, an asked section not among them is not added and the ask does not send; the status note says *At most 4 sections per message* (*每則訊息最多 4 節*), the number being the limit's.
- **A passage asked for stays.** It stays until the reader removes it, sends it, or comes back to the composer with a passage selected in the document, which replaces it; a reading that finds no selection does not clear it — that rule is for a selection the reader made and then let go of, and this one was chosen by blocks. The focus `ask` hands the composer is not read as the reader arriving either, so the selection it has just set is not replaced by a reading of the document's.

**Section links.** An answer's link to a section (`[3.2 Attention](#32-attention)`, [chat.md](./chat.md) § System prompt) is drawn as a small chip in the text — a locate glyph and the heading, on the rail surface — and a click scrolls the document to that heading, expanding a collapsed section that holds it, and flashes its block with the accent wash for 700 ms — a background only, no outline or shadow: motion is on color and background alone (§ Design system). The chip stays pressed (`--rail-active`, `--ink`) while the heading is washed, so the eye can go back and forth between the two, and the jump sets the way back (§ Result viewer, *Outline, collapse and the way back*). The heading is matched by its text, markdown removed and spacing and case ignored, else by the anchor (a GitHub-style slug of each heading), the first match in document order; a link whose heading the document no longer has reads as the heading's plain text. Only links whose target is `#anchor` or `doc.md#anchor` are read this way, and only in answers and in the notes (§ Notes, where an excerpt's link also finds its passage): everything else stays the text it was (§ Result viewer, *Inline markdown*). Copying or replying to an answer keeps the link's markdown.

**An answer is blocks, each with a handle.** An answer is the document's blocks (the viewer's parser and `MdBlock`, above), and every block but a comment carries the document's handle (§ Editing, *The block handle and its menu*): the same six-dot grip, in the thread's 20px left gutter, 20×24 there, with `data-chrome` so a copy or a reply's selection passes over it. As in the document it is drawn only where it can be used now — on the block the pointer is over or level with (in the gutter, or in the gap under it, the last block stays, so the pointer on its way to a handle keeps it), the block last tapped on a touch screen, the block holding keyboard focus, the block whose menu is open and the block being dragged — never kept on every block. A pressed handle stays until the press ends: a drag starts only once the pointer has moved, often off the block by then, and a handle already gone starts none. Its name is *Answer block: {name}* (*回答區塊：{name}*), by `blockName`. It is a tab stop while drawn, so from a link in a block Tab reaches its handle and Enter opens the menu; the window losing focus keeps it, so focus comes back to it. Its press stops at it, so it starts no selection and no reply toolbar. A live answer's blocks have handles too: a drag takes the block as it reads at that moment, and the menu's choice the block as it reads when chosen — when the answer is stored under it, the menu closes.

- **A drag is a copy.** The handle is `draggable`; the drag carries the document's block type (`BLOCK_DRAG_TYPE`, with no run of the document's), a type of its own (`ANSWER_DRAG_TYPE`) — so the document never takes one of its own drags, cut short by a reload, for an answer's — and the block's markdown as `text/plain`, under the same small card as the document's (§ Editing, *Moving blocks*). Dropped on the notes it lands as blocks, as a document block does (§ Notes); dropped on the rendered document it lands on the drop line, as dropped image files do (§ Editing, *Images*) — one block action the viewer's undo takes back, the status note saying *Block added* (*已加入區塊*); dropped on the composer or any other text field it inserts the markdown. The answer keeps its block.
- **Its menu.** A click on the handle opens *Add to notes* — the block appended at the end of the notes as blocks, the notes opened on it and washed, a block action the viewer's undo takes back — and *Copy* — the block's markdown. The menu is the single-pointer alternative to the drag (WCAG 2.5.7). While it is open the thread stops following a live answer under it, since the scroll would close it, and follows again from its end once it closes. A press on the handle whose menu is open closes it, and does not open it again; a press on another block's handle opens that block's menu. Closing gives focus back to the handle, which stays drawn to take it — unless a press elsewhere closed the menu.

**Credits.** Under a finished turn's last answer, beside *Used*, the turn's credits (`turns[].credits`, the entry's amount; nothing while it is null, which it is until the record is read again after the turn ends) as *12 credits* in the accent, since it is a cost figure (§ Design system). A send refused with 402 opens `CreditsDialog` (§ Files) rather than an error line: the minimum a turn needs, what is left and the reset date, with *See plans*. A turn that ends `out_of_credits` says so in words (*The credits ran out during this turn*) instead of the backend's token, since the token is a contract, not a sentence ([billing.md](./billing.md) § A chat turn).

**A send that would be refused is said before it is made.** When the balance is under the minimum a send needs (`credits_remaining` below `chat_min_credits`, `GET /api/me`) or the workspace is at its storage (`workspace.bytes` at or past `workspace.quota_bytes`, `GET /api/sandbox`, read when the panel opens, when the window regains focus and after each turn ends, as the balance is — a period may reset or files go while the panel stands), a notice stands above the composer — *No credits left this period*, or *Your storage is full* with what is used of what — with **See plans** (the pricing page, `/pricing`), and the composer's Send is disabled while it stands; the reader can still type, and the draft waits. The server's own refusals stay the authority (402 above, **409** `storage_full`, which opens the same notice rather than an error line): the notice only saves the reader a send that could not run.

**A failed turn is said in the reader's words.** The `turn_error`'s `error` is the backend's, in English and written for the log; the thread never shows it bare. `turnErrorKey` (`app/lib/turnError.ts`) maps the ones the worker writes — `out_of_credits`, `storage_full`, `model_unpriced`, the timeout, the upstream's exhausted credits and rate limit, an answer cut at the output limit, a declined request, too many tool calls, a history past its cap, a document or parse gone, a worker restart, an internal error, a deployment without its upstream — to one catalog line each, saying what happened and what to do next (*This conversation is too long to continue. Start a new one about this document.*); anything else reads *This turn did not finish. Try sending it again.* The backend's text stays in the line's tooltip for a bug report. `storage_full` and `out_of_credits` also carry **See plans** — except while the notice above stands for the same cause, which already carries it: **one cause, one See plans**. The line still says what happened to that turn; the notice says what to do. A turn that ran out of credits mid-way usually ends `succeeded` (it finishes within its bound, [billing.md](./billing.md) § A chat turn), so the notice alone says it.

**What the answer used, and memory lines.** Under a finished answer, beside its copy control, one muted line says what the turn was given beyond the document — *Used: your instructions · 3 memories*, from its `turn_start` event; nothing when it was given neither, and nothing for a turn from before `turn_start` carried `instructions` and `memory_ids`, whose absence reads as nothing used — each part a text button opening a small floating card on the context menu's surface: the instructions as they are now, or the memories the turn loaded (one since deleted says so), each with its kind, and a link to the Agent page. A `memory` call is not a step: each is a quiet line under the answer with a memory glyph — *Saved to memory: Term · query → 查詢*, *Memory updated: …*, *Removed from memory: …* — and its text buttons, whose writes are the memories routes ([chat.md](./chat.md) § Memory). A memory's text, in the line, its card and on the Agent page, renders its inline markdown and `$…$` math as an answer does. A line is in one of these states:

- **Saved**: **View** (the card, for that memory) and **Undo**. After this line's own Undo it reads *Undone, this term won't be remembered*, with **Save again**.
- **No longer in memory**: the row is gone without this line's Undo — deleted on the Agent page, cleared, or forgotten by a later turn — so the line says so, neutrally, and offers **Save again** only while no identical memory exists.
- **Updated**: **View** and **Undo**, which puts the memory back as it was — *Undone, this term is back as it was* — with **Apply again**.
- **Forgotten**: **Undo**, which saves it again — *Undone, this term stays in memory* — with **Remove again**.

Which state a line is in is derived from the memories as they are (`GET /api/memories`, fetched when the panel opens, when a `memory` event arrives, after each Undo and after a memory is changed in the settings dialog open over the panel), the saved row found by the call's `tool_use_id` (`source_ref`) and an updated one by its id, so a reload or another tab shows what is true rather than what was clicked; a live `memory` event is applied to that list as it arrives, before the list reloads, so the line never reads the list from before its own call.

The thread is the record plus the stream. A turn is live while the record's `finished_at` is null, whatever its status (a cancelled turn still winding down is live). For a live tool-using turn whose earlier rounds are already stored, the panel draws the stored rounds and then the stream past the last tool call the record holds — the results and the rounds that followed — so a panel opened mid-turn shows what is happening now, not only what has been stored. Every `edit` frame reloads the open document, replayed ones included: the content was fetched on its own, and the stream's order says nothing about whether an edit came before or after that fetch. A send invalidates a record reload still in flight (a terminal event's, a dropped stream's): the record it fetched predates the message just accepted, and would replace the message and its queued turn with a thread that lacks them; the new turn's own terminal event reloads the record again. **The thread follows a live turn only from its end**: while the reader is scrolled to the bottom, what arrives keeps the last line in view; scrolled up — a wheel turned up stops it at once, before the scroll lands — or having opened a step or a group that runs past the bottom, or any card, the thread stays where it is until the reader scrolls back to the end (closing a card settles it again). A card follows its control as the thread moves under it, and closes when that control leaves the thread's view, on Escape, on a press outside it or when focus leaves it. Sending a message and opening a conversation go to the end.

Both cards live inside the dialog beside the document pane, inset `--space-4` from the window's edges under the header, and never float over the document: they take their width from the pane, and closing either gives it back, the document re-centring in what is left. Scrollbars are hidden on all three regions (they still scroll); the document column keeps its 70 % measure of whatever width remains.

## Rules

- Auth state via `GET /api/me`; unauthenticated → sign-in page; signed-in on `/` → `/files` (locale-aware, client-side). Login is a plain link to `/api/auth/login` (server redirect flow, no client OAuth).
- The web app calls only `/api/*`, plus the one full-page navigation of the server redirect flow (`/api/auth/login`). Session cookie, `credentials: include`, custom `X-Requested-With` header on mutations (CSRF pairing with SameSite=Lax).
- Frontend renders only what the backend returns — empty states are real states, never fabricated sample data.
- Uploads never pass through a Nuxt route. `/files` posts its multipart body to `/api/library/documents`, which Caddy sends to FastAPI like every other `/api/*` request; there is no server route, no Nitro handler and no Node buffer in the path. The one local-development caveat is the dev proxy rather than an exception to that: `nuxt dev` pipes `/api` to `localhost:8000` so the session cookie stays same-origin, and it streams the body through without touching it. The conversation stream ([chat.md](./chat.md)) takes exactly these two paths: `EventSource` opens the relative `/api/conversations/{id}/events` URL, which Caddy routes to FastAPI in production and the dev proxy pipes through in development, with no Nitro handler or Node buffer on either; a separate API origin for the stream would put the session cookie cross-origin, which is the one thing the same-origin split exists to avoid. `curl` and connector instructions still live on `/keys` and `/connect` — the library is for reading a document, not for learning the API.
- Every control has a visible focus ring: a 2px accent outline at 2px offset, never removed, never replaced per component.
- **A tab left open across a deploy moves to the new build by itself.** The authed pages are client-rendered and long-lived — `/files` is a tab people keep for days — so without this a release changes nothing for them until they happen to reload, and a fix to the viewer looks like it never shipped. The app compares its own build id with `/_nuxt/builds/latest.json` (Nuxt's app manifest; nothing new is served) whenever the tab becomes visible, and also listens to Nuxt's own periodic check. Once a newer build exists the page reloads at the first moment that costs nothing: immediately if the page is idle, on the next route navigation (as a full load of the target), or when the page's last *hold* is released. A hold is how a page says "not now": `/files` holds while its upload queue is non-empty, while a name is being edited and while the result viewer is open, and `/history` while the result viewer or the Add to Files picker is open, because a reload would drop files still waiting to upload, lose the reader's place, or close a dialog mid-choice. A failed check is silence, never an error — the next one will do (`app/lib/build-update.ts`, `app/plugins/build-update.client.ts`).
- The browser tab title is the site name (`app.name`) on every page, set once in `app.vue` — authed pages do not set per-page titles, so the tab reads "Ema Paper" across tab switches. The public pages override it with their SEO titles.
- i18n: every user-visible string goes through the catalog; en and zh-TW ship together. Locale switching lives on the sign-in footer and, once signed in, behind the account menu's Language row (§ The account menu) — real links, since the locale lives in the URL. A locale's own name comes from the i18n config; its name in the language being read comes from the catalog (`language.<code>`), so adding a locale means adding that line to every catalog. The sign-in link passes the locale to `/api/auth/login`, which returns the visitor to the same one ([auth.md](./auth.md) § 1).
