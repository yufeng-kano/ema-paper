# Sandbox — one VM per user

The chat agent's `bash` tool runs inside a microVM that belongs to the user: `/workspace` is their workspace directory ([workspace.md](./workspace.md)), nothing of the service is reachable from inside, and the VM is stopped when idle and started again on the next command. Files survive; shell state and installed packages survive too — only `reset` discards them.

## The runner

A separate service, `apps/sandbox` (`sightread-sandbox` in compose), is the only container with the Docker socket. The API and the worker never talk to Docker; they call the runner over HTTP on the compose network with a shared token (`SANDBOX_TOKEN`). The runner starts one container per user from the sandbox image under the configured runtime and keeps shell sessions open inside it.

| Route | What it does |
|-------|--------------|
| `GET /sandboxes/{user_id}` | `{state: stopped\|starting\|running, last_used_at, shells, uptime_seconds}`; **503** when Docker cannot say (the daemon away, an inspection that timed out) — never `stopped` for a VM nothing could start, which the API shows as `unavailable` |
| `POST /sandboxes/{user_id}/exec` | `{session, command, timeout_seconds}` → `{output, exit_code, timed_out, truncated}`. Starts the VM when stopped. The session names a persistent shell — a **supervisor** process in the VM that owns the command's lifecycle, since a command that shared the supervisor's stdin could read the framing that follows it and forge the status line: the host sends each command framed by a per-command random marker; the supervisor reads it whole, runs it in a fresh `bash` as a child, with its stdin at `/dev/null` and the session's saved working directory and exported environment restored; the child `wait`s for its background jobs and saves the working directory and exported variables back (so `cd` and `export` carry from one command to the next, which is what the bash tool's contract expects; shell functions and unexported variables do not); and only once the child is gone does the supervisor run the cleanup and print the status line. The command never sees the marker and cannot end its own framing early. Whatever the command started that is still running then — a disowned job, a server, a process that left the shell's session with `setsid` — is killed before the status line: every process in the VM but pid 1, the live shells and the exec wrappers they hang from — the shells named by the runner, which sends the pids of the user's live supervisors with every command (each supervisor reported its own pid on its stdout before any command ran in it), never by anything in the VM a command could write, so a command cannot forge a shell for a process to hide behind; the sweep is repeated until a pass finds nothing left to kill (a process forking while the list is walked has children the snapshot missed, reparented to pid 1 once their parent is gone, which the next pass takes), and a VM that is not clean after fifty passes fails closed — the supervisor exits without its status line, the runner's kill inside the VM sweeps again and, failing too, stops the VM; the same sweep follows a timeout's kill and precedes an adoption. So nothing a command started writes the tree after the command's revision, and there is no way to keep a process running between commands. |
| `POST /sandboxes/{user_id}/restart` | `{session}` — kill that shell and open a fresh one (the bash tool's `restart`; the worker's cleanup of a turn a dead worker left). The command inside the VM goes first, by the supervisor's pid the runner holds, as on a timeout, then the host-side client: closing the client alone ends nothing inside. An `exec` whose request is dropped mid-command (the worker died) kills its command the same way, and so does one whose supervisor ends without a status line (a command that killed it): the in-VM kill and sweep run before the lost status is reported, and a VM where they cannot be confirmed is stopped. The fallback stop reuses the sandbox lock `restart` already holds rather than taking it again |
| `POST /sandboxes/{user_id}/stop` | stop the VM, keep everything on disk. A shell running a command is killed inside the VM first, by the pid the runner holds, before the VM is removed — so a removal that then fails leaves no command still writing behind a client already closed; idle shells are simply closed. **503** when Docker could not remove it (`SANDBOX_DOCKER_TIMEOUT_SECONDS`, 120, is how long the removal may take) and does not report it gone: the sandbox is then marked unstoppable and takes no command until it is. The same mark can be set under a running `exec` — a timed-out command whose kill failed and whose VM Docker could not remove — and that `exec` does not answer with its outcome: it waits the removal timeout for Docker to report the VM gone, and answers **503** otherwise, so the worker never commits a tree a surviving process may still write ([chat.md](./chat.md) § Tools). The api gives these control calls `SANDBOX_CONTROL_TIMEOUT_SECONDS` (180), which must cover the removal, the inspection after it and a reset's cache deletion, so a slow but healthy stop is not reported as a failure |
| `POST /sandboxes/{user_id}/reset` | stop, and delete the package cache and shell state under `/workspace/.cache`; documents are untouched. A deletion that fails or leaves anything behind answers **503**, never a done the next VM would belie. Held under the user's sandbox lock from the stop through the deletion, so no command starts into a cache being removed; a stop that fails (**503**, as above) deletes nothing, since a VM still alive could be writing into it; whatever sits at `.cache` goes — a directory, or the file or link a command put there in its place, removed without following it — so the next start can make the directory again |

Output is captured as combined stdout and stderr in fixed-size reads (never line by line, so one newline-free value of any length is cut like any other flood), kept at `SANDBOX_OUTPUT_MAX_BYTES` with the head and the tail, so a command that prints a file cannot flood the conversation. A command past `timeout_seconds` is killed *inside the VM* — the supervisor reports its pid on its stdout when it opens, and the runner kills that process, everything under it and everything in its process group through a second `docker exec`, since ending the host-side client does not end what runs in the container — then the host-side session is closed and the timeout reported; the next command of that session opens a fresh shell. When that kill cannot be confirmed — the kill fails, the `docker exec` hangs — the runner stops the VM instead, so no command outlives its timeout and goes on writing the workspace after the host has moved on; and a VM that cannot be stopped either — the removal fails or times out, and an inspection does not report it absent or stopped; the same check every stop makes, `stop`, `reset` and the idle sweep included, since closing the host-side clients confirms nothing about what runs inside — takes no further commands until Docker positively reports it gone — an inspection that fails (the daemon away) is not "gone", it is unknown, and unknown keeps the sandbox closed. `SANDBOX_COMMAND_TIMEOUT_MAX` (600) is the ceiling on what a caller may ask for.

Two backends implement the same interface: `docker` (production: `docker run` with `--runtime {SANDBOX_RUNTIME}`, the user directory bind-mounted at `/workspace`, `--network {SANDBOX_NETWORK}`, cpu/memory/pids limits, a read-only root filesystem and a tmpfs `/tmp`) and `local` (tests only: a bash process in a temporary directory, no isolation — never deployed).

## Isolation

- **Runtime:** Kata Containers (`SANDBOX_RUNTIME=kata`) — every container is its own KVM microVM with its own kernel; Cloud Hypervisor is Kata's default hypervisor, Firecracker is the alternative. The host needs `/dev/kvm` and the Kata runtime installed ([deployment.md](./deployment.md)). `runc` works for local development and gives no VM boundary; in production the runner accepts only a runtime named in `SANDBOX_VM_RUNTIMES` (the Kata names, by default) and refuses to start otherwise — any other OCI runtime would be a shared kernel under a VM's name.
- **Network:** `SANDBOX_NETWORK=none` by default, and the chat agent's prompt says so — the worker reads the same setting and `SANDBOX_INDEX_URL` with it, so the model is never told `uv add` works where no route or no index exists ([chat.md](./chat.md) § System prompt). Package installs need one egress: deploy a PyPI-only proxy on an internal compose network, point `SANDBOX_NETWORK` at that network and `SANDBOX_INDEX_URL` at the proxy; the proxy allows GET to the index and wheel hosts and nothing else — it must not become a channel out of the VM.
- **No secrets in the VM.** The upstream key, the database and the API are unreachable from inside; the agent's model calls are made by the worker on the host, never from the VM.
- **Resource limits:** `SANDBOX_CPUS`, `SANDBOX_MEMORY`, `SANDBOX_PIDS`, `SANDBOX_TMP_SIZE` (the VM's writable `/tmp`, a tmpfs of 1g by default, counted against the memory limit), per-command timeout, output cap. Shells per user are capped by the runner at `SANDBOX_MAX_SHELLS` (8): a conversation holds one shell, and when a new conversation needs one past the cap the shell that has been idle longest is killed to make room — inside the VM first, like `restart`, so its supervisor does not linger as a live shell the sweep preserves until the pid limit is reached (its conversation gets a fresh shell on its next command). A shell running a command is never evicted; if every one is busy the command is refused.
- **The document is in the VM; the original is not.** A prompt injection in a parsed PDF can at worst make the agent act on that user's own files, which revisions undo; it cannot reach another user's directory or the service. The original upload — the one file no revision can bring back — lives beside the git directory, outside the mount; the `source.*` in the document directory is a copy the host makes again when it is missing ([workspace.md](./workspace.md) § Layout).

## Lifecycle

- **Start on first use.** The first `exec` of a user whose VM is stopped boots it (Kata boots in about a second; the UI shows a starting state meanwhile).
- **Stop when idle.** `SANDBOX_IDLE_SECONDS` after the last command the runner stops the VM; a VM with a command still running is never idle, whatever the clock says — decided twice, once to pick candidates and again under the user's lock, so a command that started in between keeps its VM. Nothing is deleted, ever, by the runner.
- **A restarted runner adopts what is running.** At start the docker backend lists the `sightread-sandbox-*` containers Docker still has — a runner that cannot list them does not start, since a VM it did not adopt would take commands beside whatever the previous runner's shell left running in it — and takes them into its table as running and last used now, so the idle sweep stops them on schedule; their shells are gone with the old process, so before a VM is adopted everything running in it but pid 1 is killed — a command the old runner's shell was running must not go on writing after the worker finishes its turn — and a VM where that kill cannot be confirmed is stopped instead (and marked unstoppable if that fails too). A conversation opens a new shell on its next command. `restart` and the stop paths take the user's sandbox lock, so a restart never changes the shell table under a stop that is walking it.
- **Reset is the user's.** The Usage page's reset deletes `/workspace/.cache` (uv's cache and installed environments) and shell state; documents, notes and history stay.

## The image

`deploy/sandbox-image/Dockerfile`: Debian with `uv` and Python, `poppler-utils`, `ripgrep`, `jq`, `pandoc`, `imagemagick`, `git`, `procps` and `util-linux` (the `pgrep` and `setsid` the shell relies on), `/workspace` as the working directory, `UV_CACHE_DIR=/workspace/.cache/uv` and `UV_INDEX_URL` from `SANDBOX_INDEX_URL`. Its pid 1 is a few lines of Python that do nothing but reap: what a command left running is killed after the command and reparented to pid 1, and under a `sleep infinity` it would stay a zombie against the VM's pid limit. The runner passes the same program on `docker run`, so the image's `CMD` and the runner cannot drift. Commands run as root **inside the VM**: `/workspace` is a bind mount the api and worker write as root, and one identity on both sides is what keeps the files writable from the shell; the isolation is the VM boundary, with every capability dropped and a read-only root filesystem, not a guest UID. Built and tagged by the operator like the service images; `SANDBOX_IMAGE` names it (`sightread-sandbox`), and compose names the runner's own image `sightread-sandbox-runner` so the two never share a tag.

## Operations

- Install the Kata runtime and register it with Docker as `kata` (the runtime binary, the guest kernel and the rootfs image are Kata's packages; Docker's `daemon.json` gets `"runtimes": {"kata": {"path": "/usr/bin/containerd-shim-kata-v2"...}}` per Kata's Docker guide). Verify with `docker run --runtime kata --rm hello-world` before enabling the sandbox.
- `{WORKSPACES_DIR}` is a host directory bind-mounted into `api`, `worker` and `sandbox`. The runner holds it twice: `SANDBOX_WORKSPACES_DIR` is the host path it hands to `docker run -v` — absolute, as the daemon resolves nothing relative to the compose project, and the runner refuses to start with a relative one; compose derives it from `WORKSPACES_HOST_DIR` when nothing names it, and from `${PWD}/workspaces` when that is empty too, which is how the local `.env.example` leaves it — and `SANDBOX_START_TIMEOUT_SECONDS` (180) is how long that `docker run` may take, which api and worker allow on top of a command's timeout so a cold start never looks like a lost command; `SANDBOX_WORKSPACES_MOUNT` is where compose mounted it inside the runner, which is what the runner reads and clears itself (the `.cache` it creates and `reset` removes). A per-user quota is a filesystem concern — XFS project quotas or one fixed-size image per user mounted under the directory — see [workspace.md](./workspace.md) § Quota.
- Logs: every command is recorded in the conversation (`chat_events`), never only in the runner's log.
