# Sandbox — one VM per user

The chat agent's `bash` tool runs inside a microVM that belongs to the user: `/workspace` is their workspace directory ([workspace.md](./workspace.md)), nothing of the service is reachable from inside, and the VM is stopped when idle and started again on the next command. Files survive; shell state and installed packages survive too — only `reset` discards them.

## The runner

A separate service, `apps/sandbox` (`sightread-sandbox` in compose), is the only container with the Docker socket. The API and the worker never talk to Docker; they call the runner over HTTP on the compose network with a shared token (`SANDBOX_TOKEN`). The runner starts one container per user from the sandbox image under the configured runtime and keeps shell sessions open inside it.

| Route | What it does |
|-------|--------------|
| `GET /sandboxes/{user_id}` | `{state: stopped\|starting\|running, last_used_at, shells, uptime_seconds}` |
| `POST /sandboxes/{user_id}/exec` | `{session, command, timeout_seconds}` → `{output, exit_code, timed_out, truncated}`. Starts the VM when stopped. The session names a persistent shell: working directory and environment carry from one command to the next, which is what the bash tool's contract expects; a command returns once its background jobs have finished too (`wait` before the status line), and whatever it started that is still running then — a disowned job, a server — is killed before the status line: the shell is its own session and process group (`setsid`), and everything in that group but the shell goes, so nothing a command started writes the tree after the command's revision. There is no way to keep a process running between commands. |
| `POST /sandboxes/{user_id}/restart` | `{session}` — kill that shell and open a fresh one (the bash tool's `restart`) |
| `POST /sandboxes/{user_id}/stop` | stop the VM, keep everything on disk. **503** when Docker could not remove it and does not report it gone: the sandbox is then marked unstoppable and takes no command until it is |
| `POST /sandboxes/{user_id}/reset` | stop, and delete the package cache and shell state under `/workspace/.cache`; documents are untouched. Held under the user's sandbox lock from the stop through the deletion, so no command starts into a cache being removed; a stop that fails (**503**, as above) deletes nothing, since a VM still alive could be writing into it |

Output is captured as combined stdout and stderr in fixed-size reads (never line by line, so one newline-free value of any length is cut like any other flood), kept at `SANDBOX_OUTPUT_MAX_BYTES` with the head and the tail, so a command that prints a file cannot flood the conversation. A command past `timeout_seconds` is killed *inside the VM* — the shell writes its pid to the VM's `/tmp` when it opens, and the runner kills that process, everything under it and everything in its process group through a second `docker exec`, since ending the host-side client does not end what runs in the container — then the host-side session is closed and the timeout reported; the next command of that session opens a fresh shell. When that kill cannot be confirmed — the pid file is gone, the kill fails, the `docker exec` hangs — the runner stops the VM instead, so no command outlives its timeout and goes on writing the workspace after the host has moved on; and a VM that cannot be stopped either — the removal fails or times out, and an inspection does not report it absent or stopped; the same check every stop makes, `stop`, `reset` and the idle sweep included, since closing the host-side clients confirms nothing about what runs inside — takes no further commands until Docker positively reports it gone — an inspection that fails (the daemon away) is not "gone", it is unknown, and unknown keeps the sandbox closed. `SANDBOX_COMMAND_TIMEOUT_MAX` (600) is the ceiling on what a caller may ask for.

Two backends implement the same interface: `docker` (production: `docker run` with `--runtime {SANDBOX_RUNTIME}`, the user directory bind-mounted at `/workspace`, `--network {SANDBOX_NETWORK}`, cpu/memory/pids limits, a read-only root filesystem and a tmpfs `/tmp`) and `local` (tests only: a bash process in a temporary directory, no isolation — never deployed).

## Isolation

- **Runtime:** Kata Containers (`SANDBOX_RUNTIME=kata`) — every container is its own KVM microVM with its own kernel; Cloud Hypervisor is Kata's default hypervisor, Firecracker is the alternative. The host needs `/dev/kvm` and the Kata runtime installed ([deployment.md](./deployment.md)). `runc` works for local development and gives no VM boundary; in production the runner accepts only a runtime named in `SANDBOX_VM_RUNTIMES` (the Kata names, by default) and refuses to start otherwise — any other OCI runtime would be a shared kernel under a VM's name.
- **Network:** `SANDBOX_NETWORK=none` by default. Package installs need one egress: deploy a PyPI-only proxy on an internal compose network, point `SANDBOX_NETWORK` at that network and `SANDBOX_INDEX_URL` at the proxy; the proxy allows GET to the index and wheel hosts and nothing else — it must not become a channel out of the VM.
- **No secrets in the VM.** The upstream key, the database and the API are unreachable from inside; the agent's model calls are made by the worker on the host, never from the VM.
- **Resource limits:** `SANDBOX_CPUS`, `SANDBOX_MEMORY`, `SANDBOX_PIDS`, per-command timeout, output cap. Shells per user are capped by the runner at `SANDBOX_MAX_SHELLS` (8): a conversation holds one shell, and when a new conversation needs one past the cap the shell that has been idle longest is closed to make room (its conversation gets a fresh shell on its next command, as after `restart`). A shell running a command is never evicted; if every one is busy the command is refused.
- **The document is in the VM.** A prompt injection in a parsed PDF can at worst make the agent act on that user's own files, which revisions undo; it cannot reach another user's directory or the service.

## Lifecycle

- **Start on first use.** The first `exec` of a user whose VM is stopped boots it (Kata boots in about a second; the UI shows a starting state meanwhile).
- **Stop when idle.** `SANDBOX_IDLE_SECONDS` after the last command the runner stops the VM; a VM with a command still running is never idle, whatever the clock says — decided twice, once to pick candidates and again under the user's lock, so a command that started in between keeps its VM. Nothing is deleted, ever, by the runner.
- **A restarted runner adopts what is running.** At start the docker backend lists the `sightread-sandbox-*` containers Docker still has and takes them into its table as running and last used now, so the idle sweep stops them on schedule; their shells are gone with the old process, and a conversation opens a new one on its next command.
- **Reset is the user's.** The Usage page's reset deletes `/workspace/.cache` (uv's cache and installed environments) and shell state; documents, notes and history stay.

## The image

`deploy/sandbox-image/Dockerfile`: Debian with `uv` and Python, `poppler-utils`, `ripgrep`, `jq`, `pandoc`, `imagemagick`, `git`, `procps` and `util-linux` (the `pgrep` and `setsid` the shell relies on), `/workspace` as the working directory, `UV_CACHE_DIR=/workspace/.cache/uv` and `UV_INDEX_URL` from `SANDBOX_INDEX_URL`. Commands run as root **inside the VM**: `/workspace` is a bind mount the api and worker write as root, and one identity on both sides is what keeps the files writable from the shell; the isolation is the VM boundary, with every capability dropped and a read-only root filesystem, not a guest UID. Built and tagged by the operator like the service images; `SANDBOX_IMAGE` names it (`sightread-sandbox`), and compose names the runner's own image `sightread-sandbox-runner` so the two never share a tag.

## Operations

- Install the Kata runtime and register it with Docker as `kata` (the runtime binary, the guest kernel and the rootfs image are Kata's packages; Docker's `daemon.json` gets `"runtimes": {"kata": {"path": "/usr/bin/containerd-shim-kata-v2"...}}` per Kata's Docker guide). Verify with `docker run --runtime kata --rm hello-world` before enabling the sandbox.
- `{WORKSPACES_DIR}` is a host directory bind-mounted into `api`, `worker` and `sandbox`. The runner holds it twice: `SANDBOX_WORKSPACES_DIR` is the host path it hands to `docker run -v`, `SANDBOX_WORKSPACES_MOUNT` is where compose mounted it inside the runner, which is what the runner reads and clears itself (the `.cache` it creates and `reset` removes). A per-user quota is a filesystem concern — XFS project quotas or one fixed-size image per user mounted under the directory — see [workspace.md](./workspace.md) § Quota.
- Logs: every command is recorded in the conversation (`chat_events`), never only in the runner's log.
