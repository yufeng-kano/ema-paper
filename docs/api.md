# API

Two planes, one FastAPI app.

**Upstream.** Every call goes to **Kano Proxy** on the operator's own key: `{KANO_PROXY_BASE_URL}/openai/v1` (`/chat/completions`, `/models`) with `Authorization: Bearer <KANO_PROXY_API_KEY>` for the vision calls and the catalog, and the Anthropic-format route `{KANO_PROXY_BASE_URL}/anthropic/v1/messages` for the `chat` and `check` agents ([chat.md](./chat.md), [auth.md](./auth.md) § 3). The models are the deployment's ([billing.md](./billing.md) § Models and the operator's upstream): the `parse` agent runs `PARSE_MODEL`, with `PARSE_FALLBACK_MODEL` for a blocked page or a retry; `check` runs `CHECK_MODEL` (empty: the parse model); `chat` offers `CHAT_MODELS`, of which each user picks one ([agents.md](./agents.md)). `/v1/parse` takes a per-request `model` only from the parse agent's models (**400** otherwise). With `KANO_PROXY_API_KEY` or `KANO_PROXY_BASE_URL` empty, or `PARSE_MODEL` empty for a parse, the call is refused with **503** `upstream`. There are no user-defined upstreams: the provider connections and the per-user Kano Proxy keys were removed by step 4 of [billing.md](./billing.md) § Transition.

- **Data plane `/v1/*`** — authenticated by API key (`Authorization: Bearer sr_...`) or an OAuth access token ([auth.md](./auth.md)). This is the product. `POST /v1/parse` and the three `GET /v1/jobs/{id}*` routes additionally accept a single-use upload ticket (`srt_...`, [auth.md](./auth.md) § 5): one upload, then reads of the job that upload created, nothing else.
- **Control plane `/api/*`** — session cookie (Google OIDC), consumed only by the Nuxt web app.

`GET /healthz` is public and DB-free (`{"ok": true}`). It backs the compose healthchecks and is also routed to the API on the public origin, so an external monitor can reach it — Caddy's `@api` matcher includes it explicitly ([deployment.md](./deployment.md)). All responses are JSON unless SSE is requested. Errors use one shape:

```json
{ "error": { "type": "invalid_request | revision_conflict | auth | rate_limit | payment | insufficient_credits | checkout_unavailable | pay_unavailable | upstream | internal", "message": "..." } }
```

## Data plane

### POST /v1/parse

Multipart form (preferred) or JSON with base64 `source`.

| Field | Notes |
|-------|-------|
| `file` | required; PDF or image (jpg/png/webp/heic). Max **128 MB** (`UPLOAD_MAX_BYTES`), PDFs max **500 pages** (`PAGE_CAP`) |
| `model` | optional model id on the parse agent's upstream (Kano Proxy's or the selected connection's catalog); default: the model stored in the parse agent's settings. Neither → 400 ([agents.md](./agents.md) § Enqueue rules) |
| `pages` | optional selection, e.g. `"1-5,8"`; default all |
| `force` | optional bool; bypass dedup cache |

Responses:

- **200** — dedup cache hit ([jobs.md](./jobs.md) § Dedup): full result immediately.
- **202** — `{ "job_id": "...", "status": "queued" }`.
- With `Accept: text/event-stream` — SSE stream (below) instead; small documents feel synchronous.

The upload is hashed (SHA-256) while streaming to disk; the request must never buffer the whole file in memory.

The JSON form is held whole by `request.json()`, so the body-limit middleware gives it a ceiling of its own — the upload cap in base64 (four bytes per three) plus room for the envelope — enforced by the declared length and, for a chunked body that declares none, by counting the bytes as they arrive; only a multipart body on an upload route is exempt from the middleware. The multipart body is read through a **bounded stream** rather than Starlette's `request.form()`, on this route and on the library's. The parser spools each file part to disk as it arrives with no cap of its own, and `store_upload` — where `UPLOAD_MAX_BYTES` is really enforced — only sees the file once the whole body is parsed. A request that declares no length, or an untrue one, would otherwise be written out in full before anything could answer 413.

### GET /v1/jobs/{id} — status

`{ job_id, status: queued|running|succeeded|failed, page_count, pages_done, error?, created_at, finished_at?, credits }` — `credits` is what the parse cost once it is settled, `0` for a failed one, `null` while its reservation is pending ([billing.md](./billing.md) § Routes)

A parse with any failed page is `failed` as a whole ([parsing.md](./parsing.md) § Vision-only conversion): `error` counts the failed pages and names their reasons, and there is no result to fetch. A new upload, or the same one with `force`, parses it again; the pages are retried alone only from the web library ([jobs.md](./jobs.md) § Retrying failed pages).

### GET /v1/jobs/{id}/result — full result

```json
{
  "markdown": "…",
  "pages":   [ { "page": 1, "width_pt": 612, "height_pt": 792, "method": "vision", "model": "provider/model", "error": null } ],
  "figures": [ { "id": "fig1", "page": 3, "bbox": [120, 60, 480, 940], "caption": "Figure 1: …", "check": "verified" } ],
  "errors":  [],
  "meta": {
    "job_id": "…",
    "agent": "parse",
    "model": "provider/model",
    "bbox_format": "yxyx_norm1000",
    "pipeline_version": 2,
    "sha256": "…",
    "cached": false,
    "figure_check": { "verified": 1, "adjusted": 0, "unverified": 0 }
  }
}
```

`markdown` carries a `<!-- page: N -->` marker line before each page's content ([parsing.md](./parsing.md) § Page markers). Figure placeholders in markdown: `![fig1](sightread://p3/120,60,480,940)` with the caption verbatim on the next line; a figure's `caption` in `figures` is that line, and empty for a figure without one ([parsing.md](./parsing.md) § Coordinate contract). Cropping is the caller's job (add ~2% margin; denormalize `x_px = x/1000 * page_width_px`).

A figure's `check` is what the figure check made of its box ([parsing.md](./parsing.md) § Figure check): `verified`, `adjusted` (the box was moved to take in what it cut off, then confirmed) or `unverified` (the check could not confirm the box: crop it with a wider margin, or look at it). `meta.figure_check` counts the three. Results parsed before the check (`pipeline_version` below 10) carry neither.

A page's `model` is the model that wrote it: `meta.model` for most, another for a page a fallback or a retry finished ([parsing.md](./parsing.md) § Fallback model); results written before the field carry none. `errors` is empty on every result written since a failed page fails the job; older results can list `{page, reason}` entries for pages they omit.

Results stored before the Kano Proxy migration still carry `meta.profile` (the OpenRouter preset profile they ran); new results carry `meta.agent` instead.

### GET /v1/jobs/{id}/result.md — markdown only

The result's `markdown` string as `text/markdown` — nothing to unwrap, ready to save as a file. Same 404 as `/result` while the job has no result.

### GET /v1/jobs/last* — the upload ticket's own job

`/v1/jobs/last`, `/v1/jobs/last/result` and `/v1/jobs/last/result.md` resolve `last` to the job the presented **upload ticket** is bound to, so a ticket caller (the MCP flow) never needs to extract a job id. Only tickets: a durable credential gets 400 and uses the explicit id routes.

### GET /v1/jobs/{id}/events — SSE progress

Events: `progress` (`{job_id, pages_done, page_count, page, method}` per finished page), then exactly one of `done` (full result payload) / `error`. Reconnectable at any time; a terminal job replays the final event immediately. Keepalive comment every 10 s.

### GET /v1/models

The models a parse may run — `PARSE_MODEL`, then `PARSE_FALLBACK_MODEL` when set — as `{data: [{id, name}]}` (`name` null: the deployment names no model), the same answer as `GET /api/agents/parse/models`. 503 with no parse model configured. Also accepts a web session cookie. The ids come from the deployment's configuration, never from code.

### Partial results (control plane only)

While a job is still `queued` or `running`, the two control-plane result routes answer **200 with a partial result** instead of 404: the finished pages' stored markdown ([jobs.md](./jobs.md) § Progress) assembled exactly like the final document — page markers, renumbered figure placeholders — with `meta.partial: true`, `pages` listing only the finished pages, and `meta.page_count`/`meta.pages_done` carrying live progress. Figure ids are per-snapshot (a page finishing out of order renumbers them), so nothing may cache a partial result; the viewer re-reads until `partial` disappears. The data plane is unchanged: `/v1/jobs/{id}/result` stays 404 until the job finishes, and SSE remains its progressive interface.

### Usage aggregates

`GET /api/usage` answers `{days, per_day: [...], per_model: [...], per_agent: [...]}`; a `per_day` entry carries `date` and `agents` (the agent names that ran that day), a `per_model` entry `model`, a `per_agent` entry `agent`, and all carry the same figures:

| Field | Meaning |
|-------|---------|
| `calls` | `usage_log` rows (one per upstream call) |
| `prompt_tokens`, `completion_tokens` | summed over every call, priced or not |
| `cost` | **billed**: the sum of OpenRouter's own cost (`cost_source = openrouter`). Only historical rows carry it — OpenRouter was removed and no new call is billed — so for recent periods this is 0 with no billed calls behind it |
| `estimated_cost`, `estimated_calls` | the sum and count of costs Kano Proxy reported (always recorded) or a connection reported with `report_cost` on (`cost_source = estimated`) — an estimate, never added into `cost` |
| `unpriced_calls` | calls whose cost is unknown (`cost_source = unknown`); counted, never priced as 0 |
| `cache_read_tokens`, `cache_write_tokens` | prompt-cache reads and writes, chat rows only ([chat.md](./chat.md) § Prompt caching) |

`calls - estimated_calls - unpriced_calls` is the number of billed calls, so a client can tell "OpenRouter billed $0" from "nothing here went through OpenRouter". The per-model grouping is by model id alone, as before; one id used on two upstreams lands in one entry with its figures still separated by source.

### Why the web upload is a control-plane route

`POST /api/library/documents` duplicates no logic: it reads a multipart body and hands it to `jobs.intake.submit_parse`, exactly as `POST /v1/parse` does. It exists as a separate route because the two planes authenticate differently and must keep doing so — the data plane is bearer-only (API key, OAuth token, upload ticket) and the control plane is session-cookie plus the `X-Requested-With` CSRF pairing. Teaching `/v1/parse` to accept a cookie would put a CSRF-shaped hole in the product's own API; teaching the web app to mint itself an API key would put a durable credential in a browser. So the browser posts to the control plane with the credential it already has, and the bytes take the same path every other `/api/*` request takes: browser → Caddy → FastAPI. Nothing document-shaped enters the Nuxt server ([web.md](./web.md) § Rules).

## Limits (defaults, env-overridable)

- `UPLOAD_MAX_BYTES` = 134217728 (128 MB) — enforced in the app **and** in Caddy; keep in sync ([deployment.md](./deployment.md)).
- `PAGE_CAP` = 500, `MAX_JOBS_PER_USER` = 2 concurrent — the ceiling; what a user may run at once is their plan's `maxJobs` under it ([billing.md](./billing.md) § Plans) — `VISION_CONCURRENCY_PER_JOB` = 8.
- `SYSTEM_PROMPT_MAX_CHARS` = 8000 — cap on an agent's prompt, a prompt preset's text, a skill's body and a subagent's prompt.
- `CHAT_INSTRUCTIONS_MAX_CHARS` = 8000 — the chat agent's instructions; `CHAT_MEMORY_MAX_CHARS` = 500 one memory, `CHAT_MEMORIES_MAX` = 200 a user's memories, `CHAT_MEMORY_BLOCK_MAX_CHARS` = 12000 the memories one conversation loads; `CHAT_SECTIONS_PER_MESSAGE` = 4 whole sections added to one message, `CHAT_SECTION_HEADING_MAX_CHARS` = 512 the heading of one ([chat.md](./chat.md) § Instructions, § Memory, § What a user message carries).
- `CHAT_ATTACHMENT_MAX_BYTES` = 20971520 (20 MiB) per attached file, `CHAT_ATTACHMENTS_PER_MESSAGE` = 8, `CHAT_ATTACHMENT_TEXT_MAX_CHARS` = 100000 of a PDF's or text file's text, `CHAT_ATTACHMENT_IMAGE_LONG_EDGE` = 1568 px, `CHAT_ATTACHMENTS_PENDING_MAX` = 32 of a user's attachments waiting for a message at once, `CHAT_ATTACHMENT_CACHE_SECONDS` = 31536000 (a year) that the browser may cache an attached image, `CHAT_ATTACHMENT_PDF_TIMEOUT_SECONDS` = 60 for a PDF's text, `UPLOAD_MAX_AGE_SECONDS` = 86400 (a day) before the sweeper takes an upload entry, an unsent attachment's included; `CHAT_SKILLS_MAX` = 64 and `CHAT_SUBAGENTS_MAX` = 32 of a user's own; `CHAT_SUBAGENT_MAX_TOOL_CALLS` = 1000 per subagent run ([chat.md](./chat.md)).
- `DOCUMENT_IMAGE_MAX_BYTES` = 20971520 (20 MiB) per image inserted into a document, kept at a long edge of `DOCUMENT_IMAGE_LONG_EDGE` = 2400 px ([workspace.md](./workspace.md) § Inserted images).
- `FIGURES_PER_PAGE_MAX` = 40 — cap on stored figure crops per page, and on the boxes a page's figure check reads ([parsing.md](./parsing.md) § Figure crops).
- `FIGURE_CHECK_ROUNDS` = 2 — model rounds one page's figure check may take, one call each; at least 1 ([parsing.md](./parsing.md) § Figure check).
- `PAGE_PREVIEW_LONG_EDGE` = 1200 px — a page preview's long edge; `PAGE_PREVIEW_RENDERS` = 2 previews made at once per API process.
- `CHECK_SPOTS_MAX` = 80 spots sent to the check agent, `CHECK_MAX_CALLS` = 16 calls one check may make, `CHECK_MAX_OUTPUT_TOKENS` = 16000 per answer ([parsing.md](./parsing.md) § Format check).
- Request bodies are capped at six times `CONTENT_MAX_BYTES` plus 64 KiB — the worst case of JSON escaping, where a one-byte control character becomes a six-byte `\uXXXX` and an emoji's four bytes a twelve-byte surrogate pair, so no document under the content cap is refused for its encoding — (**413** past it, by declared length or as the bytes arrive) on every route but the four that stream an upload to disk under a cap of their own (`POST /v1/parse` and `POST /api/library/documents` under `UPLOAD_MAX_BYTES` — a markdown file then under `CONTENT_MAX_BYTES` —, `POST /api/attachments` under `CHAT_ATTACHMENT_MAX_BYTES`, `POST /api/library/images` under `DOCUMENT_IMAGE_MAX_BYTES`); a multipart label on any other route buys no exemption.
- `UPSTREAM_RESPONSE_MAX_BYTES` = 33554432 (32 MB) — cap on any upstream response body (model catalogs and vision completions); beyond it the call fails as `upstream` ([parsing.md](./parsing.md) § Upstream usage). `UPSTREAM_SSE_LINE_MAX_BYTES` = 4194304 (4 MiB) caps one line of the chat agent's event stream, and `UPSTREAM_CONTENT_BLOCKS_MAX` = 4096 the content blocks one answer may hold ([chat.md](./chat.md) § Upstream).
- **402** `insufficient_credits` with `need`, `remaining` and `period_end` inside `error` when the parse's pages cost more than the period's balance ([billing.md](./billing.md) § Refusals); the upload is not stored and an upload ticket is not spent. A chat send under the minimum balance answers the same.
- 429 with `Retry-After` when the per-user job cap is hit; upstream 402 (the upstream's credits or allowance exhausted) maps to `payment` and fails the affected pages — the other pages still run, and the job fails with them at its end.
- `MAX_CHAT_TURNS_PER_USER` = 4 concurrent chat turns (and shells); `CHAT_MAX_OUTPUT_TOKENS` = 64000; `CHAT_MAX_TOOL_CALLS_PER_TURN` = 1000; `CHAT_TURN_TIMEOUT_SECONDS` = 3600; `CHAT_STREAM_TIMEOUT_SECONDS` = 900; `CHAT_WRITER_GRACE_SECONDS` = 60; `REVERT_MAX_BYTES` = 67108864; `REVERT_MAX_PATHS` = 2000; `WORKSPACE_GIT_TIMEOUT_SECONDS` = 60; `CHAT_MESSAGE_MAX_CHARS` = 32000; `CHAT_SELECTION_MAX_CHARS` = 16000; `CHAT_TOOL_RESULT_MAX_CHARS` = 20000; `CHAT_IMAGE_ROUND_MAX_BYTES` = 33554432; `CHAT_IMAGE_TURN_MAX_BYTES` = 134217728; `SANDBOX_CONTROL_TIMEOUT_SECONDS` = 180 ([chat.md](./chat.md), [sandbox.md](./sandbox.md)).
- `WORKSPACE_QUOTA_BYTES` = 10 GiB per user ([workspace.md](./workspace.md) § Quota).
