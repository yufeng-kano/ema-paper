# Jobs: queue, concurrency, dedup, retention

## Queue = PostgreSQL, nothing else

Jobs are rows in `jobs`. The worker claims work with:

```sql
UPDATE jobs SET status='running', started_at=now(), worker_generation=:generation
WHERE id = (
  SELECT id FROM jobs WHERE status='queued'
  ORDER BY created_at
  FOR UPDATE SKIP LOCKED LIMIT 1
) RETURNING *;
```

Enqueue happens in the **same transaction** as job-row creation — no dual-write problem, no broker. If a queue swap (e.g. RabbitMQ) ever happens, it happens behind the small `queue` module interface; nothing else may know how claiming works.

The worker is the same codebase as the API, launched as its own process/container (`python -m sightread.worker`). Rendering runs in Poppler subprocesses (multi-core comes free); vision calls fan out per page with an asyncio semaphore.

One worker process runs one job at a time — concurrency inside a job is the page fan-out (`RENDER_WORKERS`, `VISION_CONCURRENCY_PER_JOB`), not more worker processes: there is **one worker per deployment**, and the worker enforces it by holding a PostgreSQL session-level advisory lock (`pg_try_advisory_lock`, one fixed key) for its whole life. A second worker process waits for the lock rather than starting — in a rolling restart the one being replaced releases it as it stops — because the recovery a worker runs at start treats every `running` row as a dead worker's, which is only true of a singleton. The lock is the session's, and PostgreSQL releases it with the session (a restart, a dropped connection), handing it to the waiting worker: so the holder pings its lock session every few seconds and, the moment the session is gone, stops and cancels the job or turn in flight rather than finish a parse beside the worker that took it over. The loss is noticed seconds late, and in those seconds the replacement has already requeued — and may have claimed — the job the stale worker is still running: so every worker takes a **generation** with the lock (the next value of the `worker_generation_seq` sequence; the SQLite fallback takes the highest on record plus one), writes it onto every job it claims (`jobs.worker_generation`, the `:generation` above) and carries it on every write it makes to a running job — a page recorded, the terminal state and the retention that follows it, the requeue on shutdown — each fenced on the row still holding that generation, the endpoint snapshot a run updates at its start included (a run whose update fences out ends there); a requeue clears it. A stale worker's writes therefore land nowhere: the page it finishes is not recorded (the upstream calls it made are still logged as usage, since the user's key paid for them), its result is not written over the replacement's, and its shutdown requeue does not put back a job the replacement owns. Its files are its own as well: every attempt renders pages into a work directory of its own and crops figures into `FIGURES_DIR/{job_id}.{attempt}/`, published as `FIGURES_DIR/{job_id}/` only by the finish that passed the fence, under the same shared hold of the backup lock as the terminal commit, so a backup never carries a succeeded result whose crops still sit in an attempt directory ([parsing.md](./parsing.md) § Figure crops, [workspace.md](./workspace.md) § Backups), so a stale attempt's discard — on a cancel, or when its finish was fenced out — takes only its own crops, never the replacement's, and nothing of the two attempts mixes; a worker starting removes every attempt directory of a job it requeues with the published one. A chat turn is fenced by its terminal state instead: the replacement finishes the stale worker's turn as an orphan, the stale worker's loop stops at its next check when it finds the turn finished, as on a cancel, its own terminal write leaves a finished turn as it is, and a message it would store — or the model change a fallback answer would record first — is written in one transaction with that check, under the conversation's lock, so a finished turn takes no more history. A cancelled page's image preparation, which runs in a thread, is waited for before the work directory is removed and the job requeued, so no thread writes into the next attempt's directory. On `SIGTERM` the worker stops claiming; a job caught mid-run goes back to `queued` keeping the pages it finished and nothing else of the attempt — its failed pages' rows and its crops go — so the next attempt transcribes only what is missing (§ Retrying failed pages): a page the user's key already paid for is never transcribed twice for its job. A job whose task raised past the runner's own handling (a database error while the terminal state was being written) is marked `failed` with `internal error` by the worker loop, as a chat turn is — never requeued, since the parse ran and billed — so no row stays `running` with nobody driving it, against its user's cap; and a worker that starts puts every job still `running` back on the queue, its crops discarded and its failed pages forgotten, as on a shutdown: there is one worker per deployment, so a job nobody is driving is one a worker that was killed outright held. After the orphaned turns, the worker sweeps the writing markers still standing — shell commands the runner could not confirm over in turns that ended ([workspace.md](./workspace.md) § Revisions) — restarting each one's shell and recording the tree (a marker that cannot be read names no shell, so the VM is stopped whole instead); a user whose runner does not answer is left for the next pass, no turn or parse of theirs run meanwhile. A worker with no runner configured (`SANDBOX_URL` gone from its environment) treats a standing marker the same way: it has nothing to stop the shell with, so the orphaned turn and the marker wait, and the user's workspace stays closed, rather than being declared safe over a VM that may still run the command.

## Concurrency caps (defaults)

- `MAX_JOBS_PER_USER` = 2 running jobs, the ceiling; intake caps a user at their plan's `maxJobs` under it (Free: `FREE_MAX_JOBS` = 1, [billing.md](./billing.md) § Plans); excess `POST /v1/parse` gets 429 + `Retry-After: PARSE_RETRY_AFTER_SECONDS` (30; fail closed, never crash). The web library's upload runs the same intake and hits the same cap, so a multi-file drop is a client-side queue that treats the 429 as back-pressure and retries ([web.md](./web.md) § Files) — the cap is not relaxed for a browser.
- `VISION_CONCURRENCY_PER_JOB` = 8 concurrent upstream calls.
- `RENDER_WORKERS` = CPU count (env-overridable) concurrent Poppler subprocesses per worker.

Fairness: the claim query above is FIFO; the ceiling is enforced at claim time too (skip a queued job whose user already has `MAX_JOBS_PER_USER` running) — the plan's cap is intake's, where the 429 is answered.

## Progress

Worker updates `jobs.pages_done` and `job_pages` rows as pages finish; SSE endpoints read from PG (LISTEN/NOTIFY for wakeup, poll fallback). Terminal jobs replay their final event on reconnect.

Each finished page's markdown is stored on its `job_pages` row (`markdown`, NULL for a failed page), so a running job has a readable partial result: the control-plane result routes assemble the finished pages with the same `assemble` the final result uses and answer 200 with `meta.partial: true` while the job is queued or running ([api.md](./api.md)). The final `results` row is still written whole at terminal state and is the only thing the dedup cache ever serves. `requeue_job` keeps the succeeded rows, their markdown included, and deletes the failed ones; `pages_done` restarts at the kept count. A failed job keeps all its rows: they are what a retry starts from.

A job that carries a format check (`jobs.check_model`) is still `running` while it is checked, after its last page ([parsing.md](./parsing.md) § Format check): the library payload says `checking` for a running job with a check whose every page is done ([api.md](./api.md)).

## Retrying failed pages

A parse with a failed page fails whole ([parsing.md](./parsing.md) § Vision-only conversion), and it is retried rather than ever opened: `POST /api/library/documents/{id}/retry` ([api.md](./api.md)) puts the job behind the document — or the document's failed re-convert (§ Re-converting a document) — back on the queue — `queued`, its error, start and finish cleared — keeping every page that succeeded. The failed pages' rows are deleted and `pages_done` restarts at the kept count, in the transaction that requeues it, which is decided under the user's workspace lock and the job's row lock (the one order, [workspace.md](./workspace.md) § Revisions) and only from `failed`, so two retries cannot both put it back. The run that claims it:

- **transcribes only the pages without a succeeded row** (`job_pages`), on the model the retry named (`jobs.retry_model`; NULL is the job's own `model`) — and sends a page that model blocks to the job's fallback, if it has one ([parsing.md](./parsing.md) § Fallback model);
- **renders the kept pages that carry figures again**, to crop them from their stored markdown: a render is ours to pay for, a transcription is the user's, and an attempt's crops come from that attempt alone ([parsing.md](./parsing.md) § Figure crops). Their boxes were checked when they were transcribed, and their statuses come with them: a kept page is not checked again ([parsing.md](./parsing.md) § Figure check);
- **assembles every page, kept and new,** and checks the document when the job carries a check, then commits the result like any result; a page that fails again, or a check that fails again, fails the job again, with nothing lost.

The retry also takes the format check again from the settings of its moment, as an upload would ([agents.md](./agents.md) § Enqueue rules): a check that failed may have failed on its model, and a reader who turned the switch off retries without one. A check with no model of its own follows the parse's, which on a retry is the model the retry named, else the job's own: a retry that moves a blocked page to another model does not send its text back to the first one in the check. A parse that failed only its check has every page kept, so its retry sends no page to a model at all.

The upload was deleted when the job failed, so a retry runs on the document's original ([workspace.md](./workspace.md)): the route copies it into the upload directory as the job's source (`source_path` set, `source_deleted_at` cleared), and the run's retention deletes that copy again — every recipient already holds its original. A requeue whose commit raises is read back on a connection of its own, as a filing is ([workspace.md](./workspace.md) § Revisions): landed, the retry stands on its copy and is answered as queued; rolled back, the copy is removed and the answer says nothing changed; unreadable, the copy stays — a retry that landed needs it, and the upload sweeper takes it otherwise — and the answer says the retry may have been queued. Only a failed `parse` behind a library document with an original is retried: an API parse kept none (its upload went with the failure; a new upload, or `force`, parses it again), and a document whose original was not kept — the workspace was at its quota — answers 409. A retry is not an upload: no per-user cap refuses it (the claim applies the cap to it like to any queued job), and it changes nothing of the dedup key — the job keeps its model, prompt and endpoint snapshot, and a result it finishes answers that key like any other.

## Re-converting a document

A document whose parse succeeded can be parsed again, whole, on a model the reader picks: `POST /api/library/documents/{id}/reconvert` ([api.md](./api.md)). It is for a parse that came out wrong in a way only a new run fixes — a better prompt or pipeline since, or a model that boxed figures badly. **The document keeps the version it has until the new parse succeeds**, so it never stands unopenable or half-replaced:

- **It is a new parse of the document's original** — a new job, listed in History like any other — run as a Files upload of that file would be, with the parse agent's settings of its moment ([agents.md](./agents.md) § Enqueue rules): the model the reader named, else the agent's own, its prompt, its upstream, its fallback model, and the format check. It is never answered from the dedup cache or joined to a parse in flight: the cached answer is the one being replaced. The per-user cap refuses it as it refuses an upload (429). The route streams the original into the upload directory as the job's source, under the workspace lock, as a retry copies it, and the run's retention deletes that copy: the document already keeps its original.
- **While it runs, the document points at it** (`documents.reconvert_job_id`, [database.md](./database.md)), set in the commit that queues the job, so no re-convert runs that its document would not take. Nothing else about the document changes: it opens, its text and notes save, the agent works on it, all on the version it has; a copy made meanwhile is a copy of that version, and the re-convert stays the document's own. The library row carries the new parse's live state as `reconvert` ([api.md](./api.md)).
- **When it succeeds, it becomes the document's parse.** Under the workspace lock, the document's directory as it stands is recorded first, then takes the new parse as one revision, `reconvert <path>`: `doc.md` from the new result as materialization writes it (the reading copy when the parse was checked) and `.meta.json` for the new job; `notes.md` is not touched. Then the row's `job_id` names the new job and the pointer clears, and the new crops are copied in as for any parse. Files before the row: a commit that fails leaves the pointer standing over files already in place, and the next taker finishes it. A swap that cannot write or record its two files puts both back as they were: the document opens on the version it has, and the next read tries again. An edit made while the parse ran is replaced too, and stays in the document's revisions like every text before it ([workspace.md](./workspace.md) § Revisions). The earlier parse stays in History, its result still the record of what it produced.
- The worker does this right after the parse's terminal commit, where it materializes a new upload's directory. The document's `content` and `result` routes do it first when they find a succeeded re-convert still pointed at — a worker that stopped between the two; one they cannot take leaves the document opening as it is. A document in the Trash when its re-convert succeeds keeps its version: the pointer clears, and the new parse stays in History to file from there.
- **When it fails, the document keeps its version**, and the pointer stays, so the row says so. A failed re-convert is retried like a failed parse (§ Retrying failed pages): the retry route sends its failed pages and keeps the rest, and a retry that succeeds swaps the document as above. Or it is dismissed (`DELETE …/reconvert`): the pointer clears, and the failed parse stays in History. A new re-convert replaces a failed one the same way.

Only a library document whose own parse succeeded, with an original kept and no re-convert queued or running, is re-converted: a failed parse is retried instead, a running one is waited for, and a document that kept no original is uploaded again (409); a markdown document has no parse (404). A figure placeholder from before the swap — in a reverted text or quoted in the notes — keeps its crop: the figure route looks for a crop the document's parse does not hold among the user's other succeeded parses of the same original ([parsing.md](./parsing.md) § Figure crops).

## Credits

A parse is charged in credits when it is queued and settled when it ends: the reservation is written in the commit that creates the job, consumed by `succeeded`, released by `failed`, and a dedup hit or an in-flight reuse costs nothing ([billing.md](./billing.md) § A parse). The worker settles in the same commit that writes the terminal state, idempotently, so a requeue that raced a finish cannot charge twice. The user's row is locked before the job is inserted, not after: the insert's foreign-key check already holds a share lock on that row, and two uploads taking the exclusive lock after it would deadlock instead of queueing one behind the other. A chat turn's entry is closed by whichever path finishes the turn, the runner's own or `fail_turn` ([billing.md](./billing.md) § A chat turn).

## Dedup cache

Key: `(user_id, agent, sha256, model, connection_id, connection_base_url, pages_spec, prompt_sha256, pipeline_version)` — `agent` because one agent's output never answers another's request ([agents.md](./agents.md)), `connection_id` because the same model id on two different endpoints is not the same model, and `connection_base_url` (the endpoint snapshot) because *editing* a connection's URL repoints what that id means: results parsed through the old endpoint must not answer uploads aimed at the new one. `pipeline_version` is the agent's own (`parse`: `PIPELINE_VERSION`).

The built-in upstream snapshots `KANO_PROXY_BASE_URL` as its `connection_base_url` (with `connection_id` NULL). Historical OpenRouter jobs have both NULL, which no new job ever has, so a result OpenRouter produced can never answer a new upload; and moving the deployment to another Kano Proxy origin likewise stops old results answering. The snapshot is taken at enqueue and **reconciled at claim time**: if the connection's URL (or `KANO_PROXY_BASE_URL`) changed while the job sat queued, the worker updates the job's snapshot to the endpoint it actually calls, so the cached result is keyed by the URL that truly produced it. A key rotation alone — editing a connection's key, or reconnecting Kano Proxy — does not invalidate the cache: same endpoint, same model, same output.

- On `POST /v1/parse`, hash while streaming to disk; if a **succeeded** job matches the full key and `force` is not set → return its result immediately (200, `meta.cached: true`), delete the fresh upload, create no job.
- **Only complete results are cache hits.** A result carrying page errors (a transient upstream failure, an unreadable page) is returned to its own job but never reused — the same upload reparses instead of replaying a degraded result forever. Since a failed page fails the whole job, only results written before that rule carry any. A result some of whose pages a fallback or a retry's model wrote is complete, and answers its key ([parsing.md](./parsing.md) § Fallback model).
- **A cache hit records no usage.** No upstream call runs, so no `usage_log` row is written — the original job's rows are the only record of what that result cost, with the `cost_source` they were recorded under. `report_cost` is not part of the key: it changes what gets recorded about a call, never the output.
- **Per-user only.** Never dedup across users: it would hand one user's paid output to another and leak that a document was parsed before.
- `force: true` always reparses (result row is replaced).
- **A retry must not buy a second parse.** The cache answers with *finished* work only, which leaves one gap: a browser cannot tell a lost response from a lost request, so it retries an upload that may already have landed, and the same bytes become a second job that bills the user's key twice for one document. `submit_parse(reuse_in_flight=True)` — asked for by the web library and by nothing else — answers such a retry with the job already queued or running for that exact key instead of starting another. The lookup is serialized by a transaction-level advisory lock on the dedup key (`hold_dedup_key`, PostgreSQL only), because reading before inserting protects a retry that arrives *after* the first upload committed but not two that overlap: both would find nothing and both would enqueue. A retry that arrives after the first request's job has already finished — succeeded with page errors, which the cache never answers, or failed — is answered with that job too, when it finished within `UPLOAD_RETRY_WINDOW_SECONDS` (60) of the retry: the browser retries within seconds, and the same bytes filed twice in that window are one upload whatever became of it; past the window the normal rule holds, and a degraded result reparses. `/v1/parse` does not do this: an API client that posts the same file twice means it, and has `force` besides.

## Retention — two layers, sweeper is the guarantee

1. **Immediate:** source file (and rendered page images) deleted the moment a job reaches `succeeded`/`failed` — figure crops are taken from the rendered page *before* it is deleted ([parsing.md](./parsing.md) § Figure crops). After that, reparsing requires re-upload — accepted trade-off, documented here on purpose. **Exception: a library document keeps its original.** When the finished job is the parse behind a `documents` row — whatever its terminal state: a failed parse's row keeps its original as a finished one does, so the upload is not lost with the error, and a row that lands after a failed parse takes the upload the same way — the worker files the source as that document's original — `{WORKSPACES_DIR}/.repos/{user_id}.sources/{document_id}.<ext>`, outside the VM's mount — and puts a copy of it in the document's workspace directory as `source.<ext>` for the shell, instead of deleting it, so the chat agent can re-render a page ([workspace.md](./workspace.md)); `source_deleted_at` is still set, since the upload directory no longer holds it. Retention runs *after* the terminal state is committed — under a shared hold of the backup lock taken before that commit and kept until the original and the copies are in place, so a backup never captures the finished rows without them ([workspace.md](./workspace.md) § Backups); the whole finalization of a committed result, retention and the document copies, runs to its end under a worker shutdown rather than being cut by it, since a cancel landing between the commit and the copies would release the locks under a copy still being made, and the requeue that follows the cancel leaves a job already `succeeded` as it is, crops included — and is best effort: a copy that fails (the workspace vanished, the disk filled) is logged, and the job is `succeeded` either way — only once every copy is done is the upload removed and `source_deleted_at` set. The rows that receive a copy are read under a lock on the job's row — in the terminal commit itself, before it decides whether the upload is kept for a row or deleted, and again in retention, after the user's workspace lock ([workspace.md](./workspace.md) § Revisions, one order everywhere) — and filing a parse (an upload landing, *Add to Files*) takes the same job lock before it inserts, so a row filed while the parse finishes either is among the recipients or is filed after, as a finished parse, never filed in the gap and left without its original. A row filed after the terminal commit but before retention holds the workspace lock finds no original yet and takes the upload as its own; retention does not then find the upload gone and keep nothing — a recipient that already holds an original is left alone, and the rest take a copy of the original any recipient holds, so the ones found at the terminal commit keep theirs whichever side got to the upload first. The Files page's upload marks its job `retain_source` when it queues it, because its `documents` row lands only after the parse is queued: a worker that finishes first finds no row and leaves the upload where it is, and the route takes it into the document directory as soon as the row exists. When the upload is a dedup hit — the parse already exists — the fresh file is kept for that row as well instead of being discarded, so a document filed through the Files page always has its original.
2. **Sweeper:** periodic task inside the worker (every 15 min) trashes anything under the upload dir older than `UPLOAD_MAX_AGE_SECONDS` (86400, a day) — catches crashed jobs, abandoned uploads, bugs, and the chat agent's attachments that were uploaded but never sent (`chat-attachment-*`, [chat.md](./chat.md) § What a user message carries; a send embeds and deletes its own, and the attachments route counts and drops their rows by the same age). The sweeper is the guarantee; immediate deletion is an optimization. `FIGURES_DIR` is outside the upload dir precisely so the sweeper cannot eat stored crops.

Crops live exactly as long as something references them: a job that ends `failed` has its crop directory removed with the result it never wrote, and a shutdown requeue removes it too — the next attempt crops every page again, the kept ones from their stored markdown ([parsing.md](./parsing.md) § Figure crops), so nothing stale from the first attempt can answer a figure route.

Results (markdown + metadata in PG) and figure crops (`FIGURES_DIR`) are kept **indefinitely** for now (low traffic); revisit when storage says otherwise. Usage rows are permanent — they are the billing history. Workspaces are never swept ([workspace.md](./workspace.md)).

## Chat turns

The `chat` agent has its own queue, `chat_turns` ([chat.md](./chat.md)): one row per user message, claimed by the same worker loop with the same `FOR UPDATE SKIP LOCKED` query shape and a per-user cap of `MAX_CHAT_TURNS_PER_USER` running turns. The worker alternates between the two queues — a parse never starves a conversation and the reverse — and runs one claimed item at a time per process, exactly as for jobs; a turn interrupted by shutdown is marked `failed` with `worker stopped` (a turn the user had already cancelled keeps `cancelled`), stamped finished and given its terminal event, never requeued: its tool calls may have run, and replaying them is not safe. A turn whose task raised past the runner's own handling (a database error before the first event, say) is marked `failed` with `internal error` by the worker loop itself, so no turn stays `running` with nobody driving it. A worker that was killed outright cannot do either, so a worker that starts finishes every turn still `running` (or cancelled and not yet wound down) with `worker restarted` and its terminal event — there is one worker process per deployment, so a turn nobody is driving is exactly one a dead worker left. Before such a turn is finished, its conversation's shell is restarted on the runner, which kills the command inside the VM first ([sandbox.md](./sandbox.md) § The runner): the dead worker may have had a command running, and the worker's end did not end it, so it must not go on writing the workspace after the terminal event. A runner that does not answer leaves that turn unfinished for the next pass rather than finishing it over a command that may still run. Then whatever the turn changed and never recorded — the worker died between a tool's write and its commit, so the tree is dirty — is committed as one revision in the turn's name (`bash: interrupted by a worker restart`, author `agent:<conversation id>`), under the shell and workspace locks the tool held, and the library follows the tree as after a command ([workspace.md](./workspace.md) § Revisions): the changes stay, revertible, and the next revision of any tool carries only its own; a tree that cannot be committed leaves the turn for the next pass too; the worker retries the whole cleanup every `ORPHAN_RETRY_SECONDS` (30) until it goes through, so a database or runner blip at start does not leave turns unfinished — and their conversations busy, and their users at the turn cap — until the next restart. Until the first pass has completed at all (a database blip at start), the worker claims nothing, parses included — the users whose turns wait are not known yet; once it has, and until it has gone through, the worker claims no chat turn at all and no parse of a user whose turn is still waiting: a command the dead worker left running holds no lock any more, and a new turn or a finishing parse writing the same user's tree beside it would corrupt the tree and its revisions. The sweeper does not touch turns.
