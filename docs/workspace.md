# Workspace — the per-user file tree

Every user owns one directory on the server, `{WORKSPACES_DIR}/{user_id}/`. It is where a document's editable copy, its notes, its original upload and its figure crops live — and, since 2026-10-25, every other file the reader keeps, stored once and whole (§ Files) — it is what the user's sandbox VM sees as `/workspace` ([sandbox.md](./sandbox.md)), and it is a git repository, which is how every edit — the user's, the agent's, a shell command's — becomes a revision that can be read back and undone. The workspace is deleted with the account and never otherwise: a user who stops using the service keeps their files until they delete the account themselves ([auth.md](./auth.md) § Deleting the account), and what they move to the Trash is deleted `TRASH_RETENTION_DAYS` (30) days later (§ The Trash) — its rows, its entry, its original and its images; the earlier revisions of its text stay in the history, which is never rewritten, until the account is deleted.

## Layout

```text
{WORKSPACES_DIR}/.repos/{user_id}/     the user's git directory: outside the VM's mount
{WORKSPACES_DIR}/.repos/{user_id}.images/{document_id}/   the images inserted into a document's doc.md or notes.md: outside the mount too
{WORKSPACES_DIR}/.repos/{user_id}.deleted   a deleted account's marker, JSON: the user's job ids, standing until the account's files are gone (below)
{WORKSPACES_DIR}/{user_id}/            host side; the VM mounts it as /workspace
├── .sightread/                        read-only in the VM
│   ├── results/{job_id}/result.md     the untouched parse output, written once, never edited; removed with its parse (jobs.md § Retention)
│   └── trash/                         the Trash (§ The Trash): document-<id>/, folder-<id>/, as they left files/
└── files/                             one-to-one with the Files page's folder tree
    └── <folder>/<subfolder>/
        ├── <file name>                a file of any kind: the upload itself, the one copy there is (§ Files)
        └── <document name>/           one document = one directory
            ├── doc.md                 the editable transcription (a markdown document's own text)
            ├── notes.md               the user's notes, shown beside the document
            ├── source.pdf             the shell's copy of the original upload (or source.<image ext>); the original itself is outside the mount, see below; none for a markdown document
            ├── figures/               p<page>_<y1>_<x1>_<y2>_<x2>.png, copied file by file from FIGURES_DIR, and img-<hash>.png|jpg, copied from the images directory (each missing one, on every materialization)
            └── .meta.json             document_id, job_id, model, bbox_format, page_count, kind (job_id and the parse fields null, kind markdown, for a markdown document)
```

- **A document is a directory, not a file.** Content, notes, crops, the original and the metadata travel together; a rename or a move is one `git mv`. When something else already sits at the destination — a directory a shell command made under that name — it is moved aside to a suffixed name first, so the document lands where the row says it is and the squatter keeps its content (if it was a document of its own, the next reconciliation finds it at the suffixed path); a commit that fails after the move puts both back — the document to its old place, the squatter to the name it had — so a failed request renames nothing.
- **The directory name is the document's name**, the folder path is its folders' names. The library keeps names unique per level, folders and documents in one namespace — a folder and a document cannot share a name in one parent, as on disk they would be one directory; the choice of a free name is made under a lock on the user's row, so two requests cannot pick the same one for a folder and a file ([database.md](./database.md)), and a folder's deletion reads its subtree under that same lock, so a folder created under it meanwhile is in the subtree it deletes rather than gone by cascade with its documents' originals kept — and it keeps them in NFC — a name is normalized when it is created or renamed, before it is compared with its siblings, so two spellings of one name are one name in the library as they are one directory on disk; names from before this rule are brought under it by a data migration (`normalize library names`): every folder and document name is normalized, and where two entries of one parent then share a name — a folder and a document, or two spellings — the later one (by id, folders before documents) takes the ` (2)` suffix a collision gets today, so no two rows ever map to one directory; `path_segment()` keeps them unique as directories too: separators and control characters are replaced, and a name that starts with `.` or `_`, is empty, or is one of the workspace's own names (`.sightread`, `.meta.json`, `.cache`, `.git`, and the names history excludes wherever they appear: `figures` and anything `source.*`, which as a directory name would have git ignore the document whole, its revisions never made) is kept whole behind a `_` prefix — `.report` becomes `_.report`, never `report`, and a document named `source.pdf` lives in `_source.pdf`, so two distinct names are two directories and no document directory is one the exclude rules match. A name longer than a filesystem component allows (255 bytes; library names go to 512 characters) becomes a prefix plus `~` and a hash of the whole name, so it still fits and still cannot collide.
- **The parse output stays immutable.** `results` in PostgreSQL remains the record of what the model produced; `.sightread/results/{job_id}/result.md` is a read-only copy for the agent to compare against — read-only in the VM too: `.sightread/` is a nested read-only mount over the workspace mount ([sandbox.md](./sandbox.md) § Backends), so a shell command cannot edit or delete the baseline, which history excludes and materialization never rewrites. A document filed twice from one parse gets two independent `doc.md`, both copied from that one result. `doc.md` starts from the result's reading copy when the parse was checked (`results.reading_markdown`, [parsing.md](./parsing.md) § Format check) and from the transcription otherwise; `result.md` is always the transcription.
- **A folder created on the Files page is a directory at once.** Its row and its directory under `files/` are made under one hold of the workspace lock, as a move or a delete, so the shell sees the empty folder as soon as a conversation starts rather than once a document lands in it; git records no empty directory, so the creation is no revision, and a workspace that takes no host write (recovering from an unconfirmed shell command) refuses the folder with **409** up front. An entry the shell planted where the directory belongs leaves the row standing and the tree the shell's, logged.
- **Materialization is lazy and idempotent.** A document directory is written the first time anything needs it — the viewer asking for content, a conversation starting — and at the moment a library upload's parse finishes — after its crops are published under the job's name, so the copy has them to take. `materialize_document()` writes what is missing and touches nothing that exists, so an edited `doc.md` is never overwritten by the parse result — which is also why a document whose parse has no result yet cannot be materialized at all (**409**): an empty `doc.md` written early would never be replaced. What it wrote is committed as `materialize <path>`; a materialization that finds the files in place but not at `HEAD` — the process died between the write and the commit — commits them then, so the first edit is a change against the parse baseline rather than the file's first appearance, and reverting it restores the parsed text instead of emptying the document.
- **The original upload is kept** for library documents — as `{WORKSPACES_DIR}/.repos/{user_id}.sources/{document_id}.pdf` (or `.<image ext>`, by the parse's kind, never by the upload's name), beside the git directory and like it outside anything the VM mounts, so no command, mistaken or injected, can damage the one file nothing can recreate; and a copy of it sits in the document directory as `source.*` for the shell's tools (Poppler, `pdftotext`), made again from the original on the next materialization when it is missing — the service's copy, which the quota does not count (§ Quota). Page rendering reads the original. At terminal state the worker files the source there (one original per document, when one parse was filed in several places) instead of deleting it ([jobs.md](./jobs.md) § Retention); a parse filed while it is still running is marked for retention under its row lock, so the worker finishing it at that moment either sees the new row or leaves the upload for it rather than deleting it; and a parse filed in the moment between the worker's terminal commit and its retention takes the upload as its own, and the worker copies from that original for the rows it found ([jobs.md](./jobs.md) § Retention). Each copy counts against the quota and is checked before it is made: at the worker's retention a workspace at its quota keeps no further copy, and the upload is deleted as it would be for a parse outside the library; an upload filed from the Files page whose copy the quota refuses is refused whole (**409**), the row deleted and the upload removed, since a document whose original was never kept could never render a page. A library upload that joins a parse already on its way (the same bytes, uploaded twice) keeps its own fresh copy for its row rather than relying on the worker's, which may have been handed out before the row existed; a copy that fails files nothing — the original and the shell's copy are removed and the row deleted — so no entry stands without the original it was promised and the browser's retry cannot file a suffixed twin. Parses submitted through the API or the connector are not in the library: their source is deleted when the job ends, and the parse itself `PARSE_RETENTION_DAYS` (30) days after it finished ([jobs.md](./jobs.md) § Retention). Only parsed documents keep an original outside the mount: a file of any other kind is kept once, in the tree, where the shell can use it (§ Files, decided 2026-10-25), and moving the parsed documents' originals into the tree under the same rule is the follow-up to that decision.
- **Deleting the account removes all of it** ([auth.md](./auth.md) § Deleting the account). Before the user's rows are deleted, a marker, `.repos/{user_id}.deleted`, records the user's job ids; once the deletion has committed, the user directory, the git directory, the originals, the images and the lock files are removed (a process that was already waiting for the lock when the account went creates an empty lock file again as it takes it, and that file stays) — through descriptors that follow nothing, as every host removal is (§ Revisions) — with the crop directories and the upload-directory files of those jobs, and the marker last. A process that dies after the commit leaves the marker for the worker's sweep, which finishes from it ([jobs.md](./jobs.md) § Retention); a marker whose user row still exists — the commit never landed — is only removed. Nothing else removes a user's files by inference.

### Markdown documents

A markdown document is a library entry with no parse behind it (`documents.kind` `markdown`, `job_id` NULL, [database.md](./database.md)): a `.md` file uploaded on the Files page, or a document written new there. Everything after the row is the workspace's ordinary path — the same directory, `doc.md`, `notes.md`, revisions, reconciliation, the agent — with these differences:

- **Its baseline is its original.** An uploaded `.md` is kept as the document's original, `{document_id}.md` in the sources directory beside the other originals, under the same rules (outside the mount, deleted with the row, counted against the quota, refused whole when the quota has no room). Materialization writes `doc.md` from it — decoded as UTF-8, a leading byte-order mark dropped and `\r\n` line ends made `\n` — where a parsed document's comes from its result. A document written new keeps no original and its baseline is empty. So a directory the shell removed comes back with the text the document started with, as a parsed one comes back with its parse.
- **No parse artifacts.** No `.sightread/results/…`, no crops, and no `source.*` copy: the original is the document's own first text, already in `doc.md` and in history, and a second copy beside it would only drift. `.meta.json` keeps its shape — `document_id` first, so the reconciliation's lookup still matches — with `job_id`, `model`, `bbox_format` and `page_count` null and `kind` `markdown`. The content route reports `has_source` false: there are no pages to render.
- **The upload is checked before it is filed.** The bytes stream to the upload directory under `CONTENT_MAX_BYTES`, the cap a `doc.md` is read under anyway (**413** past it), and must decode as UTF-8 (**400** otherwise); only then is the row inserted and the file kept, under the workspace lock, as a parse's upload is.


### Files

A file is a library entry that is neither parsed nor markdown (`documents.kind` `file`, [database.md](./database.md)): anything the reader uploads on the Files page that is not a PDF or an image to convert — a spreadsheet, a slide deck, an archive, a video, a text file — and, while the parse agent's `auto_convert` switch is off ([agents.md](./agents.md)), a PDF or an image kept as it is. Decided 2026-10-25: **one copy, in the tree, whole.** A file is `files/<folder>/<file name>`, the upload itself at the place the Files page shows it, which the VM mounts read-write like the rest of `files/`; there is no original beside the git directory, no `source.*` copy and no `.meta.json` — its row is found by its path. The shell reads it with its tools (`pandoc` for a Word file, Python for a spreadsheet), changes it and deletes it as it would any file, and what it writes directly into a folder is a file of the library (§ The tree is the truth). What the reader sees on the Files page and what the agent sees under `/workspace/files` are the same bytes at the same path.

- **The upload lands where it lives.** `POST /api/library/documents` streams a file to a `.sr-tmp-*` name at the top of `files/` — the destination folder is read only once the row is written — under `FILE_MAX_BYTES` (**413** past it; the Caddyfile raises its own cap on that one route, [deployment.md](./deployment.md)), the quota checked against the declared length before a byte is written and against the bytes once they are (**409** `storage_full`, the temporary file removed), and renames it into place under the workspace lock, the row inserted and committed last, as a markdown filing is, so no entry stands without its file and no file without its entry. The name is the upload's, cleaned by `path_segment()` as a document's is, with ` (2)` where the folder holds it. Nothing is read: a file's bytes are the reader's, never decoded, rendered or sent to a model unless the reader converts it (below) or the agent opens it.
- **It has no baseline.** A document that vanishes comes back from its parse or its original; a file that vanishes is gone, and its row with it (§ The tree is the truth). What stands between a mistaken `rm` and loss is the revision for a small text file (§ Revisions) and the daily backup for everything else (§ Backups) — the trade the one-copy rule makes, taken with open eyes: a document's original is kept outside the mount exactly because the agent could damage it, and a file is kept inside it exactly so the agent can use it.
- **Trash, Put Back, copies, renames and moves** are a document's (§ The Trash, § Copies): the entry in the Trash is the file itself, `document-<id>`, a copy is a copy of the bytes under the new name (the quota checked first), a rename or a move is one rename. A file has no conversations, no notes, no revisions of its own to list and no result: every document route that reads or writes those answers 404 for it ([api.md](./api.md)).
- **Converting a file.** A PDF or an image kept as a file becomes a parsed document on request (`POST …/convert`, [api.md](./api.md); the menu's *Convert to document…*, [web.md](./web.md) § Files): the row names the parse the moment it is queued, as an upload's row does, and the file is moved — not copied — out of the tree to be the job's source and then the document's original beside the git directory, where a parsed document's original lives ([jobs.md](./jobs.md) § Converting a file). Its directory is materialized at the same path when the parse lands, `source.*` standing there for the shell as for any document; a parse that fails leaves a failed document to retry, its original kept. Converting costs what a parse costs ([billing.md](./billing.md) § A parse).
- **The quota counts it once**, as part of the tree, and its row's `storage_bytes` is its size (§ Quota).

### Inserted images

An image the reader puts into a document — into `doc.md` or `notes.md`, from the editor's slash menu, a paste or a drop ([web.md](./web.md) § Editing, *Images*) — is a file of the document's, written as one line of markdown:

```
![diagram](figures/img-3f9a0c1d2e4b5a6c.png)
An optional caption, on the next line
```

- **It is stored like an original.** `POST /api/library/images` ([api.md](./api.md)) decodes the upload, turns it upright and flattens it onto white, downscales it to `DOCUMENT_IMAGE_LONG_EDGE` (2400 px; PNG stays PNG, anything else becomes JPEG, as the composer's attachments are prepared, [chat.md](./chat.md)) and keeps it as `{WORKSPACES_DIR}/.repos/{user_id}.images/{document_id}/img-<hash>.<ext>` — the first 16 hex digits of the stored file's SHA-256, so the same picture inserted twice is one file. That directory is outside the mount, beside the originals and for the same reason: the document's text points at it, and no command can damage it. A copy goes into the document directory's `figures/`, the one directory beside `doc.md` that history already excludes and that no document may be called, so the shell sees what the text names; materialization copies each missing one again, as it does the crops. The image route serves the stored file, never the shell's copy.
- **It goes with the document.** The images are deleted with the row (and swept with the originals when a delete died before its cleanup) and count against the quota. Nothing removes an image the text no longer names: a revert or an undo can bring the line back, and the line must still show its picture.
- **Only these names are images.** The viewer reads a line as an image only when it names `figures/img-` and sixteen hex digits with `.png` or `.jpg`: never a URL, so a document — an agent's edit included — cannot make the reader's browser fetch anything from anywhere else.

### The Trash

The Files page's Trash is a place in the workspace as well as a column in the database ([database.md](./database.md) § Rules): an item in the Trash has left `files/`, so the agent's shell, the library and the reconciliation no longer see it there, and it comes back whole.

- **Moving to the Trash is a move out of `files/`.** The row gets `trashed_at` and the directory moves to `.sightread/trash/document-<id>` — a file's entry (§ Files) is the file itself, under that name — (a folder's to `folder-<id>`, with everything in it) — inside the user directory, so the move is a rename on one filesystem even when each user directory is its own image ([sandbox.md](./sandbox.md) § Operations), and inside `.sightread/`, which the VM mounts read-only: the shell can read the Trash but neither edit nor empty it. The removal is one revision, `trash <path>`, as a delete's is; history excludes `.sightread/`. The original, the inserted images and the crops stay where they are, outside the mount and keyed by id. A document with no directory — never read yet, or removed by a shell command — moves nothing. Refused (409) while a conversation about a file in it is answering, as a delete is.
- **Put Back is the same move the other way.** The rows first — the place (the folder it was trashed from when that is live, else the nearest live folder above it, else the top level), a free name, `trashed_at` cleared — committed, then the directory back to where the rows now place it, as `put back <path>`, a squatter at that path moved aside as a move does. A document whose directory never existed gets one at its next read, from its baseline.
- **Nothing reads, writes or materializes a document in the Trash.** Materialization refuses a document that is not live, under the workspace lock, so every route that reads or writes one — content, notes, revisions, images, a conversation's creation, a turn's start — answers 404, and the worker's end-of-parse copy skips it. Retention still keeps a trashed document's original at the end of its parse, without the shell's `source.*` copy: that copy would make a directory under `files/` for a file that is not there. A message sent to a trashed document's conversation is refused (409) under the user's row lock, which the move to the Trash takes too.
- **One rule repairs what a crash or a failed commit leaves.** Moving to the Trash flushes the row, moves the directory, records the revision and only then commits the row; Put Back commits the rows and only then moves the directory. Either way, what an interruption can leave is an entry in the Trash whose row is not trashed itself — and such an entry goes back where its row places it: under `files/`, as a `restore` revision, when the row is live; inside the entry of the nearest trashed folder above it when the row is in the Trash with that folder. An entry whose row is gone — a delete for good that died before its cleanup — is removed. The rule runs under the workspace lock, at every reconciliation, before every Trash operation, before every copy and in materialization whenever a document's directory is missing — before anything fresh is written, so a fresh copy never stands at the path while the edits wait in the Trash. A place that is taken keeps the entry where it is, logged. A move to the Trash whose commit raised is checked on a fresh connection, as a move's is: landed, it stands; rolled back, the directory comes back on the spot.
- **Deleting for good comes last.** *Delete Immediately* on an item in the Trash, *Empty Trash* and the Trash's expiry (below) delete the rows first and remove the entries, the originals and the images once the commit is through; a process that dies in between leaves entries and originals with no rows, which the rule above and the reconciliation's sweep of orphaned originals remove. An item in the Trash still has its row, so its original and its images are never swept. The history is never rewritten, so a deleted document's earlier revisions stay in it until the account is deleted, and a later document at the same path lists them among its own (§ Revisions, *History follows the path*); the Terms and Privacy pages say so. A deleted document's parse is not deleted with it: it falls under the parse retention ([jobs.md](./jobs.md) § Retention).
- **The Trash empties itself after `TRASH_RETENTION_DAYS` (30) days.** An item whose own `trashed_at` is older than that is deleted for good by the worker's sweep (every 15 minutes, [jobs.md](./jobs.md) § Retention), exactly as *Delete Immediately* would delete it: rows first, then its entry, originals and images. An expired folder takes everything under it — an item trashed on its own inside it was trashed earlier, nothing inside a trashed folder being trashable afterwards, so it has expired too, and the entry of every deleted row that has its own `trashed_at` goes with it. *Empty Trash* and the expiry are one implementation, a workspace function with an optional cutoff (`trashed_before`) that the route calls without one; it lives in `workspace/`, with the helpers it needs, because the worker never imports a route. The sweep takes one user at a time under that user's workspace lock, which takes the backup lock shared (§ Backups); a user whose deletion is refused — a conversation about a file it would delete still answering (409), the workspace recovering from an unconfirmed shell command — is skipped, logged and tried again at the next sweep, and any other failure is logged and the sweep goes on to the next user. `0` turns the expiry off: the Trash is then emptied by the reader alone. The Trash tab says so beside its count ([web.md](./web.md) § Files); an undo step pointing at an item the sweep deleted fails as any step whose item is gone.
- **Reconciliation does not look into the Trash.** It walks `files/` only, and only live rows take part: a `.meta.json` there naming a document in the Trash — the shell copied it out of the read-only Trash, a revert brought a trashed directory's files back — is not that document, and the row stays in the Trash; a directory the shell makes under a trashed folder's name gets a folder row of its own.
- **History follows the path.** A document put back where it left keeps its revisions, its path being the same; one put back under a new name or in another folder starts a new chain there, since the rename is not one git can see across two commits.
- The Trash counts against the quota and is backed up with the rest of the user directory; the status route answers with it as a line of its own, the originals and images of the documents in it included (§ Quota).

### Copies

A copy — *Copy* and *Paste*, *Duplicate*, a drag with ⌥ on the Files page ([web.md](./web.md) § Files) — is a new entry with files of its own, made under the workspace lock with the quota checked first.

- **The rows.** A document copy is a row naming the same job, so the parse is not repeated and the copy reads the same result; a folder copy is a new folder with every live folder and document under it, in the same shape. Only the top item can meet a taken name at the destination, and it takes the ` (2)` suffix; a folder cannot be copied into its own subtree. A document whose parse is still running — its status read under the job's row lock — is marked for retention, as the Files page's upload marks its own: the copy takes its original from the source when the source holds one, else from the worker's retention when the parse ends.
- **The Trash's repair rule runs first.** A live item's files can wait in the Trash after an interrupted move (§ The Trash); the rule brings them back before anything is read, and a copy of an item whose files it could not bring back — its own entry, a folder's above it or, for a folder, an entry of anything it holds — is refused (409), never made from the baseline as if the item had never been read.
- **The files.** The directory is copied file by file through descriptors that follow nothing, as every host write is — links and special files are left out — with `.meta.json` written fresh for the new id and the regenerable parts left behind: `source.*` and `figures/` come from the original, the crops and the images at the copy's first materialization, and `.sr-tmp-*` is never copied. The original and the inserted images are copied under the new ids. A file of the library (§ Files) is its bytes alone, copied under the new name. The copy is one revision, `copy <from> -> <to>`. A document never materialized is copied as its row, its original and its images; its directory comes at its first read, from the baseline, as the original's would. So does the directory of a document whose parse is still running, which holds nothing of the document yet: it is not copied, and the copy's comes when the parse ends.
- **Not copied:** conversations and memories, which are about the original, and anything in the Trash, a trashed item inside a copied folder included.
- **A copy is whole or not at all.** A copy the tree refuses, or whose revision cannot be recorded, removes what it made — the directory, the originals and the images under the new ids — before the rows roll back; a commit that raises is checked on a fresh connection, as a filing's is, and a copy that did not land is removed as a revision of its own.

## Revisions

The user directory is the work tree of one git repository whose git directory lives **outside it**, at `{WORKSPACES_DIR}/.repos/{user_id}`; `sightread.workspace.git` is the only module that runs git (as a subprocess with `--git-dir` and `--work-tree` named explicitly, never the user's global config). The VM mounts only the user directory, so nothing a shell command does can reach the repository's configuration or hooks: git runs on the host, in the worker and the API, and a hook planted from the sandbox would run there with their credentials. The ignore rules live in the git directory too (`info/exclude`), not in a `.gitignore` the shell could edit — and staging consults no other ignore rule: every commit lists what it stages by the workspace's own exclusions alone (`.sightread/`, `.cache/`, `source.*`, `figures/`, `.sr-tmp-*`, given to `git ls-files --modified --deleted --others`, which reads no `.gitignore` unless asked) and stages exactly that list with `--force` — less, since files of any kind live in the tree (§ Files), every file that is not `doc.md`, `notes.md` or `.meta.json` and is binary (a NUL byte in its first 8 KiB, git's own test) or larger than `REVISION_MAX_FILE_BYTES` (1 MiB), wherever it sits: history records text, and a spreadsheet, a video or a 200 MB CSV is never hashed into the object store, counted twice (§ Quota) or packed; a small text file — a CSV, a script, a note the agent wrote — is recorded and reverted like `doc.md`, and the editor tool writes only what a revision would record ([chat.md](./chat.md) § Tools) — so a `.gitignore` a command writes into the tree hides nothing from history — a file it names is committed like any other, revertible like any other, and only the fixed exclusions and the size and binary rule stay out. An excluded file is never hashed either: until 2026-10-25 staging added everything and took the exclusions back out of the index afterwards, and every `source.*` copy and every crop stayed behind in the object store as an unreachable blob, counted against the quota (§ Quota) and never removed. A `.git` directory the shell creates inside the tree is just a directory to the host's git (ignored at the root, a gitlink below it); it never becomes the repository.

- **Fixed files are regular files.** `doc.md`, `notes.md`, `.meta.json`, the `source.*` copy and the crops are read and written by the host, so the host never opens one by path: `safe_io` walks from the user root one component at a time with `O_NOFOLLOW` and inspects what it opened through the descriptor — a plain file where a file belongs, a directory where a directory belongs, nothing else — before a byte is read or written. A check followed by an open would be a race against a shell that can swap the entry in between; the open is the check. A directory that is missing on the way is created one component at a time through the descriptor of the one above (`mkdir` relative to it, then opened without following), never by a path the shell could redirect. A write goes to a temporary file beside its destination (`.sr-tmp-*`, excluded from history), opened through the same directory descriptor, and is renamed over the destination only once every byte is written: a save that fails halfway — the disk full, the process gone — leaves `doc.md` as it was, never empty or cut short. Poppler is handed the original as an open descriptor (`/proc/self/fd/N`), never as a path to resolve again. Directory listings (reconciliation's walk of `files/` included — a `files/` the shell replaced with a link is an empty tree to it, never another user's), deletions, moves and the copy of a document's crops go the same way: a listing reads through a directory descriptor, a delete unlinks entry by entry through descriptors (a link is unlinked, never entered), and a move — tracked or not — renames through the two directories' descriptors and stages the old and the new path afterwards; git's own `mv` is not used, because it follows a link in an ancestor. A shell command that replaced `doc.md` with a link to `/proc/self/environ`, a link to another user's tree or a named pipe gets **409** from the content routes and an error result from the tools, never the target's bytes. The same goes for size: a `doc.md` or `notes.md` past `CONTENT_MAX_BYTES` (8 MiB) is refused before it is read, and a save or an editor write that would make one that large is refused before it is written, so a file the shell inflated cannot take the API's memory with it and the viewer cannot inflate one itself. A `doc.md` that is not UTF-8 is refused the same way (**409**). A `.meta.json` past 64 KiB is not a document's to reconciliation, and one id found in two places (a `cp -r` carries the file along) leaves the row where it is; a diff the shell's commit produced is read up to the tool-result cap and no further.

- **A tree a shell command may still be writing takes no host write.** A shell command holds the shell and workspace locks for its whole run, and sets a marker beside them (`{WORKSPACES_DIR}/.repos/{user_id}.writing`, naming its conversation and shell session) for as long as it may write; the locks die with the worker, the marker does not, and a command the runner could not confirm over leaves it standing too ([chat.md](./chat.md) § Tools). A marker that stands but cannot be read — a worker killed as it wrote it, though the marker is written whole and renamed into place so that cannot leave a half one — names no shell: the recovery stops the user's VM whole before it records the tree, or leaves the workspace closed when no runner can. A workspace lock acquired while the marker stands is refused with **409** (*the workspace is recovering from a shell command that could not be confirmed finished*), reads under the lock included, until a restart of that shell on the runner has confirmed the command dead and the tree is recorded: by the command's own turn, by the next worker's recovery of an orphaned turn (the orphan revision), or by the sweep every worker runs at start over the markers still standing, which restarts the shell each one names and records the tree as `bash: recovered after an unconfirmed command` ([jobs.md](./jobs.md) § Chat turns); a runner that does not answer — or a worker with no runner configured to ask — leaves the marker, and the refusals, in place for the next pass. Only those recoveries and the shell path itself take the lock past the marker.
- Every write through the API or a tool commits: `doc.md` saves from the viewer, `notes.md` saves, a re-convert taking the document over (`doc.md` and `.meta.json` as one revision, `reconvert <path>`, its crops beside them; [jobs.md](./jobs.md) § Re-converting a document), every edit the agent's editor tool makes, and whatever a shell command changed — after each tool call the runner commits a dirty tree. The commit author names who did it (`user` or `agent` with the conversation id), the message names the file and the tool. A turn a dead worker left between a tool's write and its commit is finished by the next worker, which commits what it left as `bash: interrupted by a worker restart` in the turn's name first ([jobs.md](./jobs.md) § Chat turns), so no revision carries another tool's changes.
- **Writes are serialized per user** by a lock in the workspace module — held through a file beside the git directory, outside the VM's mount, so a shell cannot unlink it from under its holders. It is taken before any database row lock, everywhere — the order is the workspace, then the user's row, then a job's row, and nothing takes them the other way round (the worker's retention of an original takes the workspace before the job's row; a filing takes the workspace, then the user's row, then the job's; a Files-page mutation takes the workspace before the user's): a Files-page move or delete, a save (which resolves the document's path under it, so a rename landing in between cannot send the text to a path that no longer exists), a revert and its guard, and reconciliation, which also takes the user's row under it, since it may add a folder row — the same row the Files page's name decisions lock, so a folder the shell made and a file the user creates cannot take one name. The holders: the user editing in the viewer, two conversations editing in parallel and a rename must not interleave their index operations. A host write commits only the paths it wrote (`git add -A -- <paths>`; a path that matches nothing is skipped, any other failure to stage or to commit is an error, never a save reported done without its revision — and the index is reset on the way out, so nothing half-staged rides into the next commit, which commits the whole index), so a shell command's half-written files elsewhere in the tree never ride along in a save's revision; the shell's own commit stages everything, and for that reason one shell command runs at a time per user, under a second lock held from the command's start through its commit — and the workspace lock is held across the command as well, so a save or another conversation's editor waits for a running command rather than reading and committing a file it is half-way through writing ([chat.md](./chat.md) § Tools). A rename, move or delete on the Files page holds that lock across its database write *and* the directory move, so no read can materialize a fresh copy at the new path in between — and the two are one outcome: the row change is flushed, the directory is moved, and only then is the transaction committed, so a move the tree refuses (an entry the shell planted, an I/O error) rolls the row back to where the files still are — and a move whose revision cannot be recorded is undone on the spot, the directory and anything moved aside for it put back, before the refusal; and a commit that fails after the move puts the directory back where the row stayed, as a revision of its own, so no fresh copy is materialized at the old path beside the moved one. A delete moves the directory aside — to a `.sr-tmp-` entry at the user root, outside `files/` and outside history — and commits the removal before its rows commit; once the rows are gone the entry is deleted. A move the tree refuses leaves the row, and the next read restores whatever files are missing; a removal whose revision cannot be recorded moves the directory back before the refusal, so nothing waits aside for a sweep to take. A commit that fails *after* the move — the database away at that moment — moves the directory back whole, originals and crops included, and records a `restore` revision, so the row that stayed keeps everything; an entry left aside by a crash in between is removed by the next reconciliation, which runs under the same lock.
- **A revert is refused (409) while a turn could be working on what it would touch.** A revision whose paths all lie in this document's directory — each path mapped through the renames made since, so a document moved since still owns its older revisions, and the revision that renamed the document itself counts as its own, the old side of its rename pair included, but only for a rename of the document itself: the old path ends with the same path inside the document and the directory it came from is gone, while a file a command moved in from another document is that document's revision too, and reaches beyond — waits only for this document's conversations; a revision whose paths cannot be read within the log bound is treated as reaching beyond; a revision that reached beyond it (a shell revision that edited or moved other documents) is refused while *any* conversation of the user has an unfinished turn, since the turn's shell or editor may be on those files. Decided under the workspace lock, before anything is read or written for the revert — the materialization that precedes a revert comes after the guard, so a refused revert never hands a turn between tool calls a fresh copy of a document it just removed. A revert is a revision before the rows follow it: should reconciliation fail after the revert's commit (the database away at that moment), the request says so — reverted, library not yet in line — rather than reporting a revert that did not happen, and the rows follow at the next read of the document or the next turn's reconciliation: a materialization that finds the row's directory missing while `HEAD` holds the document's `.meta.json` elsewhere reconciles first, so no fresh copy is written beside the moved one.
- **A move whose commit raised is checked before it is undone.** A Files-page move commits its row after the directory moved; a commit that raises usually rolled back, and the directory goes back where the row stayed — but the connection can drop after PostgreSQL made the commit durable, so the row is read again on a fresh connection first, and when it holds the new path the files stay where it points rather than being moved away from the row that now names them; a row that cannot be read at all (the database away) is indeterminate, not a rollback, and the files stay too — the next reconciliation follows the directory. A delete whose commit raised is checked the same way: a row found gone means the delete landed and finishes as if acknowledged (the directory set aside is discarded, the originals with it; a process that dies between the rows' commit and that cleanup leaves the originals beside the git directory, and the next reconciliation removes every original whose document row is gone, since every writer of an original holds the workspace lock it runs under); a row still there, or one that cannot be read, brings the directory back — an orphaned directory beside no row is a nuisance, files gone with a row that stayed is a loss. A filing (the Files page's upload, of a parse or of a markdown file) whose commit raised is checked the same way: the row present on a fresh connection means the commit landed and the acknowledgement was lost, and the filing is answered as made — reported as nothing filed, the browser's retry would file a suffixed twin of the same parse; the row absent means it rolled back, and nothing was filed — the original and the shell's copy the filing took for the row go with it, so no file stands for a row that is gone and the retry lands under the same name; a row that cannot be read is answered as unconfirmed, with the library to be reloaded before a retry. The same holds when the process dies between the removal's revision and the rows' commit: the directory waits aside, and the next reconciliation reads the `.meta.json` inside each aside directory, and the origin written beside each aside with the removal — written before the directory moves, so a process that dies between the two leaves a marker beside no aside, which the next reconciliation sweeps with the directory standing where it was, never an aside that no marker names — (`.sr-tmp-*.origin`: the path the directory was removed from; gone with the aside). An aside that holds no document metadata at all — a folder of shell-made files, a document whose `.meta.json` a command removed — goes back whole to its origin when a folder or document row still names that path, and is swept only when none does. When every document in the aside still has its row and those rows all place the aside at one path — a folder's directory, set aside whole — it goes back whole as one `restore` revision, with whatever else the folder held (files and directories the shell made, which no row names) rather than only its documents; when that place is taken, or the aside is one document's, each document whose row survived goes back where the row says (an aside that still holds one that could not go back, its place taken or the move unrecordable, is kept), and only an aside with no surviving row is swept. A filing takes the workspace lock across its quota check and its copy of the original, so two filings at once cannot both measure the room and both take it.
- **A host write whose revision cannot be recorded is undone.** A save, a notes save or an editor write that git cannot stage or commit (the disk full) puts the file back as it was — a created file is removed, and with it the directories the create made for it, so a failed create leaves no empty folder for the next reconciliation to record as a row — and answers 409 (the editor reports the failure to the model), so no unrecorded change waits in the tree for a shell's next commit to absorb as its own; a materialization whose commit fails removes the files it wrote, so the next read writes and commits them again rather than finding them present and leaving them unrecorded forever. A content read holds the workspace lock from the materialization through the read, so a shell command cannot move the directory or rewrite `doc.md` under it.
- **A revert whose revision cannot be recorded is rolled back.** If staging or committing the revert fails (the disk full), the index is reset, the moves are undone, the paths the revert touched — those alone, since the tree may hold edits a failed shell commit left unrecorded elsewhere, which are not this revert's to discard — are put back as they were before the revert began (their bytes are held from the preflight, so an unrecorded edit to the very file being reverted survives too; a file too large to hold is restored from the head revision) and the files the revert wrote are removed, so the tree is as it was and no later save or shell commit can absorb an unrecorded revert; the route answers 409.
- **A reverted rename takes the directory's untracked assets with it.** History records text only, so a rename of a document directory is, to git, a rename of its tracked files; the revert moves those back one by one and then moves whatever the vacated directory still holds — `source.*`, `figures/` — to the restored one (never over an entry already there), so the original and the crops land where the document is again, and the empty directory is pruned.
- **Revisions follow renames.** The history a document lists is its directory's log merged with `git log --follow` of its `doc.md` and `notes.md`, so the edits made before it was renamed or moved (or a folder above it was) stay listed; a revert reads each file where it lived at that commit, so they stay revertible too.
- `revision` in the API is the SHA-256 of the file's current content, not a commit id: a save carries the `base_revision` it was made from, and a save whose base no longer matches the file is refused with **409** — the client reloads and the reader sees what changed in between. The git log is the history the UI lists — read up to a bound (`WORKSPACE_LOG_MAX_BYTES`, 4 MiB of log, and `WORKSPACE_LOG_FILES_MAX`, 200 paths per revision; the rename and path lists a revert reads are read under the same byte bound and a revert may touch at most `REVERT_MAX_PATHS` (2000) paths — past either it is refused (**409**), so a shell revision over a workspace's worth of tiny files cannot have the API hold its metadata or spawn a `git show` per file under the lock; a shell that commits ten thousand files sees its revision listed with the first two hundred and a count, and a revision whose own list reaches the bound is still listed, with what fit and a marker), never buffered whole; `revert` writes every path the commit touched as it was before it — a shell revision may reach beyond one document — each at the place it lives now if it was moved since, and commits that, so undoing is itself a revision and nothing is ever rewritten. A file the commit created is removed (a document's `doc.md` or `notes.md` is emptied instead, so the directory keeps its shape); a rename the commit made is moved back (and the file's bytes restored as they were before it, when the commit edited it too), and the library is reconciled afterwards so the row follows the directory. Every restoration is resolved and read before the first write, so a revision that cannot be restored (a file past the cap, more than `REVERT_MAX_BYTES` (64 MiB) of restored content in all — a shell revision that touched a workspace's worth of files is not undone from the API's memory — an entry that is not a plain file, a rename whose old place is occupied again — a revert never overwrites what sits there now) leaves the tree exactly as it was. The route answers with the commit the revert made, which is what the thread's *Apply again* reverts in turn.
- `source.*`, `.sightread/`, the sandbox's package cache and every binary or large file (above) are excluded from history, and from the object store: it records text, not binaries.
- **The history is packed.** Git writes each revision as a loose object, a whole compressed copy of the file; packed, a revision is a delta against a similar one (a `doc.md` saved 180 times took 30 MB loose and about 1 MB packed). The worker's sweep ([jobs.md](./jobs.md) § Retention, at start and every 15 minutes) packs every repository holding `WORKSPACE_GIT_PACK_LOOSE_OBJECTS` (100) loose objects or more with `git gc --prune=now`, under the workspace lock: every writer of the object store holds it, so nothing staged and not yet committed is pruned, and the backup lock it takes shared keeps a snapshot from catching a repository between its new pack and its deleted loose objects. A workspace whose lock is refused (a shell command still being recovered) waits for the next sweep. Git's own automatic gc is off on every call (`gc.auto=0`, `maintenance.auto=false`): it would run detached after a commit, outside both locks.
- Every git call the host makes is bounded in time by `WORKSPACE_GIT_TIMEOUT_SECONDS` (60) — the bounded readers watch the deadline while they read, so a git that stalls after a few bytes cannot hold a worker thread and the workspace lock indefinitely — and the call fails rather than waits.

## The tree is the truth

A shell command in the sandbox can `mkdir`, `mv` and `rm` under `/workspace/files`. After every conversation turn the runner reconciles the tree with the database: each `.meta.json` names its `document_id`, so a moved or renamed directory updates the row's folder and name, and a folder that appeared becomes a `folders` row — an empty one too, so a `mkdir` from the shell shows on the Files page; a folder directory the shell renamed gets a row under its new name and keeps the old one, since rows are never deleted here, and the empty row is the user's to remove. Reconciliation never deletes a document's or a folder's row (a file's is the one exception, below): a document directory that disappeared is materialized again from its baseline — the parse result, or a markdown document's original — on its next read, and deleting a document is done from the Files page, where it is deliberate. Only live rows take part: a folder or document in the Trash is matched to no directory and moved by no shell command (§ The Trash). A directory without `.meta.json` is not a document, and a document comes into the library only from the Files page (an upload, a copy, a new markdown document), never from the tree. **A plain file directly in a folder is a file of the library** (§ Files): one the shell wrote, copied in or renamed gets a `documents` row of kind `file` at its path — its name as typed where `path_segment()` allows it, else moved to the segment it encodes to, as a directory is; its type from its extension, its size from the walk — and shows on the Files page after the turn; one that moved is a new row at the new path, the old row gone with the old path; and **a file that is gone from the tree is gone from the library** — the one row reconciliation removes, since nothing could bring the file back and a row that opens to nothing is worse than none. The shell's command stays in the conversation's events, and the daily backup is the copy there is (§ Backups). A file inside a document's directory is the document's own, as before, and a plain file whose name a document or folder row already holds at that path is logged and left where it is. A directory nested under a document's directory is never recorded as a folder: a folder row under a document's name would share that document's directory, so a document a command moved inside another is not found there and is left where its row says.

A document directory that took a sibling folder's name — the shell removed `files/Reports` and moved a document there — is logged and its row left as it was: a document and a folder cannot share a name in one parent, as on disk they would be one directory, and `folders` and `documents` are separate tables whose constraints would not catch it. Rows that trade places — one command swapped two document directories — are updated in two phases, every changing row first taking a name nothing holds, so the swap never meets the unique constraint on its way and the rows follow the directories instead of the whole reconciliation being abandoned with each row pointing at the other's files.

Reconciliation holds the user's workspace lock from the scan through the row updates and their commit — the same lock a rename on the Files page holds across its database write and its move — so neither can apply a path the other has just changed. It runs after turns and when the API itself moved something; it is not a watcher. A change made from the shell between turns shows on the Files page after the next turn.

A directory the shell named in a way `path_segment()` would not — `.report`, `_report` — is first moved to the segment that name encodes to (`_.report`, `__report`, one commit under the workspace lock; a commit that fails undoes the moves, so no directory is stranded under a name its row does not hold, and the next reconciliation tries again) and then recorded under the name as typed, so the row's name and its directory agree and the next read finds the shell's edits instead of materializing a fresh copy beside them. A directory whose canonical path is already taken is left where it is and logged, never recorded.

Reconciliation stops at a document's directory: once a `.meta.json` is found, nothing beneath it is scanned — the sub-directories a shell made inside a document (an `analysis/` of scratch files, an extracted archive) are the document's own, never canonicalized or recorded as folders, and a document that holds a workspace's worth of small directories costs the reconciliation one look, not one per directory.

## Quota

The user's storage is their plan's — `FREE_STORAGE_BYTES` (512 MB) on Free, the plan's `storageBytes` on a paid one, never past the deployment's ceiling `WORKSPACE_QUOTA_BYTES` (default 10 GiB) ([billing.md](./billing.md) § Plans). It is the size the Usage page shows the workspace against and the point past which the API refuses to materialize another document and a chat send (**409** `storage_full`, so a client can tell it from every other 409 and point at the plan), and a turn already queued fails before it starts — no shell runs in a full workspace. Nothing is deleted when a plan lapses: over the cap the user can read and delete, not add. Hard enforcement is the operator's: mount `{WORKSPACES_DIR}` on a filesystem with per-directory quotas, or back each user directory with a fixed-size image ([sandbox.md](./sandbox.md) § Operations). What counts is what the user holds, each thing once (decided 2026-10-25: Usage read five times what the Files page listed, a PDF counting as its original, the shell's copy and a blob git kept of that copy, § Revisions):

- **Counted:** every original and every inserted image (beside the git directory), everything in the tree — `doc.md`, `notes.md`, `.meta.json`, every file of the library (§ Files), whatever a shell command wrote, the sandbox's package cache — the Trash, and the git directory, packed (§ Revisions).
- **Not counted: the service's own copies**, which it makes and makes again: a document directory's `source.*` when it is the size of the document's original with that extension, a file in its `figures/` the size of the stored image of that name (§ Inserted images) or of the crop of that name from the document's parse (`FIGURES_DIR/{job_id}/`, whose crops count against no one), and `.sightread/results/` (the database's result, copied for the agent). A document directory is one whose `.meta.json` names a document of the user's, the first one found when two do; each original, image and crop excuses one copy at most, so a shell that writes `.meta.json` files and copies of the right size elsewhere moves an exemption, never adds one. The disk still holds the copies — about twice what is counted for a PDF — which is the operator's to plan for.
- **Three lines.** *Files*: the live documents — each one's directory, original and images — and the rest of the tree outside the Trash. *Trash*: `.sightread/trash/` and the originals and images of the documents in it, a document with no directory there included. *History*: the git directory. The status route answers with the three and their sum (`GET /api/sandbox`, [api.md](./api.md)), and the library carries each document's share as `storage_bytes` — a file's is its size — what the Files page lists as its size, so the documents add up to the *Files* line, the rest of the tree aside ([web.md](./web.md) § Files).
- **Measured by walking**, through directory descriptors that follow nothing, like every other look at the tree, so a link the shell plants cannot send the walk into another user's files; one descriptor per level of depth, and no deeper than 512 levels — a tree nested past that cannot be measured, the Usage page and the quota answer **409** naming it, the Files page lists no sizes, and deleting the document or folder that holds it, which removes a tree of any depth with a handful of descriptors by folding its deepest levels up as it goes, is the way out.

## Backups

The workspace is primary data from this version on — the parse output can be recreated from PostgreSQL, the edits, notes and originals cannot. The production backup service archives `{WORKSPACES_DIR}` with the database dump ([deployment.md](./deployment.md)), and the two are one snapshot: every workspace and shell lock is taken *shared* on `{WORKSPACES_DIR}/.repos/backup.lock` first, and the backup holds that file exclusively from the start of the dump to the end of the archive, so no rename, save, shell commit or reconciliation lands between the rows and the tree it captures. Writes wait for the backup, not the other way round — keep the backup short (a filesystem snapshot under it, where the operator has one, is the way to make it instant) — and the one place a file of the library (§ Files) that a command deleted or overwrote can be read back from, since a binary or a large file has no revision, so a deployment whose libraries grow should move to a snapshot before the nightly archive outgrows its window. A writer whose database commit comes *before* its workspace write — the worker finishing a parse, which commits the result and then files the original and the copy — holds the backup lock shared on its own (`backup_shared`, no workspace lock) from before the commit until the files are in place, so a snapshot never carries rows for a copy or an original that is still on its way in the upload directory, which is not backed up. The Files page's upload goes the other way round: under the workspace lock, the row is inserted, its original taken into place, and the transaction committed last, so a process that dies in between leaves no row without the original it was promised; the backup lock is held shared around the whole of it. The workspace lock taken inside that hold takes the backup lock shared again, which a shared hold never refuses. A writing marker (`.repos/<user>.writing`, § Revisions) is the one write the lock does not cover: the VM behind it may still be writing with no lock held, so the backup waits for the markers to clear, bounded by `BACKUP_WRITING_WAIT_SECONDS`, and when one still stands archives anyway — a late backup beats none — naming it in the stamp's `unconfirmed-writes.txt` ([deployment.md](./deployment.md)); the tree it names is complete up to its last revision, with possibly a file mid-write beyond it. Nothing is removed from a stamp once it is written: what is deleted — an item from the Trash, a purged parse, a whole account — leaves the backups as the stamps that hold it rotate out, and with the newest seven daily stamps kept it is gone from them about a week later ([deployment.md](./deployment.md)).
