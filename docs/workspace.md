# Workspace — the per-user file tree

Every user owns one directory on the server, `{WORKSPACES_DIR}/{user_id}/`. It is where a document's editable copy, its notes, its original upload and its figure crops live, it is what the user's sandbox VM sees as `/workspace` ([sandbox.md](./sandbox.md)), and it is a git repository, which is how every edit — the user's, the agent's, a shell command's — becomes a revision that can be read back and undone. The workspace is never deleted: a user who stops using the service keeps their files until the operator removes the account.

## Layout

```text
{WORKSPACES_DIR}/.repos/{user_id}/     the user's git directory: outside the VM's mount
{WORKSPACES_DIR}/{user_id}/            host side; the VM mounts it as /workspace
├── .sightread/
│   └── results/{job_id}/result.md     the untouched parse output, written once, never edited
└── files/                             one-to-one with the Files page's folder tree
    └── <folder>/<subfolder>/
        └── <document name>/           one document = one directory
            ├── doc.md                 the editable transcription
            ├── notes.md               the user's notes, shown beside the document
            ├── source.pdf             the original upload (or source.<image ext>)
            ├── figures/               p<page>_<y1>_<x1>_<y2>_<x2>.png, copied file by file from FIGURES_DIR (each missing one, on every materialization)
            └── .meta.json             document_id, job_id, model, bbox_format, page_count
```

- **A document is a directory, not a file.** Content, notes, crops, the original and the metadata travel together; a rename or a move is one `git mv`. When something else already sits at the destination — a directory a shell command made under that name — it is moved aside to a suffixed name first, so the document lands where the row says it is and the squatter keeps its content (if it was a document of its own, the next reconciliation finds it at the suffixed path).
- **The directory name is the document's name**, the folder path is its folders' names. The library keeps names unique per level, folders and documents in one namespace — a folder and a document cannot share a name in one parent, as on disk they would be one directory; the choice of a free name is made under a lock on the user's row, so two requests cannot pick the same one for a folder and a file ([database.md](./database.md)) — and it keeps them in NFC — a name is normalized when it is created or renamed, before it is compared with its siblings, so two spellings of one name are one name in the library as they are one directory on disk; `path_segment()` keeps them unique as directories too: separators and control characters are replaced, and a name that starts with `.` or `_`, is empty, or is one of the workspace's own names (`.sightread`, `.meta.json`, `.cache`, `.git`) is kept whole behind a `_` prefix — `.report` becomes `_.report`, never `report`, so two distinct names are two directories. A name longer than a filesystem component allows (255 bytes; library names go to 512 characters) becomes a prefix plus `~` and a hash of the whole name, so it still fits and still cannot collide.
- **The parse output stays immutable.** `results` in PostgreSQL remains the record of what the model produced; `.sightread/results/{job_id}/result.md` is a read-only copy for the agent to compare against. A document filed twice from one parse gets two independent `doc.md`, both copied from that one result.
- **Materialization is lazy and idempotent.** A document directory is written the first time anything needs it — the viewer asking for content, a conversation starting — and at the moment a library upload's parse finishes. `materialize_document()` writes what is missing and touches nothing that exists, so an edited `doc.md` is never overwritten by the parse result — which is also why a document whose parse has no result yet cannot be materialized at all (**409**): an empty `doc.md` written early would never be replaced.
- **The original upload is kept** for library documents, as `source.pdf` or `source.<image ext>` by the parse's kind, never by the upload's name: at terminal state the worker moves the source file into the document directory (a copy into each, when one parse was filed in several places) instead of deleting it ([jobs.md](./jobs.md) § Retention), so the agent can re-render a page with Poppler. Each copy counts against the quota and is checked before it is made: a workspace at its quota keeps no further copy, and the upload is deleted as it would be for a parse outside the library. A library upload that joins a parse already on its way (the same bytes, uploaded twice) keeps its own fresh copy for its row rather than relying on the worker's, which may have been handed out before the row existed. Parses submitted through the API or the connector are not in the library and keep today's rule — their source is deleted.

## Revisions

The user directory is the work tree of one git repository whose git directory lives **outside it**, at `{WORKSPACES_DIR}/.repos/{user_id}`; `sightread.workspace.git` is the only module that runs git (as a subprocess with `--git-dir` and `--work-tree` named explicitly, never the user's global config). The VM mounts only the user directory, so nothing a shell command does can reach the repository's configuration or hooks: git runs on the host, in the worker and the API, and a hook planted from the sandbox would run there with their credentials. The ignore rules live in the git directory too (`info/exclude`), not in a `.gitignore` the shell could edit. A `.git` directory the shell creates inside the tree is just a directory to the host's git (ignored at the root, a gitlink below it); it never becomes the repository.

- **Fixed files are regular files.** `doc.md`, `notes.md`, `.meta.json`, `source.*` and the crops are read and written by the host, so the host never opens one by path: `safe_io` walks from the user root one component at a time with `O_NOFOLLOW` and inspects what it opened through the descriptor — a plain file where a file belongs, a directory where a directory belongs, nothing else — before a byte is read or written. A check followed by an open would be a race against a shell that can swap the entry in between; the open is the check. A directory that is missing on the way is created one component at a time through the descriptor of the one above (`mkdir` relative to it, then opened without following), never by a path the shell could redirect. A write goes to a temporary file beside its destination (`.sr-tmp-*`, excluded from history), opened through the same directory descriptor, and is renamed over the destination only once every byte is written: a save that fails halfway — the disk full, the process gone — leaves `doc.md` as it was, never empty or cut short. Poppler is handed the original as an open descriptor (`/proc/self/fd/N`), never as a path to resolve again. Directory listings (reconciliation's walk of `files/` included — a `files/` the shell replaced with a link is an empty tree to it, never another user's), deletions, moves and the copy of a document's crops go the same way: a listing reads through a directory descriptor, a delete unlinks entry by entry through descriptors (a link is unlinked, never entered), and a move — tracked or not — renames through the two directories' descriptors and stages the old and the new path afterwards; git's own `mv` is not used, because it follows a link in an ancestor. A shell command that replaced `doc.md` with a link to `/proc/self/environ`, a link to another user's tree or a named pipe gets **409** from the content routes and an error result from the tools, never the target's bytes. The same goes for size: a `doc.md` or `notes.md` past `CONTENT_MAX_BYTES` (8 MiB) is refused before it is read, and a save or an editor write that would make one that large is refused before it is written, so a file the shell inflated cannot take the API's memory with it and the viewer cannot inflate one itself. A `doc.md` that is not UTF-8 is refused the same way (**409**). A `.meta.json` past 64 KiB is not a document's to reconciliation, and one id found in two places (a `cp -r` carries the file along) leaves the row where it is; a diff the shell's commit produced is read up to the tool-result cap and no further.

- Every write through the API or a tool commits: `doc.md` saves from the viewer, `notes.md` saves, every edit the agent's editor tool makes, and whatever a shell command changed — after each tool call the runner commits a dirty tree. The commit author names who did it (`user` or `agent` with the conversation id), the message names the file and the tool.
- **Writes are serialized per user** by a lock in the workspace module — held through a file beside the git directory, outside the VM's mount, so a shell cannot unlink it from under its holders. It is taken before any database row lock, everywhere — the order is the workspace, then the user's row, then a job's row, and nothing takes them the other way round (the worker's retention of an original takes the workspace before the job's row; filing takes the user's row before the job's; a Files-page mutation takes the workspace before the user's): a Files-page move or delete, a save (which resolves the document's path under it, so a rename landing in between cannot send the text to a path that no longer exists), a revert and its guard, and reconciliation, which also takes the user's row under it, since it may add a folder row — the same row the Files page's name decisions lock, so a folder the shell made and a file the user creates cannot take one name. The holders: the user editing in the viewer, two conversations editing in parallel and a rename must not interleave their index operations. A host write commits only the paths it wrote (`git add -A -- <paths>`; a path that matches nothing is skipped, any other failure to stage is an error, never a save reported done without its revision), so a shell command's half-written files elsewhere in the tree never ride along in a save's revision; the shell's own commit stages everything, and for that reason one shell command runs at a time per user, under a second lock held from the command's start through its commit ([chat.md](./chat.md) § Tools). A rename, move or delete on the Files page holds that lock across its database write *and* the directory move, so no read can materialize a fresh copy at the new path in between — and the two are one outcome: the row change is flushed, the directory is moved, and only then is the transaction committed, so a move the tree refuses (an entry the shell planted, an I/O error) rolls the row back to where the files still are. A delete removes the directory before its rows commit; a removal that fails midway leaves the row, and the next read restores whatever files are missing.
- **Revisions follow renames.** The history a document lists is its directory's log merged with `git log --follow` of its `doc.md` and `notes.md`, so the edits made before it was renamed or moved (or a folder above it was) stay listed; a revert reads each file where it lived at that commit, so they stay revertible too.
- `revision` in the API is the SHA-256 of the file's current content, not a commit id: a save carries the `base_revision` it was made from, and a save whose base no longer matches the file is refused with **409** — the client reloads and the reader sees what changed in between. The git log is the history the UI lists — read up to a bound (4 MiB of log, 200 paths per revision; a shell that commits ten thousand files sees its revision listed with the first two hundred and a count, and a revision whose own list reaches the bound is still listed, with what fit and a marker), never buffered whole; `revert` writes every path the commit touched as it was before it — a shell revision may reach beyond one document — each at the place it lives now if it was moved since, and commits that, so undoing is itself a revision and nothing is ever rewritten. A file the commit created is removed (a document's `doc.md` or `notes.md` is emptied instead, so the directory keeps its shape); a rename the commit made is moved back (and the file's bytes restored as they were before it, when the commit edited it too), and the library is reconciled afterwards so the row follows the directory. Every restoration is resolved and read before the first write, so a revision that cannot be restored (a file past the cap, more than `REVERT_MAX_BYTES` (64 MiB) of restored content in all — a shell revision that touched a workspace's worth of files is not undone from the API's memory — an entry that is not a plain file, a rename whose old place is occupied again — a revert never overwrites what sits there now) leaves the tree exactly as it was. The route answers with the commit the revert made, which is what the thread's *Apply again* reverts in turn.
- `source.*`, `.sightread/` and the sandbox's package cache are excluded from history: it records text, not binaries.

## The tree is the truth

A shell command in the sandbox can `mkdir`, `mv` and `rm` under `/workspace/files`. After every conversation turn the runner reconciles the tree with the database: each `.meta.json` names its `document_id`, so a moved or renamed directory updates the row's folder and name, and a folder that appeared becomes a `folders` row. Reconciliation never deletes a row: a document directory that disappeared is materialized again from the parse result on its next read, and deleting a document is done from the Files page, where it is deliberate. A directory without `.meta.json` is not a document — a file the agent wrote is visible to the agent and in the sandbox, not in the library; `documents.job_id` stays required. A directory nested under a document's directory is never recorded as a folder: a folder row under a document's name would share that document's directory, so the document inside it is logged and left where its row says.

Reconciliation holds the user's workspace lock from the scan through the row updates and their commit — the same lock a rename on the Files page holds across its database write and its move — so neither can apply a path the other has just changed. It runs after turns and when the API itself moved something; it is not a watcher. A change made from the shell between turns shows on the Files page after the next turn.

A directory the shell named in a way `path_segment()` would not — `.report`, `_report` — is first moved to the segment that name encodes to (`_.report`, `__report`, one commit under the workspace lock) and then recorded under the name as typed, so the row's name and its directory agree and the next read finds the shell's edits instead of materializing a fresh copy beside them. A directory whose canonical path is already taken is left where it is and logged, never recorded.

## Quota

`WORKSPACE_QUOTA_BYTES` (default 10 GiB) is the size the Usage page shows the workspace against and the point past which the API refuses to materialize another document (**409**) and a chat turn fails before it starts — no shell runs in a full workspace. Hard enforcement is the operator's: mount `{WORKSPACES_DIR}` on a filesystem with per-directory quotas, or back each user directory with a fixed-size image ([sandbox.md](./sandbox.md) § Operations). Usage is measured by walking the tree plus the git directory beside it (through directory descriptors that follow nothing, like every other look at the tree, so a link the shell plants cannot send the walk into another user's files), which the status route lists as its own line.

## Backups

The workspace is primary data from this version on — the parse output can be recreated from PostgreSQL, the edits, notes and originals cannot. The production backup service archives `{WORKSPACES_DIR}` with the database dump ([deployment.md](./deployment.md)), and the two are one snapshot: every workspace and shell lock is taken *shared* on `{WORKSPACES_DIR}/.repos/backup.lock` first, and the backup holds that file exclusively from the start of the dump to the end of the archive, so no rename, save, shell commit or reconciliation lands between the rows and the tree it captures. Writes wait for the backup, not the other way round — keep the backup short (a filesystem snapshot under it, where the operator has one, is the way to make it instant).
